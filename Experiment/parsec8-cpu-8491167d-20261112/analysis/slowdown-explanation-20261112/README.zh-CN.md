# 当前slowdown为什么较高：已有证据及归因边界

本分析只读取首轮已接受结果与完整gzip日志，不启动仿真，不改论文发布快照。

已证实：Native/EC退休指令数一致，增加的是执行这些指令的target cycles。以Freqmine为例，CPI从0.607升至1.708，增加301550个ROI周期；Streamcluster从0.749升至1.502，增加305846周期。两侧核频率相同，主图不计启动、软件准备和ROI后的checker接受尾部。宿主软件仿真耗时与这个比值分开。

| 程序 | Native CPI | EC CPI | ROI内版本保留等待起始事件 | ROI内写回阻塞起始事件 |
| --- | ---: | ---: | ---: | ---: |
| blackscholes | 1.709 | 1.785 | 38 | 0 |
| fluidanimate | 0.536 | 0.888 | 50 | 47 |
| bodytrack | 1.551 | 1.810 | 85 | 50 |
| freqmine | 0.607 | 1.708 | 8125 | 939 |
| swaptions | 1.064 | 2.149 | 2659 | 628 |
| ferret | 1.502 | 2.077 | 8 | 9 |
| dedup | 0.615 | 1.184 | 1487 | 40 |
| streamcluster | 0.749 | 1.502 | 2216 | 439 |

冻结模型的PRESERVATION_WAIT和WB_BLOCK事件表明，执行期间确有跨package缓存版本保留和写回资源等待。Freqmine有8125次版本保留等待起始和939次写回阻塞起始，Blackscholes分别为38和0；与前者高slowdown的现象一致。它们是状态进入事件，可以包含同一请求的重试，不能当作阻塞周期，更不能直接相加解释额外周期。

对ROI内捕获且完整匹配的SVB条目，Freqmine平均capture→ACK为4801.88 BOOM周期，promotion→ACK为107.83周期；平均4694.05周期发生在promotion之前。这支持应重点检查允许发布之前的安全水位/选择排队，以及相关存储反压，而不能只归因于最后的写回传输。生命周期可以并行重叠，甚至跨ROI边界；不能将其总和当作BOOM停顿时间。尚未区分等待checker安全水位与安全后排队各自的占比，也没有证明相关等待都阻塞了退休。

checker100MHz、BOOM200MHz属于冻结配置。四个checker并行，单个频率低不推出程序必然2倍慢。每包执行、日志/状态传输、比较和结果释放都有成本；真实总吞吐与共享缓存压力有关。现有checker局部间隔包含服务与等待，不是纯重放成本；不能从局部均值推断某个瓶颈已饱和。

Native的CPI很低也会放大比值。例如Freqmine每条指令多约1.101周期，对原0.607 CPI就是2.812倍；Blackscholes多0.076周期，对原1.709 CPI仅1.045倍。此为数学分解，并非独立因果归因。

工作负载范围仍有限：Freqmine3条事务、Dedup6字节、Streamcluster16点，其余也有缩减或真实组件重放。小输入改变分支、分配、初始化/算法阶段权重和cache局部性；不能假设它们只会放大或只会缩小slowdown。双方链接地址与cache初态不同，系统性影响尚未校准。三次重复零方差只排除当前确定性仿真的运行波动，不能消除这些混杂因素。因此1.672531倍只描述八个声明范围，不能概括完整PARSEC。

若要建立严格瓶颈分摊，需要冻结版本下与BOOM退休停顿相关联的等待计数或窄信号trace，再做同地址布局/初态的成对控制。现有日志足以支持版本保留/缓存反压为重点嫌疑，不足以给出checker/SVB/缓存各占额外周期的百分比。

证据：cpi-and-observed-waits.csv列出全部数值，evidence.json保存ROI、原始gzip哈希、原事件示例及生成RTL事件定义哈希，analyze.py可重现离线提取。MSHR数量、SVB事件或package数都不能单独替代性能归因。
