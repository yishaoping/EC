**一、明确四种事件及其顺序**

1. `close_accept(oldOwner, oldSeq, reason)`：接收关闭请求，锁存旧包身份和后续动作。开始阻止目标上下文的新dispatch，旧ROB仍可退休。barrier close ACK表示请求已接管；它不表示最终计数、PASS或safe。
2. `boundary_capture(oldOwner, oldSeq)`：空ROB、有效架构next PC、注册quiet/armed保护均满足，在RSU实际延迟捕获完成后冻结旧包最终计数和ECP。允许同一边界生成下一包CPS，但旧包关闭不以此为前提。
3. `producer_end(oldOwner, oldSeq, finalCount)`：旧包提交观察级、GH_BUF输出以及该包ECP/CSR的源端传输都已完成，不会再产生旧包记录。通过有序、可背压的消息交给checker。
4. `result/release(oldOwner, oldSeq)`：checker完成指令、数据、ARF/CSR、局部尾部及返回清理后，沿现有result队列/CDC释放ownership。只有现有PASS协议允许安全水位前进。

关键偏序：`close_accept → 全部旧包退休 → 安全snapshot/capture → producer_end`；checker可与这些阶段并行重放。producer_end不能等待checker PASS、LSL为空或safe watermark。最终PASS仍等待全部consumer完成条件。

**二、R_IC：稳定的producer身份与统一计数**

引入独立于调度target的producer上下文：`producer_valid/owner/seq`，以及关闭事务寄存器`close_pending/owner/seq/reason/next_action/snapshot_kind`。已有`package_owned(i)`仍表示从allocation直到result-release的checker资源占有；它不能被拿来表示“该包还可以新增退休”。一个已封口但尚未PASS的包仍owned。

所有计数更新集中到一个next-state定义，移除各FSM分支重复写counter的模式。定义：

```text
delta(s,t) = 本拍实际arch_valid退休中、按既有监控上下文规则属于s的指令数
             排除既有协议不计数的mret/sret/ecall
C(s,t+1)   = C(s,t) + delta(s,t)       （producer仍开放时）
N(s)       = boundary_capture冻结的C(s)
final(s)   => 后续delta(s)=0
```

count的归属取稳定的producer/closing owner，不取在cooling更新的`crnt_target`。计数资格由包生命周期和实际架构退休决定，不再由`fsm_check`枚举决定。close请求当拍、postcheck、等待调度、cooling、snap等待阶段，只要有合法旧包退休，就必须且只能计入一次。未分配的startup drain、非目标上下文及真正退出后不计入旧包。

`postcheck`仅接管关闭，不设置done。drain期间继续发布增长的计数，done保持0；在实际RSU capture确认且架构冻结后，才把旧包计数锁为最终值。最后一笔提交与捕获在设计上不能同拍，仍用断言约束；计数公式保留当前拍delta，防止FSM迁移吞掉最后一笔。

低位count和final标志分开保存，组合输出时才拼接，禁止用16位加法把count进位误作done。清零只针对匹配seq的释放/新allocation初始化；release与allocation的优先级显式化。正在开放的producer不能因旧clear电平而丢计数或被复用。若收到活动producer的FAIL/CANCELLED释放，进入现有失败收尾语义并阻止复用，不能把它当正常成功边界。

移除/统一当前被末尾连接覆盖的`cdc_cnt`输出赋值；保留经硬件证实的连续状态发布语义，不恢复实际上已被覆盖的“四周期输出”行为。

**三、关闭旧包必须先于、且独立于等待新checker**

Recommended FSM行为是`OPEN → DRAIN_OLD → CAPTURE_OLD → EMIT_OLD`，之后按请求选择继续、等待或退出。具体状态名称可以复用现有枚举，但所有路径必须经过同一关闭事务。

- 调度可以在drain期间预选/预留下一checker；没有空闲checker时，必须仍然能drain、捕获并发送旧包ECP和producer_end。
- 在安全capture时已有合法新checker：可保留同一snapshot同时作为旧包ECP、新包CPS的现有优化。old/new身份在请求中分别锁存。
- 没有新checker，或真实exit：执行ECP-only capture/merge。之后等待释放再做CPS-only启动；不能再次给已经关闭的旧包发ECP。
- 无空闲checker时，目标程序不能穿过无owner区间继续退休。旧包源端关闭完成后等待，消费者继续运行并释放资源；非目标进程保持原来可执行的语义。
- 新producer开始退休之前，旧包的提交观察级和GH_BUF尾部必须排空，关闭描述符必须已经可靠保存；先完成旧源端传输再放开新dispatch。该等待不包括checker PASS。
- 不恢复旧`functionalBarrierStall`。barrier ACK之后仍允许旧ROB合法退休；实际GH_BUF/CDC/RSU背压照常生效。

`R_RSU`需支持显式的`ecp_valid/owner/seq`、`cps_valid/owner/seq`和snapshot格式，锁存到frame完成，不能随scheduler target变化。保持当前延迟捕获与hold，提供实际capture完成/源端merge完成事件。ECP-only时必须保留ARF类型编码7，仅把CPS目的置无效；把整个pidx清零会使RocketTile不再识别ARF，这不等价于“只发ECP”。继续保留merge末拍背压保护。

| 普通threshold切包 | 停止新dispatch，全部旧ROB退休被计数，最终count/ECP/records覆盖同一前缀。 |
| LSL memory/CSR/RoCC或BJL高水位 | 走同一close；保留真实背压，持续发送live count，让checker边重放边腾空间。 |

| barrier与mode_switch/mode_ret/exception并发 | barrier只是close原因；snapshot格式由实际架构模式边界决定，包含原本要求的CSR内容，不能强制普通ctrl=0格式。 |
| 普通/特权无空闲checker，原ctrl=1/5 | ECP-only关闭不等待新slot；关闭后暂停目标程序，随后ctrl=2语义恢复。 |

| 首次start/恢复，原ctrl=2 | 没有旧producer时只做CPS，不伪造seq0 ECP/done；startup无有效nextPC时保留受限的首次退休建立PC路径。 |

ctrl=0/4、1/5、2、3的正常/特权、暂停/恢复、真实退出功能保留，但不再让一个ctrl同时隐含“旧owner”“新owner”“snapshot格式”“close完成”。架构异常/返回所需的redirect必须先被现有next-PC/quiet guards吸收，不能把handler指令错误纳入一个无法按原格式重放的普通包。

process限定不能简单给整条`rsu_hang`加门控。drain dispatch hold应区分“目标上下文冻结”和“已接受snapshot的原子捕获hold”；后者必须跨越完整延迟捕获，即使live process信号改变也不能半途撤销。commit的上下文资格和owner应与commit uop一同经过tile寄存级，不能用延迟uop配实时资格造成一拍错配。已有GH forwarding/监控窗口的功能约定保留，不能把非目标流量强行计入以凑平计数。

**五、计数传输与seal：推荐使用带seq的进度消息和有序END**

完整方案选用以下明确协议，不再依赖一个不断被覆盖的全BOOM seal电平。

1. 现有控制CDC传递带seq的live count。消息至少包含`{seq,count,valid}`，owner由唯一合法的checker/BOOM路由确定；可保持现有status字段。drain时计数变化本身就触发待发送消息，不依赖session status或done。使用稳定的pending/in-flight寄存器：valid在ready之前持续保持、payload不变；尚未送出的中间进度可合并成同seq最新值，但不能丢最终进度或越序。
2. 源端按checker保存关闭描述符`{seq,N,source_closed}`，保持到匹配结果释放或规定的失败收尾。一个checker只有一个未释放包，因此每slot一个关闭记录足够；不能只保留全BOOM“最新seal”。没有空间时背压新边界，不覆盖旧描述符。
3. GHM在旧包最后一个data beat入队、ECP/CSR源端尾拍也完成传输后，向该checker的**同一data AsyncQueue**追加显式END记录`{kind=END,seq,finalCount=N}`。现有包data payload不重新解释；增加独立kind/metadata字段，扩展所有桥接宽度和解码。END pending保持到enq.fire；不得等待LSL为空、checker exec_done或PASS。
4. END排在该seq全部data之后；只有它deq.fire才在checker持久记录`final_count=N / done=1 / producer_sealed=1`。END不写LSL/BJL/CSR/RoCC FIFO，不冒充指令或内存事务，其ready不以LSL quiescent为条件。它也不能越过尚未接受的真实data beat。
5. checker在END前继续根据live count执行。无论控制消息与data的相对CDC延迟如何，匹配END一旦接受，旧live count都不能回退count或撤销done。收到小于已观测进度的N属于协议错误，不可强行PASS。
6. count可早于data anchor/CPS到达；为同seq保留待用状态，实际package start时带入。不能在start时把已经到达的final count清掉，也不能让旧seq的done污染复用后的slot。未分配/未来seq只在有匹配的合法pending allocation时保留。
7. producer_end证明该seq源端已关闭；之后该checker的局部CDC drain不应再依赖另一个包把全BOOM GH_BUF变空。保留consumer局部CDC连续空观察、LSL quiescent、ECP seq/frame complete和ARF/CSR gate。END与data同队列的顺序用于证明“没有更晚的旧data”，而不是拿一次empty电平代替该事实。

这样finalCount/done/seal属于同一条消息，不受多位裸同步器取样或seal覆盖影响。源端R_IC内部final可在capture完成时成立，对checker的最终边界授权则在END到达时生效。此前仍可发送N作为done=0的live进度；consumer能够排空数据，因而不会形成“先要END才能执行、先执行完才能产生END”的环。

R_ICSL继续使用注册的instruction_tail_waiting及原有正常包`N+1`/特权包`N`规则。普通startup jump的+1保留。仅在匹配seq的最终边界成立时进入tail wait；不因暂时追上live count而永久停止，也不删除现有overtake保护。

**六、容量、阈值、跨周期和Chisel生成约束**

- 当前`v1Config → WithNParaMedicBooms`为3宽、42 ROB entries；本次漏掉42条与此相符，但修复必须按参数计算，不能硬编码+42。
- `GH_TOTAL_INSTS=5000`注释定义最大包长。不能到5000才启动drain，然后默许包长变成5042。按ROB最大残留、触发/dispatch停止延迟和当拍commit宽度预留保守余量，提前触发关闭，证明`trigger_count + maximum_tail <= configured_limit`。更精确的reservation可以另行优化，本方案先选择可证明的保守余量；不在本轮凭源码拍脑袋确定周期余量。
- 同时证明15位计数及checker的N+1运算不溢出。使用扩展位运算/显式切片和overflow断言，不以饱和截断掩盖丢计数。
- 高水位是请求关闭，full/ready是传输背压，两者不能互相替代。旧ROB可以间歇stall直到checker腾出空间，但不能等待done或safe才能恢复。
- 对每个实际FIFO bank核算停止背压后仍不可撤销的寄存级enq数量，保留足够headroom；不要求LSL一次容纳整个ROB tail，也不能以全局free替代每bank容量。保留多lane beat所有目标consumer均ready才fire的语义。
- snapshot与END的ready/valid只推进寄存状态。不能新增`live commit → capture → gh_stall → commit`、`LSL/pipe empty → checker stall → empty`或`END ready → source final → END valid`的组合环。
- count、done、route、close描述符分别有唯一next-state定义；当拍分配/关闭/释放的优先级明确并有断言。不要混用Scala `var`重新绑定与Chisel `:=`连接；检查动态Vec下标宽度、Bool/UInt转换、Mux各分支宽度。
- 新的Bundle/AsyncQueue/bridge宽度从同一协议定义导出；big-core与checker未用端口显式连接。debug probes只对命名Wire/Reg使用dontTouch，避免历史动态target解析错误。

**七、有界恢复：修复xRET无限续期，但不能用cancel替代正常修复**

`RocketCore`的no-progress计时只由实际推进当前seq的事件重置：新的合法退休、匹配记录实际消费/接受、ARF/CSR阶段首次完成、END首次接受、package start/exec完成等。重复的final/seal电平、重复CSR done电平、管理循环、独立xRET均不算新进度。

保持ICSL现有trap_depth/resume_state/matching xRET逻辑。返回只恢复执行状态；随后真正的包进度才重置主计时器。正常handler允许使用配置的有限异常处理预算，不能在每次进入/返回时重新赠送无限预算；如果单独暂停主计时，暂停额度必须从上次真实进度以来累计且有限。阈值按实际时钟比及BOOM剩余watchdog预算验收，不能仅因常量都叫65535就认为次序正确。

到期沿现有CANCELLED result和清理链收尾，保持trap尚未合法返回时禁止上下文复用；CANCELLED不推进PASS safe watermark，也不解除cache安全约束。此项解决已证实的放大因素；当前工作负载的通过标准仍是完整、正确的PASS，不是提前cancel后绕开528000。

**九、为什么消除当前first-bad和regression**

对保存的600条退休序列进行逻辑重放时，558只会是done=0的中间进度。旧包后42条均加到锁存的checker1/seq0x16，最终N=600；普通checker边界对应sl_counter=601。5个store对应的指令仍可被执行并消费LSL。最后data之后的END才使done和seal成立，随后原有LSL/CDC/ARF/CSR/exec gate可以按序完成。不会再在ROB非空且允许旧包继续退休时对checker宣告“558是最终值”。

这不是保证重新仿真仍在同一FST时刻、仍分成完全同样600条：新控制时序可能改变包划分。需要证明的是对每个实际新seq，都有`final_count = 同一CPS→ECP区间的合法架构退休数`，且record属于该前缀。

相对Git基线，恢复的是“所有归属于包的退休被计数，final之后不再产生该包新退休”的功能契约；保留使ROB真正排空的有效patch。基线那些依赖停止退休而成立的假设，被明确的producer生命周期取代。正常切包、无slot、true exit、特权snapshot、非目标上下文、FIFO背压都有具体路径，不以barrier case打特判。

此前修复继续受到以下不变量保护：

- snapshot仍需要empty ROB、valid committed next-PC、注册quiet/armed，捕获窗口仍冻结；不会回到stale head PC或can_commit_hint边界。
- GH_BUF记录仍覆盖整个旧包，最后记录送出前不换归属；LSQ已经锁存的seq/token不被live新seq重写。
- LSL的read/prefetch、注册payload/valid、type/address匹配、仅fire出队全部保留。不能丢掉5条尾store、放宽match或清空FIFO来伪造完成。
- producer_end只授权source已关闭；消费者仍要求局部尾部、ARF/CSR、exec全部完成，result仍保持到fire，BOOM仍只认sequenced release。
- barrier close ACK不代替PASS；L2仍要求matching ACK且`barrierSeq <= safeWatermark`，保留TtoN、metadata-clear顺序和strict token一次性完成。
- 上述反馈都通过寄存事件推进；不把已排除的组合环重新接回来。
