# `assert__assert_21` at 461000: 根因分析（只读）

## 结论

`461000` 不是首个错误，而是 BOOM 在长期无提交后的 pipeline watchdog。当前波形中最早可以直接证明的功能错误发生在 FST `393657`：Rocket checker 发出 load 请求时，`R_LSL` 从 FIFO 队首取出了一个 store 项，并把这个 store 项作为 load 返回。ELU 随即产生 `io_error_ld=1`，checker 将包置错；该包随后被取消，安全水位停在包序号 1，DCache 开始阻塞跨包请求，最终 BOOM 无 ROB commit 并在 `461000` 触发 watchdog。

同时，快照边界存在一个独立的上游时序错误：FST `393089` 对外出现了 `packet_alloc_valid`，但到 `393091` 时 `active_packet_seq` 仍为 1，而 `packet_alloc_seq` 已经是 2。这说明分配信号是由组合逻辑产生的短脉冲，R_IC 的顺序寄存器没有在同一个边界采纳它。它改变了包所有权/数据流边界，并使 R_LSL 的潜在协议缺陷在这次运行中暴露；但当前波形已经足以证明 R_LSL 错配本身是首个功能性错误。

## 立即功能错误：R_LSL 消费了错误类型

`rocket-chip/src/main/scala/r/R_LSL.scala` 的数据编码为：

```scala
Cat(io.m_st_valid(i), io.m_ld_valid(i), io.m_ldst_data(i), io.m_ldst_addr(i))
```

因此 FIFO 项的 bit 129 是 store 标记，bit 128 是 load 标记。当前 dequeue 逻辑（约 130-136 行）只检查请求有效、队列非空和 kill：

```scala
deq_valid(i) := lsl_deq_bank === i.U &&
                io.req_valid &&
                !u_channel(i).io.empty &&
                !io.req_kill
```

它没有检查请求类型是否与队首项的 bit 129/128 一致，也没有检查请求地址是否与队首地址一致。`io.req_ready`（约 150 行）只要任意 LSL FIFO 非空就为高；`io.ld_deq`（约 163 行）又根据请求命令而不是实际 FIFO 项类型报告 load dequeue。于是 393653 的 load 请求能够消费队首 store。

随后 `out_packet = Mux1H(RegNext(deq_valid), deq_data)` 在下一拍输出该 store 项，而 `resp_valid_reg` 仍由请求有效和“FIFO 非空”决定（约 142-151 行）。这正好产生 393657 的 store 返回地址和 load 请求地址不一致，ELU 直接置 `io_error_ld`。

这是当前波形已经证明的**立即阻塞条件**。它不是由 watchdog 推断出来的，也不是仅凭 FIFO 空电平推断出来的。

## 上游边界错误：snapshot allocation 没有原子采纳

`rocket-chip/src/main/scala/r/R_IC.scala` 约 184-188 行把 `snapshot_accepted` 作为组合信号生成；约 216、223-231 行又直接用它同时驱动分配输出和更新顺序寄存器：

```scala
val package_allocated = snapshot_accepted && !ctrl(0).asBool
when (package_allocated) {
  packet_seq_counter := allocated_packet_seq
  active_packet_seq  := allocated_packet_seq
}
io.packet_alloc_valid := package_allocated
io.packet_alloc_seq   := allocated_packet_seq
```

当前波形显示 `package_allocated/packet_alloc_valid` 在 393089 的时钟边界之后才可见，并在 393091 消失；同一时段 `active_packet_seq` 仍为 1，`packet_alloc_seq` 为 2。`core.scala` 中新增的 `snapshot_quiet_armed = RegNext(snapshot_quiet)` 只延迟 ready 条件，没有把 `snapshot_accepted` 变成独立的、跨采样边界保持的 fire/ack 握手。因此“对外已分配”和“R_IC 内部已更新所有权”仍可分离。

这解释了为什么当前包边界和 LSL 数据流时序发生变化。它是**强支持的上游触发因素**，但不能替代对 R_LSL 的直接修复；即使边界时序恢复，R_LSL 当前也仍缺少类型/地址匹配协议。

## 错误后的放大链

```text
R_LSL load 请求消费 store 队首项
  -> ELU 地址/类型校验失败
  -> package_error 持续记录
  -> checker 包 1 在 414785 被取消
  -> safe watermark 无法越过包 1
  -> crossPackagePendingSeq=1 / crossPackagePending=1
  -> DCache 周期性跨包阻塞和 s2_nack
  -> BOOM 最老 STQ/ROB 工作项反复重试，提交停止
  -> idle_cycles 达到 2^18
  -> `assert__assert_21` at log 461000
```

这条链中，LSL 错配和 package cancel 是当前波形直接证明的；水位阻塞和 DCache nack 有对应观测；最终“无提交达到 watchdog”由断言本身和波形末端共同证明。

## 尚未单独证明、但需要保留的风险

`R_ICSL.scala` 约 135-139 行在 `new_commit` 同时到达时使用 `sl_counter + 1` 进行完成判断，约 174 行再递增 `sl_counter`。已有 d7 波形显示在 `sl_counter == ic_counter_shadow` 时可能先完成再递增一拍。这是独立的边界 off-by-one 风险，但不是本次 393657 首个错误的直接证据，不能用它替代 LSL 错配结论。

## 结论分级

- **已证明的最终症状**：BOOM `idle_cycles` watchdog 在日志 461000 触发。
- **已证明的立即功能错误**：R_LSL 用 load 请求 dequeue 了 store 队首项，导致 ELU `io_error_ld` 和 `package_error_now`。
- **已证明的后续结果**：包被取消，`crossPackagePendingSeq=1`，DCache 跨包阻塞，最终没有 ROB commit。
- **强支持的上游触发因素**：snapshot allocation 是半周期组合脉冲，`packet_alloc_seq` 与 `active_packet_seq` 在边界不一致。
- **尚未证明为本次首错的独立风险**：R_ICSL 的 `sl_counter + 1` 完成判断。
