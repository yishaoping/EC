benchmark output is still functionally wrong:


## Findings

### 1. Checker result transport did not lose three results

The current log reports exactly 254 allocated, 254 completed, and 254 passed.
The per-package checker result path therefore has no count mismatch in this
run. This does not prove that the checker saw every architectural instruction
or that the overall memory image is correct. The benchmark checksum disproves
end-to-end correctness.

At source level, `R_IC` package allocation is generated by
`snapshot_accepted` (`R_IC.scala` around lines 200-215). The DCache increments
`allocatedPackages` on the allocation pulse and increments completion/pass
counters only for accepted sequence-matched results (`dcache.scala` around
lines 1077-1160 and 1312-1365). The exact number of allocations is therefore a
workload/ownership observation, not a result-CDC drop count.

### 2. Address-statistics sequence ownership remains broken

The current error is `0x10`, which maps to `errMalformedEvent` in
`PackageAddressStats.scala`. An event is malformed if its packet sequence is
zero, is already at or below the safe watermark, or its access crosses a cache
line (`processMalformed`, around lines 240-248).

The source still assigns address-event ownership from the live global sequence
at retirement:

```scala
io.dmem.address_stats_event(w).bits.packetSeq := io.core.active_packet_seq
```

This is used for both stores and loads in `lsu.scala` around lines 1834-1851.
It is not the sequence stored with that particular LDQ/STQ operation. The
recent `core.scala` change also keeps R_IC's last allocated sequence connected
to LSU after R_IC leaves `fsm_check`. That fixes the zero sequence symptom for
some events, but creates two ownership hazards:

1. A retirement from an older queue entry can be tagged with a newer package's
   live sequence.
2. A retirement after a package passed can carry the last sequence, which is
   now `<= safePacketWatermark` and is rejected as stale.

The error bit alone does not identify which malformed predicate fired. The
source/dataflow mismatch is proven; attributing this particular run's first
error to one predicate is strongly supported but requires a focused waveform
sample of `processEvent.packetSeq`, `safeWatermark`, and `processCrossesLine`.

### 3. The active sequence mux can affect coherence tracking

The LSU stores a sequence in STQ entries and sends it through DCache/MSHR
requests. DCache uses nonzero request sequence to mark dirty lines as tracked
and to decide whether overwriting another package's dirty line must wait for
the safe watermark (`dcache.scala` around lines 1000-1016 and 1530-1565).

Before the latest change, BOOM drove zero to LSU outside `fsm_check`. The new
continuous mux supplies the last allocated sequence in those periods too.
This expands packet ownership to operations that did not execute in the active
checker interval and can change shadow-line tracking, replay, and overwrite
ordering. It is a high-risk contributor to the changed workload behavior and
checksum, although the three fewer allocations cannot be attributed to it
without the previous waveform.

### 4. Statistics show an ownership/window mismatch, not strict double count

`boom_arch == boom_strict` for both Store and Load, so the strict completion
logic is not adding a duplicate count in this run. However:

```text
Store: 61383 - 60679 = 704
Load:  78334 - 76607 = 1727
```

The BOOM counters are gated by global `traffic_counting`, while checker totals
represent traffic associated with checker packages. The live active sequence
does not establish that every operation in the BOOM measurement window belongs
to a checker package. These totals therefore still have incompatible ownership
unless the package boundary is carried with each operation and the stop/drain
boundary is unified.

## Root cause assessment

**Proven:** overall benchmark correctness still fails; the checker package
result counters are internally balanced; address statistics reject malformed
events; architecture event ownership is sampled from a live global packet
sequence instead of a per-operation sequence.

**Strongly supported:** holding the last packet sequence globally past
`fsm_check` causes old or out-of-package LSU operations to receive incorrect
sequence ownership. This can explain both malformed address events and changed
cross-package dirty-line behavior.

**Not proven from saved artifacts:** which exact source edit caused the
257-to-254 allocation change, which malformed predicate first raised `0x10`,
and which exact cross-package writeback caused `parent_checksum=40304848`.

## Repair direction

1. Restore the packet-tracking sequence qualification for coherence traffic:
   requests outside a valid checker-owned interval must not inherit R_IC's last
   sequence. Do not use a persistent global active sequence as a substitute for
   per-operation ownership.
2. Carry an explicit sequence-valid/sequence tag with each operation from its
   package boundary through LDQ/STQ and commit. Address statistics must use
   that captured tag, not the current R_IC sequence at retirement. A zero or
   stale tag must be treated as an ownership/window issue and diagnosed, not
   dropped to force PASS.
3. Define the measurement start/stop boundary over the same package set as
   `checker_sum`, including drain of already-owned queue entries. Preserve
   `boom_arch == boom_strict`; do not alter strict token completion to hide the
   mismatch.
4. Preserve the prior shadow-writeback fixes (`TtoN`, no reissue while metadata
   clear is pending). The current run's 254/254/254 does not justify reverting
   those protocol corrections.
5. Before another full benchmark, add focused observability for first malformed
   event (`packetSeq`, `safeWatermark`, `processCrossesLine`) and per-package
   allocation/result sequences. Compare the resulting sequence list with the
   prior run if its waveform can be recovered.

Do not accept package count equality as proof of end-to-end correctness. The
run passes only when the benchmark checksum matches its known-good result,
address statistics are valid, and BOOM/checker accounting agrees under the
same package window.
