## C. `slotEpoch` 精确等价方案

源码依据：[定义与 reset](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:516)、[probe](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:1105)、[cross-clear](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:1416)、[refill commit](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:2061)。

### 当前 next-state 合同

对任意槽 \(j=(s,w)\)，定义当前时钟沿前状态：

```text
E_j = slotEpoch[s][w]
R_j = reservedEpoch[s][w]
inc16(x) = (x + 1) mod 65536
```

probe 更新条件：

```text
P = prober.meta_write.fire
    && !prober.meta_write.bits.data.coh.isValid()
    && !slotReserved[probeSet][probeWay]
```

cross-clear 更新条件：

```text
C = crossPackageMetaClear.fire
```

refill 更新条件：

```text
r = {in1.bits.addr[13:6], OHToUInt(in1.bits.way_en)}

G = dataWriteArb.in(1).fire
    && refillLastBeat
    && (in1.bits.slot_epoch == R_r)
    && slotReserved[r]
    && (E_r != R_r)
```

再定义：

```text
P_j = P && probeIndex == j
C_j = C && clearIndex == j
F_j = G && r == j
```

**已证明，当前精确方程是：**

```text
old_next[j] =
    reset ? 0 :
    F_j   ? R_j :
    C_j   ? inc16(E_j) :
    P_j   ? inc16(E_j) :
            E_j
```

这里 `reset` 指 DCache 寄存器实际 reset 条件。

| 优先级，高→低 | 写源 | 写入值 |
|---:|---|---|
| 4 | reset | `0` |
| 3 | refill final commit | 当前 `reservedEpoch[j]` |
| 2 | cross-package clear | 当前 `slotEpoch[j]+1`，截断 16 位 |
| 1 | probe invalidation，且当前未 reserved | 当前 `slotEpoch[j]+1`，截断 16 位 |
| 0 | hold | 当前 `slotEpoch[j]` |

replacement、eviction、install、reservation create/clear、completion、replay **没有其他直接 `slotEpoch` 写源**。它们可以影响上述事件的产生，但不能因此新增 epoch 更新。

所有 RHS 和 guard 都读取**更新前状态**：

- 同周期 reservation create 不会向 refill 转发新 `reservedEpoch`。
- 两个 increment 不会叠加为 `+2`。
- 同槽存在多个实际写使能时，按上表覆盖。
- probe 与 refill 对同槽分别要求 `!slotReserved` 和 `slotReserved`，其 guard 已排除这一特定冲突；候选不依赖额外事件互斥假设。

生成代码也确认了顺序：[当前更新函数](/data1/gzh/EC/chipyard/sims/verilator/generated-src/chipyard.TestHarness.v1Config/chipyard.TestHarness.v1Config.debug/VTestHarness___024root__226.cpp:3054) 的分支是 refill、cross-clear、probe，reset 分支在 784388 附近统一清零。

### 各候选的新方程及证明

**Patch 1：**

相同 payload 来源和索引使所有 selected wire 等于原表达式，因此：

```text
G' = G
new_A_next[j] = old_next[j]
```

**B1：**

每个目标使用：

```text
writeEnable[j] = G && r == j
writeData[j]   = R_j
```

于是：

```text
new_B1_next[j] =
    reset ? 0 :
    (G && r == j) ? R_j :
    C_j ? inc16(E_j) :
    P_j ? inc16(E_j) :
          E_j
```

它与旧方程逐项相同。核心恒等式为：

```text
r == j  ⇒  reservedEpoch[r] == reservedEpoch[j]
```

不同静态目标写不同寄存器，循环迭代之间不新增 priority。

**B2：**

固定 set `s` 内仅动态选择 way。对目标 `(s,w)`：

```text
G && refillSet == s && refillWay == w
    ⇒ reservedEpoch[s][refillWay] == reservedEpoch[s][w]
```

因此 `new_B2_next[j] = old_next[j]`。

**B3 的预解码静态写：**

只将 `r==j` 拆成公共 set/way equality，仍是 B1 方程，同样等价。

这些证明覆盖当前 256×2 配置的全部索引与两位 mask，包括 `00/11`。其他参数配置须另做位宽和边界验证。

以下均按源码 last-connect 顺序，高→低；未列事件表示 hold。

| 状态 | 非 reset 写优先级 |
|---|---|
| `slotReserved` | publish clear ＞ reservation create |
| `installActive` | publish clear ＞ install fire set ＞ reservation create clear |
| `completionPending` | completion dequeue clear ＞ completion enqueue set |

| `imageValid` | semantic write true ＞ refill false ＞ cross false ＞ probe 条件 false |
