## 6. 助手 · 2026-08-11T08:02:55.805Z

总体判断：该方法对 `store_uncache` 可以作为“平均延迟估计”，但不能直接称为严格时间戳测量；对脏写回直接套用同一公式目前不合理，因为 checker 统计的是指令，而写回统计的是 cache line，两者没有一一对应关系。

**公式成立的条件**

设 BOOM 中第 \(i\) 个事件的物理时间为 \(B_i\)，checker 完成时间为 \(C_i\)，则：

\[
\overline{L} =
\frac{\sum_{j=1}^{4}\sum C_{j}-\sum B_i}{N}
\]

确实等于逐事件延迟的平均值，但必须同时满足：

- 每个 BOOM 事件只分配给一个 checker，并且恰好完成一次。
- BOOM 事件数 \(N_B\) 等于四个 checker 事件数之和 \(N_C\)。
- 两侧统计窗口完全相同。
- 所有时间戳已经转换到同一个物理时间轴。
- 分母是总事件数 \(N\)，不是 checker 数量 4，也不是四个核计数的简单平均。

不要求 checker 按 BOOM 的事件顺序完成，这是时间戳求和法的优点。

**当前 `store_uncache` 的实际含义**

当前 BOOM 的统计点是 IOMSHR 的 TileLink A 请求被接受，即 `mem_access.fire`，参见 [mshrs.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/mshrs.scala:462)。此时 MMIO store 已经对外不可撤销。

Rocket 的统计点则是 LSL 返回、指令成功进入 WB，参见 [RocketCore.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/rocket/RocketCore.scala:877)。

因此二者相减得到的是：

```text
IOMSHR A通道接受 -> checker重执行WB
```

它不是严格的：

```text
BOOM提交/日志产生 -> 错误被发现
```

也不是：

```text
BOOM提交 -> 整个checkpoint确认通过
```

如果未来实现 check-before-communication，使 MMIO store 等 checker 通过后才能发出，那么 A 通道时间反而会晚于 checker 时间，当前公式会产生负值或测量到完全不同的含义。此时起点应改成 BOOM commit、日志入队或 barrier 开始，而不是 A 通道发送。

**主要潜在问题**

1. **各 hart 的 `cycle/mcycle` 不是天然的全局时钟。**  
   当前配置是 BOOM 200 MHz、四个 Rocket 100 MHz，参见 [RocketConfigs.scala](/data1/gzh/EC/chipyard/generators/chipyard/src/main/scala/config/RocketConfigs.scala:9)。除以频率只能消除比例差，不能消除每个时钟域的起始偏移。正确模型应为：

   \[
   t_h = cycle_h/f_h+\beta_h
   \]

   异步复位释放、时钟相位和启动时间都会形成 \(\beta_h\)。若不校准，平均值中会一直保留按各 checker 负载加权的固定偏差。

2. **`mcycle` 不一定连续表示 wall-clock。**  
   当前 CSR 实现在 `mcountinhibit` 置位或 `csr_stall` 时停止累加，参见 [CSR.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/rocket/CSR.scala:699)。WFI、cease、调试、写 `mcycle` 或未来 DVFS 都会破坏按固定频率换算的假设。

3. **CDC 延迟会被统计进去，但未被单独区分。**  
   BOOM 到 checker 经过深度 256 的异步队列，参见 [GHM.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/guardiancouncil/GHM.scala:107)。最终数值混合了日志等待、调度、CDC、checker 执行和 checkpoint 等待，无法定位瓶颈。

4. **checker WB 不一定是“确认安全”的时间。**  
   单条 store 在 WB 完成，只说明该条重执行到达完成点。若安全策略以整个 segment/checkpoint 成功并按序提交为准，应使用验证 watermark 推进时间，而不是单条 WB 时间。错误或异常导致没有 WB 的事件还会形成幸存者偏差。

5. **现有 checker 的 store 校验并不完整。**  
   当前比较有效虚拟地址和按 size 截取的数据，参见 [R_ELU.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_ELU.scala:90)，并没有独立证明物理地址、byte mask、实际 L1/TileLink 写入和设备只执行一次。因此统计的是“当前 checker 机制的完成延迟”，不是完整 store 正确性的检测延迟。

6. **`store_uncache` 类别过于混杂。**  
   它可能包含不同地址空间、不同 manager、PutFull/PutPartial、不同 size 和不同设备。UART、CLINT、PLIC 或其他 MMIO 的行为差别很大，混为一个平均值解释性较弱。还需要区分 A 请求接受、D Ack 成功、`denied`、`corrupt` 和超时。

7. **计数器和时间戳和必须原子快照。**  
   当前软件逐项执行 RoCC 读取，参见 [secondary.c](/data1/gzh/EC/Software/Test/secondary.c:19)。读取期间若还有事件发生，事件数与时间戳和可能来自不同瞬间。应使用 freeze/snapshot，或者在完全排空后读取，并检查前后 generation。

8. **绝对时间戳求和很容易溢出。**  
   单个 64 位 `mcycle` 很难溢出，但“每个事件都加当前绝对周期”会以事件数乘运行时间增长，远快于普通计数器。需要至少 128 位累加、窗口基线或明确的模运算规则。软件换算也应采用整数/有理数，避免 `float` 精度损失。

9. **平均值会隐藏最危险的尾延迟。**  
   检测框架更关心最长错误暴露窗口。仅有 `sum/count` 无法发现少量事件等待很久。至少还应保留 `max`、分桶直方图以及 P50/P95/P99，并按 checker 分开报告负载不均。

**写回统计的额外问题**

当前 L1→L2 在 C 通道首拍统计 line 级消息，数据型 `ReleaseData/ProbeAckData` 归为 dirty，参见 [dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:846)。

当前 L2→DRAM 则在 InclusiveCache 的 `SourceC.req.fire` 统计 DCache 来源 victim，参见 [Scheduler.scala](/data1/gzh/EC/chipyard/generators/sifive-cache/design/craft/inclusivecache/src/Scheduler.scala:144)。这还不是 AXI 写完成；clean victim 通常也不产生真正的 DRAM 数据写。

因此存在以下问题：

- 一条 dirty cache line 可能包含多条 store、多个 checkpoint，甚至同一字节被多次覆盖。
- 一个 store 可能从未形成写回，也可能同一 line 因 Probe、重新获取和再次淘汰形成多次传播。
- 当前 L2 的 `dcache` provenance 只说明该 line 曾被 DCache 使用，不能表达具体 BOOM store、checker、segment 或验证状态。
- “脏且未校验”不能从 dirty bit 和 store 计数推导出来，必须为 line 或 byte/sector 保存 segment ID、epoch 或 pending-validation 元数据。
- L2 还需要把验证元数据随 C 通道传播并保存在 directory/sidecar 中，否则 L1→L2 后关联关系已经丢失。
- 如果多个未校验 store 合并到一条 line，必须明确写回延迟按 line 加权、按 store 加权，还是按 byte 加权，三者结果不同。

更合理的写回分类应至少区分：

```text
L1->L2:
  eviction / probe
  Release / ReleaseData / ProbeAck / ProbeAckData
  clean / dirty
  verified / unverified
  request -> C first beat -> C last beat -> ReleaseAck

L2->DRAM:
  clean victim / dirty victim
  BOOM DCache / 其他DCache / ICache / DMA来源
  verified / unverified
  SourceC schedule -> outer C last -> AXI AW -> WLAST -> B OK/ERROR
```

对于“脏且未校验”，更建议统计：

- 未校验写回尝试次数。
- 因验证未完成而阻塞的周期数。
- 从写回尝试到验证 watermark 允许放行的等待时间。
- 实际越过 L1/L2 边界的未校验 dirty line 数，此项在正确实现中应为 0。

若确实允许未校验数据先传播，再测暴露窗口，则必须让每次写回事务携带关联的 segment/timestamp，并在对应 segment 真正按序验证后形成完成时间。不能直接用四个 checker 的 store 时间戳和减去 cache-line 写回时间戳和。

本轮仅进行了静态代码和统计口径分析，没有修改代码、运行仿真或生成硬件。

  \[
  \sum T_{completed}-\sum T_{dirty}
  \]
  确实等于总延迟，除以事件数可得平均延迟。

**主要问题**

1. **包尾时间戳不是校验完成时间**

   如果 Rocket 返回的是包内携带的 BOOM 包尾时间戳，那么它只表示该包在 BOOM 上的执行位置。  
   `包尾时间戳 - 脏行时间戳` 测量的是“最后一次写到包尾之间的 BOOM 执行距离”，不包括发送、Rocket 重执行、checkpoint 比较和返回时间。

   要测真实延迟，应在返回消息到达 BOOM 时再次采样 BOOM CSR：

   \[
   L_i=T_{\text{BOOM收到校验完成}}-T_{\text{line last write}}
   \]

   这会包含返回 CDC 延迟，但所有时间都处于同一个 BOOM 时钟域，计算严格成立。

2. **不能用 Rocket CSR 时间直接和 BOOM CSR 时间比较**

   即使分别按频率转换成纳秒，也仍然存在复位时刻、相位和计数起点偏差。频率转换只能消除比例差，不能消除时钟偏移。

   因此建议区分：

   - BOOM 包尾时间戳：随包发送并原样返回，用于确定校验位置。
   - BOOM 返回接收时间戳：返回到 BOOM 后采样，用于计算实际延迟。
   - Rocket CSR 时间：可用于分析 Rocket 内部耗时，但不直接与缓存行时间戳相减。

3. **四个 Rocket 并行完成会破坏简单的最大水位**

   当前 GHM 为每个 Rocket 使用独立异步队列，[GHM.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/guardiancouncil/GHM.scala:107)。后分配的包可能先完成。

   因此不能简单地：

   ```text
   verified_timestamp = max(returned_tail_timestamp)
   ```

   否则包 12 已完成、包 11 未完成时，包 11 对应的缓存行也会被误判为已校验。需要根据包序号维护完成表，只在之前所有包都完成后推进“连续校验水位”。

4. **CSR 周期不能唯一表示提交顺序**

   BOOM 可以同周期提交多条指令，包边界和多个 store 可能具有相同 CSR 周期。仅比较 `line_timestamp <= packet_tail_timestamp` 无法区分同周期内谁先谁后。

   应增加单调包序号或提交序号：

   ```text
   package = {sequence, start_cycle, end_cycle}
   cache line = {last_write_sequence, last_write_cycle}
   ```

   序号负责正确性判断，CSR 周期负责时间统计。

5. **包尾产生时间可能早于 store 真正写入 DCache**

   如果包尾在指令提交时采样，而 store 在之后才从 STQ 写入 DCache，那么可能出现：

   ```text
   line_last_write_cycle > containing_packet_end_cycle
   ```

   即使该包已经校验，缓存行仍会被误判为未校验。需要让缓存行保存该 store 的提交序号/提交时间，而不是简单使用较晚的 data-array 写入时钟；或者保证包关闭前相关 store 已完成 DCache 更新。

6. **“最后一次操作”应限定为最后一次脏化操作**

   Load、prefetch 和普通 refill 不应更新时间戳，否则一次校验较晚的 load 会使已经校验过的脏数据重新表现为未校验。应覆盖所有实际修改数据的路径：

   - store hit；

   - SC 成功；

   当前写回统计点是 TileLink C 通道首拍握手，[dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:847)。但受害行在更早的 `WritebackReq` 阶段已经确定，WritebackUnit 会锁存请求，[dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:83)。

\frac{\sum T_{\text{BOOM receipt}}-\sum T_{\text{line write}}}

\]

## 35. 助手 · 2026-08-12T01:48:29.051Z

问题 4 的核心是：**CSR 时钟只能说明“发生在哪个周期”，不能说明“同一周期内谁先谁后”**。

BOOM 是多发射、乱序执行核心，一个周期可以提交多条指令。假设某周期提交宽度为 4：

| CSR 周期 | 提交槽位 | 指令 | 所属校验包 |
|---|---:|---|---|
| 1000 | 0 | store A | 包 7 |
| 1000 | 1 | add | 包 7 |
| 1000 | 2 | 包 7 结束 | 边界 |
| 1000 | 3 | store B | 包 8 |

如果只记录 CSR 时钟：

```text
store A timestamp = 1000
包7 tail timestamp = 1000
store B timestamp = 1000
```

那么比较：

```text
line_timestamp <= verified_tail_timestamp
```

对 A 和 B 都成立。但实际语义是：

- A 属于包 7，包 7 校验完成后可以认为已校验；
- B 属于包 8，包 7 校验完成时还不能认为已校验。

仅靠 `1000 <= 1000` 无法区分这两种情况。

**为什么换成 `<` 也不行**

为了避免误判，可以尝试：

```text
line_timestamp < verified_tail_timestamp
```

但这样 store A 也会被判断为未校验，因为：

```text
1000 < 1000 = false
```

因此：

- 使用 `<=` 会把同周期但位于包尾之后的操作误判为已校验；
- 使用 `<` 会把同周期且确实位于包内的操作误判为未校验。

根本原因不是比较符号，而是时间戳缺少同周期顺序信息。

**多个 store 同周期的问题**

再考虑同一个周期内有多个 store：

| 周期 | 槽位 | 操作 |
|---|---:|---|
| 2000 | 0 | store line X |
| 2000 | 1 | 包 10 结束 |
| 2000 | 2 | store line X |
| 2000 | 3 | 其他指令 |

缓存行 X 采用“最后一次操作时间戳”，最后一次修改来自槽位 2。但两次 store 的 CSR 时间都是 2000。

最后缓存行保存：

```text
line X timestamp = 2000
```

包 10 返回：

```text
verified tail timestamp = 2000
```

比较结果会认为 X 已经被包 10 覆盖，但 X 的最新内容实际来自包 10 边界之后，所以尚未校验。这正是错误分类“未校验脏行”的情况。

**CSR 周期只能提供偏序**

可以把 CSR 周期理解为粗粒度坐标：

```text
cycle = 1000
```

它能确定：

```text
cycle 999 的操作早于 cycle 1000
cycle 1000 的操作早于 cycle 1001
```

但不能确定：

```text
cycle 1000, slot 0
cycle 1000, slot 1
cycle 1000, slot 2
cycle 1000, slot 3
```

之间的先后关系。数学上，CSR 周期不是每条提交指令的唯一序号，多条指令会映射到同一个值。

**推荐解决方法一：提交序号**

为每条提交指令分配严格递增的逻辑序号：

在你给出的约束下，方法总体可行，但还不能简化为“缓存行记录一个序号和时间戳，完成位图置位，未校验写回放入普通 FIFO”。以下问题仍需要明确。

1. **完成位图必须推进连续校验水位**

不能直接检查缓存行对应包的位是否为 1。

例如缓存行包含：

```text
包10：写 byte 0
包11：写 byte 8，成为最后一次脏化操作
```

若包11先完成、包10未完成：

```text
done[10] = 0
done[11] = 1
line.last_dirty_seq = 11
```

只检查 `done[11]` 会认为整行已校验，但 byte 0 仍来自未完成的包10。

正确做法是维护：

```text
verified_prefix = 最大的连续完成包序号
```

仅当：

```text
line.last_dirty_seq <= verified_prefix
```

时才认为整行已校验。这样“只保存最后一次脏化序号”才足够。

2. **完成时间不能直接采用该包自己的完成时间**

考虑：

```text
包11在小核1的时钟500完成
包10在小核2的时钟700完成
```

包11虽然先完成，但连续水位必须等包10完成后才能推进到11。因此序号11对应缓存行真正变成“连续已校验”的时间应是700，而不是500。

需要定义：

\[
T_{\text{safe}}(s)
=
\max(T_{\text{safe}}(s-1),T_{\text{complete}}(s))
\]

延迟统计使用 `T_safe(last_dirty_seq)`，而不是简单使用 `T_complete(last_dirty_seq)`。

这意味着完成位图旁边还需要保存完成时间戳。只有位图不能完成正确的延迟配对。

3. **普通 FIFO 不能天然保证正确配对**

脏写回的包序号未必按写回顺序排列。例如 probe 可以先写回一个很旧的缓存行，随后 replacement 又写回较新的缓存行：

```text
FIFO entry 0：seq=20，尚未完成
FIFO entry 1：seq=8，已经完成
```

只检查 FIFO 队首会让 entry 1 长时间不能结算。更严重的是，如果等到它最终出队时才使用当前 `T_safe`，会把等待 FIFO 的时间也错误计入校验延迟。

可选方案是：

- 队列项增加 `resolved` 和匹配后的完成时间，水位推进时关联更新所有命中项；
- 按包序号建立桶，保存该包的写回数量和脏时间戳总和；
- 保留足够长的 `seq -> T_safe` 历史表，让队首出队时仍能取得当时的准确完成时间。

仅保存 `{seq, dirty_timestamp}` 的简单 FIFO 不够。

4. **包序号的粒度必须与最终完成信号一致**

当前一次 GHT 传输包含两个136位记录，见 [GH_GlobalParams.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/guardiancouncil/GH_GlobalParams.scala:9)，但 Rocket 的 `if_check_completed` 对应的是完整 checkpoint 校验段结束，见 [R_RSUSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_RSUSL.scala:296)。

因此包序号应该分配给“一次完整 checker 校验段”，不能分配给每个136位记录或每次双记录传输，否则一个完成时间无法对应多个局部序号。

5. **store 的包序号和脏化时间戳来自不同阶段**

包序号应在 BOOM 提交端确定，并随 store 保存到 STQ。store 提交后可能很久才从 STQ 发往 DCache，当前路径见 [lsu.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:833)。

## 41. 助手 · 2026-08-12T02:37:49.556Z

按照现在的定义，缓存行确实不再需要保存 CSR 时间戳，但不能说整个方案不需要时间戳：

- 缓存行保存：`epoch + last_dirty_packet_seq + valid`
- 校验完成记录保存：`packet_seq + pass/fail + Rocket CSR cycle + checker_id`
- 写回事例保存：`packet_seq + BOOM CSR cycle`

包头、包尾时间戳对于“未校验脏写回延迟”这项统计可以取消。剩余主要正确性问题如下。

**1. 小核完成时间与大核收到完成消息之间存在空窗**

这是当前最大的问题。

假设：

```text
包10在Rocket上完成校验：100 ns
完成消息到达BOOM：120 ns
该缓存行写回：110 ns
```

写回发生在110 ns时，大核位图还没收到包10的完成消息，因此会暂时认为它未校验。但根据你定义的小核校验安全时间100 ns，这次写回实际发生在校验完成之后，不应计入未校验写回。

如果直接计入，会产生：

```text
100 ns - 110 ns = -10 ns
```

因此必须把写回时的判断定义为“候选判断”：

```text
last_dirty_seq > 当前已知安全水位
    -> 暂存为候选写回
```

当包的真实安全时间确定后再最终判断：

```text
writeback_time < safe_time
    -> 真正的未校验写回
writeback_time >= safe_time
    -> 丢弃该候选，不计数
```

也就是说，当前位图状态只能决定是否需要暂存，不能最终决定该写回是否未校验。

**2. 每个包桶只保存次数和时间总和可能不够**

继续考虑包10，其安全时间为100 ns。到完成消息抵达前，桶里可能已经有：

```text
写回A：90 ns
写回B：110 ns
```

正确结果只有A属于未校验写回：

```text
count = 1
latency = 100 - 90 = 10 ns
```

如果桶里只保存：

```text
count = 2
writeback_sum = 200 ns
```

则无法把110 ns的写回B排除掉。

所以在采用“小核物理完成时间”的前提下，每个包桶必须保存候选写回时间明细，例如一个子队列：

```text
bucket[seq] = {
    candidate_writeback_cycles[]
}
```

或者保存某种能够计算：

```text
count(writeback_time < safe_time)
sum(writeback_time < safe_time)
```

的数据结构。单纯的 `{count, sum}` 只有在安全时间定义为“大核收到完成消息的时刻”时才足够。

**3. 校验安全时间必须逐包递推，不能给一次位图推进的所有包同一个时间**

假设小核实际完成时间为：

```text
C10 = 100
C11 = 160
C12 = 120
```

完成消息可能按如下次序抵达：

```text
11 -> 12 -> 10
```

包10抵达后，位图可以一次从9推进到12，但各包的安全时间不是都等于100：

\[
S_{10}=100
\]

\[
S_{11}=\max(S_{10},C_{11})=160
\]

\[
S_{12}=\max(S_{11},C_{12})=160
\]

一般公式是：

\[
S_i=\max(S_{i-1},C_i)
\]

因此完成表不仅要保存完成位，还要保存每个包的：

```text
pass
completion_cycle
checker_id
```

位图推进时必须逐项生成安全时间。

**4. 跨核时间比较必须先变成相同单位**

你暂不考虑初始偏移和相位差没有问题，但频率比例仍必须处理。

例如：

```text
Rocket：100 MHz
BOOM：200 MHz
```

不能直接比较：

```text
rocket_cycle < boom_cycle
```

需要转换到共同时间单位，或者在硬件中转换成等价 BOOM 周期：

```text
rocket_time_in_boom_cycles = rocket_cycle * 2
```

因为问题1要求在硬件中排除“完成后、消息返回前”的写回，所以这种转换不能只在最终软件打印时进行。否则硬件不知道候选写回是否满足：

```text
writeback_time < safe_time
```

如果四个Rocket频率不同，还必须为每个完成时间保留`checker_id`。

**5. 包序号必须在BOOM提交端确定并随store传递**

不能在store最终访问DCache时读取“当前包序号”。BOOM的store在ROB提交后，还可能在STQ等待较长时间才真正送往DCache，当前路径正是这种结构，[lsu.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:833)。

正确链路应为：

```text
ROB提交时确定所属包序号
    -> 写入对应STQ项
    -> 随DCache请求和重放传递
    -> 随MSHR合并/填充传递
    -> 数据阵列真正被修改时写入缓存行序号元数据
```

还必须明确同周期多条提交指令跨越包边界时，每个提交槽位属于哪个包。

**6. 缓存行序号必须表示所有脏数据的最大包序号**

缓存行可能包含来自多个包的部分写：

```text
包10写byte 0
包12写byte 8
```

缓存行应保存：

```text
last_dirty_seq = max(10, 12) = 12
```

由于安全水位只能连续推进，当包12安全时，包10也一定安全，因此最大序号足够。

但以下条件必须成立：

- 包序号是全局单调序号，而不是每个小核各自编号。
- store miss及secondary store合并时取最大序号。
- refill不能覆盖已经合并进去的store序号。
- SC失败不能更新序号。
- SC成功、AMO和普通store都必须在真正修改数据时更新。
- nack或replay不能重复或提前更新。

**7. 完成、通过和失败必须是三个清晰状态**

建议每个完成槽使用：

```text
allocated
completed
passed
completion_time
```

安全水位只能越过`completed && passed`的包。

另外，所有已分配序号最终都必须进入某种终态：

```text
passed
failed
cancelled
```

否则一个因异常、调度取消或恢复而永远不返回的包会永久堵住连续水位。

如果一个包失败，后续策略也必须明确：

- 停止安全水位并保留所有后续未校验统计；
- 或在恢复后开启新epoch并重新开始统计。

不能把失败包仅仅当作普通完成包置位。

**8. `if_check_completed`必须与最终pass/fail严格匹配**

当前 `if_check_completed` 是checkpoint扫描计数结束信号，[R_RSUSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_RSUSL.scala:296)。新增返回记录时必须确认：

```text
completion_cycle
pass/fail
packet_seq
```

在同一个逻辑完成事件上锁存。

如果错误检测结果比`if_check_completed`晚一拍，便可能先把包标成passed并推进水位。更稳妥的语义应是：

```text
package_result_valid
package_result_pass
package_result_seq
package_result_cycle
```

其中`result_valid`只在所有LSL比较、存储检查以及ARF/FARF比较结果已经归并后有效。

**9. 写回与安全水位同周期更新需要固定规则**

可能同一大核周期内同时发生：

```text
完成记录更新安全水位
TileLink C通道首拍写回
```

需要明确本次写回使用旧水位还是新水位。采用最终时间比较后，可定义为：

```text
writeback_time < safe_time：未校验
writeback_time >= safe_time：已校验
```

这样相等时视为已经安全。如果希望保守统计，也可以使用`<=`，但必须固定规则，否则结果会有一周期随机偏差。

**10. 写回序号必须随WritebackReq锁存**

这一点仍然必要。缓存行的序号应在受害行确定时，与tag、set、way一起进入WritebackUnit，而最终计数发生在C通道首拍，[dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:847)。

不能在C通道握手时重新读取序号阵列，因为原set/way可能已经被填入新缓存行。

**11. 测量开始和复位需要epoch**

统计复位时，DCache中可能已有脏行，完成位图中也可能存在旧包。仅清计数器会导致旧序号和新序号混淆。

至少需要：

```text
measurement_epoch
packet_seq
line_seq_valid
line_epoch
completion_epoch
```

或者在开始测量前保证DCache全部清空且没有在途包。前者更可靠。

**12. 观测队列溢出会使结果失真**

不阻塞写回是合理的，但候选写回事例数量不受“未完成包跨度”限制。同一个未完成包可能对应多次相同地址的换入、脏化和写回。

因此除了位图宽度，还要考虑每个包候选写回时间存储的容量。若满时继续写回，必须：

```text
dropped_count += 1
statistics_valid := false
```

否则软件打印出的平均值看起来正常，实际已经漏样。只做观测可以丢，但必须显式说明结果无效。

**结论**

缓存行和校验包的头尾CSR时间戳可以从这项统计中移除。最低限度的数据结构应是：

```text
cache line:
    {epoch, last_dirty_packet_seq, valid}

completion table:
    {epoch, packet_seq, completed, passed,
     checker_id, checker_completion_cycle}

writeback bucket:
    {epoch, packet_seq, candidate_writeback_cycle_list}
```

最关键的剩余问题是：由于小核完成消息存在返回延迟，包桶不能仅保存次数和时间总和，必须保留足够的信息，在安全时间确定后排除那些实际上发生在校验完成之后的候选写回。否则会出现负延迟和未校验次数虚高。

## 实现要点

### 时间源

`CSR.scala:1369`：

```scala
io.time := reg_cycle
```

因此 BOOM 和 Rocket 引出的都是各自 CSR 的 `cycle/mcycle`，不是共享 `mtime`。

### store_uncache 延迟

BOOM：

- 完成点是 `mshrs.io.traffic_store_complete`，即不可缓存 store 的 TileLink A 请求真正被接受。
- 同周期采样 BOOM CSR `cycle`。
- 维护数量和 `store_uncache_cycle_sum`。

Rocket：

- 只在 checker 重执行成功完成时统计不可缓存 store 数量。
- 每包暂存 `store_uncache` 数量。
- 等 ARF 和必要 CSR shadow 都校验完成，形成整包结果时，用 Rocket CSR `cycle × 本包数量` 累加。
- 取消包清除本包暂存，不产生包尾时间和。

软件：

```text
hart_time_ns = cycle_sum × 1e9 / hart_frequency
latency_sum  = 四个 Rocket time_sum 之和 - BOOM time_sum
average      = latency_sum / BOOM store_uncache_count
```

先检查 BOOM 数量等于四个 checker 数量总和。不同核时钟偏移暂按用户要求忽略，所以该值是近似检测延迟。

### 包序号与返回结果

- 32 位全局包序号，0 表示不属于校验包。
- `R_IC` 在 `snapshot_accepted` 时分配 `packet_seq_counter + 1`。
- 序号随 packet、ARF/CSR 数据跨 GHM 到 Rocket。
- Rocket 返回 `{valid, status, seq}`，状态为 `pass/fail/cancelled`。
- Rocket 本地 Queue 加 GHM AsyncQueue，均有反压，避免结果静默丢失。
- BOOM DCache接收所有 checker 结果。

### 位图和安全水位

BOOM DCache 内有 256 项窗口：

- `bitmapAllocated`
- `bitmapCompleted`
- `bitmapPassed`
- `bitmapSeq`

结果可以乱序到达。只有从当前水位开始连续分配、完成且通过的包，才推进 `safePacketWatermark`。

同周期分类使用已经合入新结果后的 `newSafePacketWatermark`，避免把刚完成的包误判为未校验。

位图时间不是 Rocket 时钟；当前“校验安全时间”定义为结果到达 BOOM 位图并推进水位时的 BOOM CSR `cycle`。

### 缓存行脏化归属

BOOM DCache 每个 `set × way` 保存：

- `dirtyPacketSeq`
- `dirtyPacketTracked`

规则：

- 成功写 data array 时更新。
- 同一行多次受检脏化取最大包序号。
- 后续未跟踪 store 会清除旧归属，防止把旧包错误附着到新数据。
- refill 安装新 tag 时清除 victim way 遗留归属。
- 同一地址多次换入换出按多次缓存行生命周期统计。
- WritebackUnit 接受 victim 请求时锁存序号和 tracked 标志，之后等待和多拍 C 通道不会改变归属。
- 最近修复了 `s3_way` 宽度：使用 `Reg(UInt(nWays.W))`，避免 `OHToUInt` elaboration 报未知宽度。

### L1 到 L2 写回

在 TileLink C 通道首 beat `fire` 统计一次：

- total：所有行级 Release/ProbeAck。
- dirty：`ReleaseData` 或 `ProbeAckData`。

脏写回分类：

- verified：tracked 且 `seq <= newSafePacketWatermark`
- unverified：tracked 且 `seq > newSafePacketWatermark`
- untracked：没有有效校验包归属

当前只做观测，不阻塞写回。

### 写回桶和未校验脏写回延迟

256 个桶按包序号低位索引，每桶保存：

- 完整包序号。
- 写回次数。
- 写回 BOOM cycle 总和。

未校验脏写回发生时写入对应桶。安全水位越过该包时：

```text
safe_cycle_sum += 当前 BOOM cycle × 桶内写回次数
writeback_cycle_sum += 桶内写回 cycle 总和
resolved += 桶内写回次数
```

软件计算：

```text
latency_cycle_sum = safe_cycle_sum - writeback_cycle_sum
average_cycles    = latency_cycle_sum / resolved
average_ns        = latency_cycle_sum × 1e9
                    / (BOOM_frequency × resolved)
```

### 统计有效性

硬件记录：

- seen/resolved/pending/dropped
- allocated/completed/passed/failed/cancelled
- result dropped
- arithmetic overflow
- stats valid
- safe watermark

软件仅在以下条件满足时输出未校验脏写回平均延迟：

```text
stats_valid == 1
seen == resolved
pending == 0
dropped == 0
result_dropped == 0
arithmetic_overflow == 0
failed == 0
cancelled == 0
completed == allocated
passed == completed
safe_cycle_sum >= writeback_cycle_sum
```

### 测量窗口和快照

性能控制扩展为 7 位：

- bit 0：RESET
- bits 4:1：保留旧 perf selector
- bit 5：START
- bit 6：STOP

原问题是 GHE 只有 5 位，导致 START/STOP 被截断，现已修复。

语义：

- RESET 清零并禁用。
- START 开始计数。
- STOP 停止新样本并冻结完整统计向量。
- STOP 只在上升沿捕获一次快照。
- 包协议内部可以继续推进，不因统计停止影响校验正确性。

### L2 到 DRAM

- 每 bank 使用 Gray counter 跨时钟域同步到 BOOM。
- START 保存基线。
- STOP 保存终点差值。
- 输出测量窗口内 total/dirty 数量。
- 当前没有实现 L2→DRAM 未校验脏写回的包序号分类和延迟，只实现窗口计数。文档必须明确，不能夸大为已经实现。

### 软件流程

大核：

1. reset
2. start
3. 执行 workload
4. 等四个 checker 保存统计
5. 轮询 `allocated/completed` 收敛，结果丢失时提前退出诊断
6. stop
7. 读取冻结的 35 项 counter
8. 打印分类、诊断和延迟

小核：

1. reset
2. start
3. 完成全部包校验
4. stop
5. 读取本 hart counter
6. 写入 `hart_traffic[hart]`
7. 设置 ready

使用 `unsigned __int128` 避免频率换算和纳秒乘法在软件中溢出。

## 第二个硬件问题

当前：

```scala
val new_package =
  io.packet_seq_valid && io.packet_seq =/= package_seq_reg
```

任何不同序号，包括迟到的较小序号，都会被当成新包。

数据 packet 和 ARF/CSR packet 使用两条独立 AsyncQueue，跨域后相对到达顺序不保证。该逻辑违反此前确定的“选择最大序号”规则，迟到旧片段可能造成序号回退和误取消。

应改为只接受严格更大的序号：

```scala
val new_package =
  io.packet_seq_valid && io.packet_seq > package_seq_reg
```

较小序号只能作为迟到片段忽略，不能切换当前包。
