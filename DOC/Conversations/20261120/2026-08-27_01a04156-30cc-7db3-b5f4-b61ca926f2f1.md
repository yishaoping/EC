- seq222 在结果前扫描 16 次、产生 67 个 mismatch 脉冲

- `150153`：`new_package=1`，同时 seq20 的迟到 ARF mismatch 到达

- `150157`：seq21 安装时已经带着 `package_error=1`

### 2. ECP valid 气泡被错误解释为流结束

10 个失败包的 ECP 首个 burst 只到 index7：

`2,10,26,45,48,55,64,68,178,222`

根因位于 `R_RSUSL.scala:145-146`：

```scala

has_ECP := Mux(if_RSU_packet === 1.U, false.B,
               Mux(det_fall, true.B, has_ECP))
```

任意 valid 下降沿都被当成整条 ECP 结束。深度 8 的异步队列产生合法反压气泡后，后续 index8..32 被：

```scala

```

条件丢弃。

- `86877`：BOOM x8=14
- `87019`：BOOM `rsu_master.arfs_ss_8=14`
- `88169`：checker 收到 `{index=8, data=14}`
- 但 index7 后已有 valid 气泡，`has_ECP` 于 `87077` 置位
- index8 到达时 ECP RAM 写使能为 0
- `105265`：比较读到旧 ECP x8=0，而 checker x8=14
- 产生 mismatch，`105357` 上报 FAIL

`2,45,55,64,68,178,222`

## `result_dropped=241` 的当前判断

这与 71 个 FAIL 是独立统计 bug。

```scala

```

会把首次已接受后仍保持为高的同一个 result 当成 invalid，并在 `dcache.scala:1137-1138` 增加 `packageResultDropped`。

## 21. 助手 · 2026-08-27T04:28:39.532Z

建议采用“显式 ECP 事务 + 一次性比较 + 稳定快照 + 结果去重”的保守方案。保持 load/store、CSR、LSL、包分配和 safe watermark 语义不变，不通过增大 FIFO、固定延时或屏蔽错误来掩盖问题。

**设计约束**

修复后应始终满足：

1. 每个 sequence 只接收一份完整 ECP，允许 valid 气泡。
2. 每个 sequence 最多启动一次有效 ARF 比较。
3. 比较使用稳定的 checker 架构快照，不读取正在变化的实时 RF。
4. mismatch 必须带 sequence，只能归属于相同的 active package。
5. 一个结果只计数一次，但 GHM 可以继续保持 release level。
6. ECP 缺失、协议异常和超时不能误报 PASS，也不能读取旧 RAM。

**方案一：重构 ECP 接收边界**

在 [R_RSUSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_RSUSL.scala:132)中删除 `det_fall/has_ECP`作为结束条件，改为三态事务：

```text
Idle -> Receiving -> Complete
```

接收规则：

- 新 package 被正式接纳时清空 `ecp_seen`、`expected_index`和 complete。
- 每个 `packet_valid_ECP`都作为独立 beat 接收，valid 下降不改变状态。
- index0 开始事务；index0..32严格顺序写入。
- index32 且已经收到全部 33 项后置 `ecp_complete`。
- sequence、index重复、倒退或跳号产生 transport/protocol fault。
- result 完成或取消后才能清理 ECP RAM 所属状态。

建议复用 GHM ARF CDC 中已有的 sequence，将其传到 RSUSL；不需要更改 CDC payload 格式。

不要采用以下临时方案：

- 把 AsyncQueue 从 8 加大：只能改变气泡出现位置。
- valid 再次上升时清 `has_ECP`：会把一个 ECP 拆成多个事务。
- 用若干空闲周期判断 tail：CDC 延迟变化后仍会失效。

**方案二：一次性、带 sequence 的比较引擎**

将当前电平触发的 `do_check`改为握手式 FSM：

```text
Idle -> Running -> Done
          |
          +-> Abort -> Idle
```

接口建议为：

```scala
start.valid
start.seq
busy
done.valid
done.seq
done.error
abort
```

行为要求：

- `start`仅在 Idle 接受一次，立即锁存 `compare_seq`。
- Running 固定扫描 x1..x31，保持现有 x0 排除、FARF 比较和 ELU 诊断行为。
- mismatch 只写入本地 `compare_error_accum`，不直接驱动 `package_error_now`。
- Done 只发出一次 `{seq,error}`，保持到 RocketCore 确认。
- 比较期间架构边界失效或进入 trap 时，丢弃本轮局部错误并 Abort；不得上报半次扫描结果。
- `new_package`必须等待 `busy=0 && done.valid=0 && ECP receiver idle`。

这样可以消除 `if_check_done`持续为高造成的 596 次重复启动。

**方案三：在稳定架构快照上比较**

只把 FSM 状态改到 postchecking 仍不够，因为中途仍可能进入异常。更稳妥的做法是在比较开始时冻结输入：

- `fsm_postchecking`或`fsm_postchecking_priv`
- trap depth为0
- 本拍无 exception/eret
- `wb_reg_valid=0`、`rf_wen=0`连续两拍
- DIV/FPU无 inflight
- ECP完整、LSL和 ingress 已排空

满足后一次性锁存：

```text
checker_arf_snapshot[0..31]
checker_farf_snapshot[0..31]
```

比较引擎只读取冻结副本。之后即使发生 interrupt 或 handler 改写 x2，也不会污染本包结果。

这里不能等待 `full_check_complete`再启动比较，因为 `full_check_complete`本身依赖 ARF compare done，会形成环形等待。应由 R_ICSL 输出独立的 `arch_compare_ready`。

**方案四：严格限定错误归属**

在 [RocketCore.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/rocket/RocketCore.scala:1295)中将包错误分为两类：

```text
架构校验错误：load/store、CSR、ARF/FARF
传输基础设施错误：ECP格式、超时、overflow
```

处理原则：

- `new_package`时 `package_error := false`，不能再从无标签的 `package_error_now`继承。
- ARF 错误只在 `done.valid && done.seq === package_seq_reg && package_check_active`时锁存。
- 其他异步错误也应携带或绑定当前 sequence。
- 旧 sequence 的迟到 done/error只做诊断并丢弃，不改变新包。
- transport fault建议输出 `CANCELLED`而不是架构 `FAIL`，以区分 BOOM 错误和校验基础设施错误；safe watermark仍不越过该包。

**方案五：只在 DCache 端去重 held-valid**

暂不改 GHM release 协议，降低 CDC 和 ownership 路径风险。在 [dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:929)增加每个 checker 端口的“当前已观察 payload”：

- valid首次出现或 payload变化：作为新结果处理。
- valid持续且 payload完全相同：识别为 held-valid duplicate，不接受、不计 dropped。
- valid拉低后清除 held 状态。
- payload在 valid保持期间异常变化仍按新结果检查，避免吞掉背靠背结果。
- allocation不存在、sequence为0、status非法、低电平后再次发送已完成 sequence，仍计真正的 dropped。

这比修改 [GHM.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/guardiancouncil/GHM.scala:477)的 release 时序风险更小。

**建议实施顺序**

1. ECP事务化和完整性判断。
2. 比较引擎一次性握手及 sequence 标签。
3. 稳定快照和 `arch_compare_ready`。
4. RocketCore错误归属与新包准入。
5. DCache held-valid去重。
6. 最后再考虑是否拆分 GHM result pulse 与 release level。

每一步都应保持现有 timeout/cancellation 作为兜底，并加入以下断言：同一 sequence 只 done 一次、compare不得跨 sequence、ECP complete前不得start、busy时不得接纳新包、结果状态生成后不得变化。

## 关键结论和修复原则

1. 本次首发问题不是 future-seq CDC 乱序，而是协议定义错误：`package_seq` 不是 ECP frame 的唯一 ID；一个 package 可包含多个 privileged ECP frame。
2. 不能简单删除 ECP error 检查，否则会隐藏真正的乱序和跨包 beat。
3. 应将 ECP 追踪改为 frame/epoch 语义：
   - 同 owner `seq` 且在已完成 frame 后重新出现 `index=0`，必须允许开启下一 frame；
   - 比较逻辑必须明确“哪个 ECP frame 是最终可比较的快照”，不能只以 `ecp_complete` 永久 level 判定；
   - 最稳妥的长期方案是在 BOOM→GHM→Rocket 增加 ECP epoch/frame ID 或明确 ECP-final marker。仅使用 seq 无法区分“合法下一 frame”和“传输重复 frame”。
4. `ecp_protocol_error_seq_reg` 仍建议记录 offending `packet_seq_ECP`，而非无条件记录旧 `ecp_owner_seq`。本次两者同为 9，不是直接根因，但跨 seq 场景会产生错误取消风险。
5. cancellation 不可复用会改变 `mstatus.prv/mpp` 的 `check_priv_ret` 路径。需要独立的取消恢复路径，或从被检查上下文可靠恢复原 privilege，而不是固定/隐式返回 U。
6. BOOM 释放和 Rocket cleanup 的解耦虽用于打破旧死锁，但 cancelled result 释放后必须保证 Rocket 本地可恢复。否则 BOOM 可以重分配尚未可复用的 checker。不能通过增大 watchdog 或屏蔽 assertion 掩盖此问题。

## 66. 助手 · 2026-08-27T09:16:04.562Z

建议不要通过屏蔽断言、增大 watchdog 或直接删除 ECP 错误检查来处理。要保证校验继续运行，必须同时修正“ECP frame、取消恢复、结果释放、checker 复用”四个所有权关系。

**1. 修正 ECP 多 frame 协议**

当前 [R_RSUSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_RSUSL.scala:168) 把 `package_seq` 当成了 ECP 唯一标识，但同一个 package 可以产生多个同序号的特权 ECP frame。

建议增加以下状态：

```text
ecp_owner_seq
ecp_frame_epoch
ecp_active
ecp_frame_complete
ecp_final_frame_seen
ecp_expected_index
```

每个 ECP beat 携带：

```text
package_seq + frame_epoch + packet_index
```

状态规则：

```text
idle + index=0                       -> 开始新 frame
active + index=expected_index       -> 接收 beat
旧 frame complete + 新 index=0      -> 开始下一个合法 frame
active + 序号错误/索引跳变          -> protocol error
final frame 未到达                  -> 不启动 ARF compare
```

`frame_epoch` 应从 `R_RSU.scala` 产生，并通过 GHM、RocketTile 传递到 `R_RSUSL`。不能仅通过“同序号再次出现 index=0”判断，因为这样无法区分合法新 frame 和重复传输。

短期若不能扩展接口，至少应允许：

```text
同一 seq、旧 frame 已完成、重新收到 index=0
```

重新打开 ECP 接收状态，并将 compare 延迟到 package 最终完成。但这种方案只能作为过渡方案。

另外，错误序号必须记录实际出错 beat 的 `packet_seq_ECP`，不能无条件记录旧的 `ecp_owner_seq`。

**2. 只比较最终 ECP 快照**

`ecp_frame_complete` 不能直接等价于 package 完成。建议使用：

```text
ecp_compare_ready =
    final_frame_seen &&
    data_ingress_drained &&
    lsl_empty &&
    arch_snapshot_stable &&
    !compare_busy
```

比较开始后：

- 保持 R_ICSL 在 postchecking 状态；
- 锁存一次 Rocket ARF/FARF；
- 比较锁存快照，不比较实时寄存器；
- 比较完成后再生成 PASS/FAIL；
- 不能因为 ECP index 32 到达就提前触发特权返回。

这部分应与 [R_ICSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_ICSL.scala:256) 的 `package_exec_done`、ARF compare 和 CSR compare 统一成一个最终完成条件。

**3. 取消路径必须独立于 `check_priv_ret`**

当前 [CSR.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/rocket/CSR.scala:1407) 的 `check_priv_ret` 会执行类似 `mret` 的逻辑，并把 `mstatus.mpp/prv` 变为 U 态。这是本次取指异常的直接原因。

应拆分为两个信号：

```text
normal_priv_return
cancel_return
```

正常 PASS/FAIL 路径才允许使用 `check_priv_ret`。

取消路径应执行：

```text
收到 cancel
  -> 停止 checker 取指和写回
  -> 清空 LSL/RSUSL 比较状态
  -> 若当前无 trap，直接跳转 pc_special
  -> 若当前有 trap，等待真实 eret/mret/sret
  -> 返回管理流
  -> 产生 cleanup_done
  -> 再发送 CANCELLED result
```

取消返回必须保存并恢复取消前的 privilege、虚拟化状态及必要的 CSR 上下文，不能固定设置为 U 态。

特别要保证：

```text
cancel cleanup 不依赖 result CDC dequeue
result CDC dequeue 也不依赖 checker 再次执行管理代码
```

这样可以避免取消路径再次进入 `fsm_self_xcpt_priv` 后永久等待 `eret`。

**4. 将 BOOM 释放与 Rocket 清理组成两阶段握手**

推荐把结果生命周期拆成两个阶段：

```text
result_generated
cleanup_done
```

Rocket 侧先锁存结果：

```text
result_generated(seq, status)
```

只有满足：

```text
cleanup_done &&
R_ICSL.context_idle &&
RSUSL.ecp_idle &&
RSUSL.compare_idle &&
LSL.empty
```

才允许：

```text
package_result_valid = 1
```

GHM 只有在结果 CDC `deq.fire` 且序号匹配时，才产生：

```text
clear_ic_status_tomain
```

也就是说：

```text
Rocket 生成结果
  -> Rocket 本地清理
  -> 结果进入 GHM CDC
  -> GHM dequeue
  -> BOOM 清除 ic_status
  -> 允许该 checker 重新分配
```

不能在 `package_result_fire` 或结果刚入 Rocket 本地队列时就释放 BOOM。否则 BOOM 会像本次一样，在 Rocket 仍未恢复时重新分配 `seq=11`。

[R_IC.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_IC.scala:172) 的 owner 清除也应绑定 `release_seq`，不能只依据无序的单 bit clear。

**5. 新 package 必须在 CDC 入口处背压**

当旧 package 或其结果仍被本地持有时：

```text
新 seq 不得进入 Rocket 的 RSUSL/LSL
新 seq 只能停留在 GHM CDC FIFO
```

必须保留：

- 数据 anchor 优先；
- ARF/CPS/ECP 等待匹配的数据 anchor；
- 旧 package 未清理时禁止新 package 覆盖本地状态；
- pending sequence 使用 FIFO 或至少能容纳多个新序号；
- 序号比较使用可回绕的 modular compare。

不能让 candidate package 先进入本地资源，再用 `checker_cleanup_done` 阻止它自己被接纳，否则会形成新的自锁。

**必须保留的保护条件**

```text
result_release -> cleanup_done && release_seq == owner_seq
ecp_accept -> packet_seq == owner_seq
compare_start -> final_frame_seen
new_package -> no old package/result pending
cancelled -> bounded cleanup before release
```

建议的落地顺序是：

1. 先实现独立取消恢复和两阶段释放，确保不会再卡死；
2. 再加入 ECP frame/epoch 语义；
3. 再将 ARF compare 限制到最终 frame；
4. 最后收紧 CDC admission 和序号断言。

该方案不改变软件 RoCC ABI，也不需要通过屏蔽 `assert__assert_22` 来掩盖问题。当前 VCD/生成 RTL 与工作区 Scala 不是完全同一版本，后续验证时必须使用一致的源码和生成物；本次不执行代码修改、仿真或硬件生成。

### 2. 将结果 handoff 延迟到本地清理完成

```scala

  checker_cleanup_done &&
  !package_start_pending &&
  !package_check_active
```

```scala

  io.package_result_ready && package_result_handoff_allowed

  package_result_queue.io.deq.valid && package_result_handoff_allowed
```

必须保证结果仍保持在本地 queue 中，直到 cleanup 完成。

```text

  -> Rocket 本地 cleanup_done
  -> result CDC enq.fire

  -> clear_ic_status_tomain

  -> checker 可重新分配
```

### 3. 修复 ECP 多 frame

最低风险实现：

- 在 `R_RSUSL` 内增加 `ecp_frame_epoch`；
- 每次合法同序号 `index=0` 作为新 frame 起点；
- 新 frame 起点：
  - `ecp_active := true`
  - `ecp_complete_reg := false`
  - `ecp_expected_index := 1`
  - `ecp_frame_epoch := ecp_frame_epoch + 1`
- frame tail `index=32`：

  - `ecp_complete_reg := true`

```text

```

但仍拒绝：

```text

different seq + current owner
index jump
tail extension
```

核心原则是把“包结果事件”“BOOM checker 资源释放电平”“统计快照”拆成三个独立协议。当前问题正是结果事件和资源释放电平混用了同一个 `valid`。

**方案一：GHM 结果只发送一次**

修改目标位于 [GHM.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/guardiancouncil/GHM.scala:464)。

当前行为：

```text

release_pending 周期：checker_results_out.valid = 1
```

建议改为：

```scala
result_event_valid := result_deq_fire

checker_results_out(i) := Mux(
  result_deq_fire,
  Cat(true.B, u_result_cdc(i).io.deq.bits),
  0.U
)

checker_result_release(i) :=
  result_release_pending(i) || result_deq_fire
```

其中：

- `checker_results_out.valid` 只代表“一次新的包结果事件”。
- `checker_result_release` 继续保持，直到 BOOM 的 `ic_status` 清零。
- `result_release_seq/status` 继续锁存，便于诊断和保持释放请求。
- `u_result_cdc.deq.ready := !result_release_pending` 保持不变，防止前一个 checker slot 尚未释放时取出下一个结果。

新的完整链路为：

```text
result CDC deq.fire
  ├─ 单周期 checker_results_out.valid -> DCache统计一次结果
  └─ 置位 result_release_pending
       -> checker_result_release保持
       -> R_IC清除ic_status
       -> GHM观察到ic_status=0
       -> 清除result_release_pending
```

这是首选修复，因为不改变 CDC、序列号、结果队列和 BOOM 所有权语义，只纠正输出信号的事件/电平混用。

**方案二：DCache增加重复保持防护**

修改范围位于 [dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:929) 和 [dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:1092)。

每个 checker 输入增加一个“当前 valid 电平已经消费”的内部状态：

```text
resultLevelConsumed[i]
resultLevelPayload[i]
```

建议规则：

```text
首次合法 valid：
  resultAccepted=1
  锁存完整 payload
  resultLevelConsumed=1

valid 持续为1且 payload完全相同：
  benignHeldDuplicate=1
  不再次完成包
  不增加result_dropped
  不清除stats_valid

valid持续为1但seq/status发生变化：
  仍视为非法结果

valid回到0：
  resultLevelConsumed=0
```

非法结果条件改为概念上的：

```text
valid
&& !resultAccepted
&& !resultStale
&& !benignHeldDuplicate
```

必须避免以下过宽处理：

```scala

```

不能直接把所有旧序列都当成 benign duplicate，否则可能掩盖错误 checker、错误状态、结果重放和序列回绕问题。防护必须限定为：

- 同一个 checker 通道；
- `valid` 中间没有拉低；
- 完整 `{status, seq}` 与首次接受结果一致。

**方案三：STOP快照原子化**

当前 [dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:1437) 在 STOP 边沿直接执行：

```scala

```

如果同一边沿还发生 `resolvedThisCycle`，快照可能读取寄存器更新前的值。

低侵入方案是延迟一个 BOOM 周期冻结：

```text
STOP边沿：
  允许该边沿已经发生的事件完成统计
  trafficEnabled清零
  stopCapturePending置位

下一个BOOM周期：
  此时统计寄存器已经包含STOP边沿贡献
  trafficCounterSnapshot := trafficCounterLive
  trafficCounterSnapshotValid := 1
  stopCapturePending := 0
```

同时将统计窗口边界明确为“STOP 边沿包含”：

```scala
trafficCounting :=
  (trafficEnabled || io.traffic_start) &&
  !io.traffic_reset
```

即 `traffic_stop` 在该边沿更新 `trafficEnabled`，从下一周期开始停止统计。这样同一边沿已经完成握手的 C-channel 写回或结果结算不会被静默排除。

**方案四：改进软件排空与错误诊断**

当前 [report.c](/data1/gzh/EC/Software/Test/stat/report.c:57) 一看到 `result_dropped != 0` 就立即结束排空。若将来真的在运行末尾出现错误，这可能让 STOP 在 `pending` 尚未归零时过早发生。

```text

继续等待 completed==allocated && pending==0
达到排空条件后返回 HARD_ERROR
若一直不能排空则在既有超时后返回 TIMEOUT
```

这样即使统计已经无效，仍能获得完整诊断快照，不会因为错误标志本身提前截断周期和。

平均值有效性检查必须保留。不要简单删除：

```c

stats_valid != 1
```

目前延迟统计失败并不是时钟周期漏加，而是包结果被重复上报后误判为“结果丢失”。

根本原因是：**GHM 和 DCache 对 `checker_results.valid` 的语义理解不一致**。

```text
GHM认为 valid 可以保持：
  第1周期：新结果到达，valid=1
  第2周期：等待 BOOM ic_status 清零，继续保持 valid=1

DCache认为 valid 每个高电平周期都是一个新结果：
  第1周期：正常接受结果
  第2周期：对应包已经完成，判定为非法结果
```

所以每个包都发生：

```text
正常接收一次 + 错误地报告一次 result_dropped
```

本次共有245个通过的包，正好得到：

```text
allocated=245
completed=245
passed=245
result_dropped=245
stats_valid=0
```

软件看到 `result_dropped != 0` 或 `stats_valid != 1`，便拒绝输出平均延迟。

波形同时证明周期统计本身是完整的：

```text
unverified_seen=293
resolved=293
pending=0
writeback_dropped=0
arithmetic_overflow=0
```

从波形逐事件重建得到的两个周期和也与日志完全一致：

```text
safe_cycle_sum=30251901
writeback_cycle_sum=28198088
```

如果暂时忽略这个误报，实际统计值为：

```text
总延迟 = 30251901 - 28198088
       = 2053813 BOOM cycles

平均延迟 = 2053813 / 293
         = 7009.601 cycles
         ≈ 35.048 us @ 200 MHz
```

因此真正的根本问题不是计数器，而是：**一次性“结果事件”和需要保持的“资源释放请求”共用了同一个有效信号。**

**方案一：最小根因修复**

只修改 GHM 的结果输出语义：

```text
result_deq_fire
  -> checker_results_out.valid 只拉高一个周期
  -> DCache只收到一次结果

result_release_pending
  -> checker_result_release继续保持
  -> 直到BOOM ic_status清零
```

具体原则：

- `checker_results_out.valid` 只由 `result_deq_fire` 产生。
- `result_release_pending` 不再驱动 `checker_results_out.valid`。
- `checker_result_release` 仍然由 `result_deq_fire || result_release_pending` 驱动。
- 结果的 `seq/status` 继续锁存，不改变CDC和资源释放顺序。

优点：

- 改动最小。
- 直接修复当前245次误报。
- 不改变Rocket结果队列、CDC、包序列号和BOOM资源释放机制。
- 原有包校验功能基本不受影响。

不足：

- 如果以后其他模块再次输出保持型结果，DCache仍可能重复计数。

**方案二：生产端和消费端双重保护，推荐**

在方案一基础上，DCache增加防御性重复识别。

DCache记录每个checker通道当前已经消费的结果：

```text
首次出现 valid + 合法 seq/status：
  正常接受

valid连续保持且seq/status完全相同：
  benign duplicate
  不重复完成包
  不增加result_dropped
  不清除stats_valid

valid连续保持但seq/status变化：
  真正的协议错误
  增加result_dropped
  清除stats_valid

valid回到0：
  清除该通道的保持状态
```

重复判定必须严格限定为：

- 同一个checker通道；
- `valid`没有在中间拉低；
- 完整 `{status, seq}` 与已接受结果相同。

不能简单地把所有已完成序列都忽略，否则可能掩盖真正的旧结果重放、错误序列和错误状态。

这个方案同时修复：

- 当前GHM保持型结果误报；
- 未来类似接口误用；
- 结果在释放等待阶段保持多个周期的问题。

这是风险和完整性最均衡的方案。

**方案三：全面闭环修复**

在方案二基础上，再处理统计窗口边界和软件排空。

1. 修复STOP快照边界

当前STOP边沿可能与最后一次统计更新同周期。虽然本次没有触发，但理论上快照可能读到更新前的寄存器值。

建议：

```text
STOP到达
  -> 停止接收新的统计事件
  -> 等一个BOOM周期
  -> 冻结更新后的trafficCounterLive
```

或者统一计算所有计数器的next-state，并在STOP时快照next-state。

本次波形中最后一次结算远早于STOP，所以这不是当前失败原因，但修复后可以防止真正的末周期漏统计。

2. 改进软件排空

当前软件发现 `result_dropped` 后立即停止等待。建议改为：

```text
发现错误：
  记录hard_error
  继续等待allocated==completed且pending==0
  排空后再STOP并输出完整诊断
```

这样即使发生真正的协议错误，也不会因为过早STOP造成统计窗口不完整。

3. 保留严格有效性检查

不要删除：

```c
stats_valid != 1
result_dropped != 0
```

否则未来真正丢结果时，软件仍会输出一个看似正常但不可信的平均值。

**建议选择**

推荐采用方案二，并同时加入方案三中的STOP快照修复：

```text
GHM：结果事件单周期化
DCache：严格识别连续保持的相同结果
DCache：STOP使用更新后状态进行快照
软件：错误后继续排空，但仍拒绝无效平均值
```

修复后的目标状态应为：

```text

result_dropped=0
stats_valid=1

unverified_seen=293
resolved=293
pending=0
writeback_dropped=0
arithmetic_overflow=0
```

这样既解决当前延迟统计失败，也覆盖重复结果、STOP边界和异常排空三个潜在问题。当前仅给出方案，没有修改代码。
