```text
    +

```

- snapshot 后没有新的 committed 指令，形成合法的 zero-data segment；
- 或序列边界比 GH_BUF 中的数据流提前切换；
- 更严重时，GH_BUF 中延迟输出的数据还可能被新的 segment watermark 错误标记。

最终状态为：

```text

data CDC valid     = 0
ARF CDC valid      = 1
ARF CDC ready      = 0
ARF CDC enq_ready  = 0
```

GHM 的释放条件是：

```scala
arfAfterData =
  dataConsumedSeq =/= 0.U &&
  arfHeadSeq <= dataConsumedSeq
```

当前：

```text

```

所以 `arfAfterData=false`，而 data CDC 又没有 `deq.fire`，导致 ARF CDC 永远不能 dequeue。ARF FIFO 深度为 8，填满后：

```text

  -> arfs_cdc_busy
  -> bigcore_hang
  -> core.io.big_hang
  -> R_RSU merge_counter 停止
  -> BOOM pipeline stall
  -> 无新 commit
  -> 更不可能产生 sequence 7 data
```

这是一个自锁环路，而不是单纯的 CDC 延迟。

```text
normal_result_event =
    package_check_active &&

    package_exec_done
```

```text
result_handoff_done =
    package_result_handoff_fire

checker_cleanup_done =
    R_ICSL 已回到 nonchecking/reset
```

```text
package_abort
```

其行为是：

```text

 -> 清理本地 checker 状态
 -> 结果仍通过 result CDC 交付 GHM
 -> GHM 产生 clear_ic_status_tomain
```

1. 增加明确的包状态机

```text

  -> CHECKING(seq)
  -> RESULT_WAIT
  -> RELEASE_WAIT
  -> IDLE
```

## 171. 助手 · 2026-08-27T01:09:57.084Z

最稳健的方案不是分别补一个 `excpt_mode` 条件和一个 FIFO 判断，而是把“checker 执行上下文”和“包传输事务”明确建模成两个有握手、有恢复路径的协议。

**问题一：异常态跨包泄漏**

建议拆分两个状态机：

```text
Context FSM:
MANAGER_READY -> REPLAY -> TRAP -> REPLAY/POSTCHECK -> RETURN -> MANAGER_READY

Package FSM:
EMPTY -> START_WAIT -> INGEST/RUN -> POSTCHECK -> RESULT_PENDING -> CLEANUP -> EMPTY
```

核心规则：

1. 所有活跃状态都必须处理异常，不能只有 `fsm_checking` 响应 `self_xcpt`。
2. 状态转移优先级固定为：

```text
reset/cancel > exception > eret > completion > normal transition
```

3. 在 `checking` 或 `postchecking` 收到异常时：
   - 锁存 `resume_state`。
   - 进入统一的 `TRAP` 状态。
   - 禁止 `if_ret_special_pc`。
   - 等待真实 `mret/sret` 完成。
   - 返回锁存的 `resume_state`，再决定是否进入 `pc_special` 返回流程。
4. `pc_special` 返回改成 held request/ack：
   - `return_req` 一直保持到 `returned_to_special_address_valid`。
   - 只有 `trap_depth==0 && !excpt_mode` 才允许发出。
5. 不能通过强制清零 `excpt_mode` 修复。那会隐藏尚未完成的 CSR/trap 上下文，造成更隐蔽的寄存器和特权级错误。

新的 checker 可用条件建议定义为：

```scala
checker_context_ready =
  icsl.cleanup_done &&
  !excpt_mode &&
  trap_depth === 0.U &&
  !return_pending &&
  pipeline_quiescent

package_ready_for_new =
  checker_context_ready &&
  rsu_idle &&
  lsl_empty &&
  no_result_pending &&
  !package_owned
```

当 context 未恢复时，GHM 中的数据 anchor 保持不出队，不能先写入 LSL/RSUSL。即使旧包结果已经释放 BOOM slot，本地 checker 仍保持 unavailable，直到真实 `mret` 和 cleanup 都完成。

**问题二：LSL 漏反压和静默丢包**

不能简单把当前 OR 改成全局 AND。全局 AND 会让与当前 packet 无关的消费者阻塞数据。应在 RocketTile 根据当前 beat 类型计算 type-aware ready：

```scala
memNeeded  = any lane is load/store
csrNeeded  = any lane is CSR
roccNeeded = any lane is RoCC
bjNeeded   = any lane is branch/jump

beatReady =
  (!memNeeded  || lslMemCanAccept(memCount)) &&
  (!csrNeeded  || lslCsrCanAccept(csrCount)) &&
  (!roccNeeded || lslRoccCanAccept(roccCount)) &&
  (!bjNeeded   || frontendCanAccept(bjCount))
```

一个 CDC beat 的两个 lane 必须原子接受：

```text
全部目标都 ready -> 整个 beat fire
任意目标不 ready -> 整个 beat 保持
```

不能出现 memory lane 已写入、branch lane 未写入，或者反过来。

R_LSL 建议彻底移除当前“双 bank + round-robin 指针”结构，改成：

- memory、CSR、RoCC 各自一个保序队列。
- 输入端使用 2-lane multi-enqueue queue，或 2-entry skid buffer 加标准单入口 `Queue`。
- `canAccept = freeEntries >= PopCount(validLanes)`。
- write pointer 和 occupancy 只在 `beat.fire` 后更新。
- 每个队列提供真实 `enq.ready`，禁止 `valid && full` 时静默忽略。

这能同时消除：

- channel0 空、channel1 非空造成的 head-of-line 死锁。
- FIFO full 静默丢写。
- lane 压缩和 enqueue pointer 不一致。
- unrelated consumer ready 绕过 LSL backpressure。

GHM 的 `data_cdc_ready` 也应使用独立连接，不再复用 `ghe_event` 位域或组合多个消费者的 ready。

**协议级加固**

为了避免下一次又在 completion、ARF 或 RoCC 上出现类似问题，建议增加包级 manifest：

```text
BEGIN(seq)
DATA(seq, type, payload) ...
END(seq, mem_count, csr_count, rocc_count, arf_count)
```

本地队列条目保留 `seq`，完成条件改为：

```text
END 已收到
&& 各类型 accepted_count == expected_count
&& 各类型 consumed_count == expected_count
&& ARF/CSR compare 完成
&& instruction boundary 完成
```

这样“数据没到”和“数据数量为零”可以明确区分，也不再依赖 `cdc_empty && lsl_empty` 猜测包尾。取消时可以按 sequence 精确 flush，不会污染下一包。

**统一进度监督**

所有非空状态都必须有 watchdog，不能以 `lsl.empty` 为启动条件：

- `START_WAIT_TIMEOUT`：有 sequence 但长期没有 COPY。
- `INGRESS_STALL_TIMEOUT`：END 未到且长期没有 CDC fire。
- `EXEC_NO_PROGRESS_TIMEOUT`：无 commit、LSL dequeue、trap/eret 或状态变化。
- `TRAP_TIMEOUT`：异常长期没有匹配 `eret`。
- `RETURN_TIMEOUT`：`return_req` 长期没有 ack。
- `RESULT_TIMEOUT`：结果长期无法交付 GHM。

超时后生成带 sequence 的 `CANCELLED(reason)`，先释放 BOOM ownership；本地 checker 在上下文恢复和队列 flush 完成前继续保持 unavailable。这样不会拿“释放资源”和“允许新包进入”互相阻塞。

**建议实施顺序**

1. 修复 R_ICSL 全状态异常处理、返回握手和 context-ready 准入。
2. 将 packet ready 改为按类型、按 lane 原子计算。
3. 替换 R_LSL banked FIFO，建立真正的 ready/valid enqueue。
4. 增加 phase/no-progress watchdog 和取消原因。
5. 最后加入 sequence tag、BEGIN/END manifest 和计数一致性断言。

不建议只添加 `!excpt_mode` admission gate，因为当前 postchecking 已可能让 `excpt_mode` 永远无法清除；也不建议只把 ready OR 改成 AND，因为会引入新的跨类型阻塞。上述方案保持现有软件 ABI、BOOM slot 分配和 sequenced result release 路径不变，主要重构 checker 内部的事务边界与流控。

2. 所有 active/postchecking 状态都处理异常。
3. 状态优先级：`reset/cancel > exception > eret > completion > normal`。
