Make 只比较文件时间戳，不判断硬件内容是否真的变化。因此只要生成文件比模拟器新，或者 `VTestHarness.mk` 缺失、不完整，Make 就会重新运行 Verilator。这通常属于构建缓存/生成物状态问题，不代表你修改了硬件源码。


### 1. GHM 发送 6-bit 状态，而不是纯状态码

### 状态语义混杂

同一个 6-bit word 混合：

```text

bits 4:0: GHT run/end status
```

- 上一轮的 done 可泄漏到下一轮；
- 单纯清零又可能让跨 CDC 的旧完成消息被新会话错误接收；
- 多 benchmark 或 repeated run 时会有 stale completion。

- `checker.c:34-39`、`checker.c:52-53`
- `report.c:250-252`

```scala
when (checkerDone) {
  ghe_status_reg := 0x02.U
}
```

理由：

- 保留 GHM 当前 bit 5 的原语义；
- 最终 `0x22` 会被识别为“filters empty + test finished”；
- 软件 API 不变，`ghe_checkght_status()` 仍返回 `0x02`；
- GHM 已将 `received_ctrl` 做成 checker 域寄存器保持，不依赖 CPU 正好采样一个 pulse。

注意：不要只修改软件为 `(status & 0x1f) == 2`，当前软件读到的是 GHE 的 `ghe_status_reg`，它尚未被硬件锁存，所以仍是 0，软件掩码无效。

### B. 推荐根治：定义显式、有版本的会话协议

替换目前“状态位拼接 + 隐含解释”的协议。最小消息集合：

```text
BOOM/GHM -> checker:
  SESSION_START(epoch)
  SESSION_FINISH(epoch)

checker -> BOOM/GHM:
  CHECKER_DONE(epoch)
  CHECKER_RESULT(epoch, packet_seq, PASS | FAIL | CANCELLED)
```

每个 checker 的完成谓词：

```text
checker_done =
    session_active
 && finish_seen
 && packet_ingress_drained
 && lsl_empty
 && !package_check_active
 && !result_pending
```

含义：

- 没有被分配 package 的 checker，在收到 `SESSION_FINISH(epoch)` 后也能立即回 `CHECKER_DONE(epoch)`。
- 有 package 的 checker 必须等待 packet、ARF/CSR postcheck、result CDC 都完成。
- `CHECKER_DONE` 必须作为 level/acknowledged transaction 保持，直到对端确认，而不能是单周期 pulse。
- 新 session 必须递增 epoch，任何不匹配 epoch 的状态、done、result 均丢弃或诊断。
- 禁止从裸 `status == 2` 推导跨域会话完成。

### C. 包所有权 / 结果链保持现有正确方向

按 `Debug/guardian_protocol_audit.md:100-115`：

```text
full_check_complete
-> result(epoch, seq, PASS/FAIL/CANCELLED) 入 result CDC
-> BOOM 域 dequeue result
-> 同一 BOOM 时钟边：更新 completion bitmap + clear ic_status
```

不要让 `ghe_release()` 直接释放 BOOM 的 `ic_status`。`ghe_release()` 可以保留为 checker 软件生命周期事件，但不得作为包 ownership 的唯一依据。

### D. 软件修改：用于诊断和防止假统计

修改方案不应通过跳过 ready 等待来“修好”问题，否则统计不可信。

1. `checker.c` 的两个等待加 cycle deadline。
2. 超时时打印：
   - hart id
   - raw GHE/GHM status
   - session epoch
   - 本地 ingress empty
   - package active / result pending
3. `report.c` 按 enable mask 等待 checker done，而非硬编码 `[1..4]`。
4. `report_end()` 超时时输出 ready mask、allocated/completed/pending，返回明确失败状态，不再静默空转。
5. 成功前检查所有 enabled checker 的 `CHECKER_DONE(epoch)` 均收到。

**三、协议设计中的主要缺陷**

1. **完成状态是脉冲，不是事务**

`deq.fire` 只持续一个 checker 时钟周期，GHE 软件不保证正好在该周期内执行 RoCC 读取。

正确协议必须满足：

```text

```

当前代码没有做到这一点。

2. **AsyncQueue 的 valid 没有保持**

当前：

```scala

  filterEmptyRise || routed_status =/= 0.U || counter_msb
```

其中 `filterEmptyRise` 是一个周期脉冲。如果 FIFO 当周期没有 `ready`，该事件可能直接丢失。跨 CDC 的消息不能依赖裸脉冲。

3. **完成状态、filter empty、packet drain 混在一起**

当前 GHE 看到 `1` 时，无法区分：

- 仍有 packet 没有排空；
- checker 没有 owner；
- 完成消息丢失；
- GHM 控制队列没有发送；
- checker 本身异常。

`1` 只是一个哨兵值，不是明确的协议状态。

4. **没有 session/epoch**

`ghe_status_reg` 只在 reset 时清零，遇到 `2` 后一直保持：

```scala

}
```

新 benchmark 开始时没有明确清除机制，存在旧 benchmark 的完成状态泄漏问题。

[report.c:250](/data1/gzh/EC/Software/Test/stat/report.c:250) 固定等待：

```c

```

但硬件支持 checker enable mask 和 owner 路由。被禁用或没有分配任务的 checker 可能根本不会写 ready，软件仍然会永久等待。

6. **`ghe_release()` 与真正的包释放语义混淆**

当前硬件已经有 sequenced result CDC：

```text

  -> GHM result CDC
  -> BOOM dequeue
  -> clear_ic_status
```

这是正确的 BOOM 包所有权释放路径。



这个问题应在旧版本中通过字段解码解决，但它不是当前 v1Config 波形中 hart2～4 卡死的主要原因。当前运行的直接原因仍然是完成脉冲丢失。

## 3. Rocket checker 侧修改

### 3.1 增加明确的本地状态机

在 `RocketCore.scala` 中，将当前 `package_check_active` 和 `package_result_waiting` 统一为以下状态：

```text
IDLE
  -> ACTIVE
  -> DRAINING
  -> RESULT_PENDING
  -> RELEASE_WAIT
  -> IDLE
```

状态含义：

- `IDLE`：没有 ownership。
- `ACTIVE`：正常接收 data、ARF、CSR。
- `DRAINING`：已经收到 FINISH，等待所有输入和内部队列排空。
- `RESULT_PENDING`：结果已生成，但还没有被 Tile/GHM 接收。
- `RELEASE_WAIT`：结果已经被 GHM 接收，等待 BOOM 的 release acknowledgement。

### 3.2 结果必须锁存并保持 valid

结果生成后锁存：

```scala
result_pending       := true.B
result_pending_seq   := package_seq_reg
result_pending_epoch := session_epoch
result_pending_status:= result_status
```

输出必须符合标准 Ready/Valid 规则：

```scala
io.package_result_valid := result_pending

when (io.package_result_valid && io.package_result_ready) {
  result_pending := false.B
  release_waiting := true.B
}
```

在 `ready` 为 0 时：

```text
valid保持为1
payload保持不变
seq/status不能变化
```

禁止使用只持续一个周期的：

```scala
package_result_event
```

作为跨时钟域传输的唯一依据。

### 3.3 本地状态不能提前清除

当前取消逻辑中，`package_cancelled` 会驱动：

```scala
icsl.io.if_check_cancelled := package_cancelled
```

建议改为：

```text
检测到取消条件
    -> 停止接收新包
    -> 进入DRAINING
    -> 生成CANCELLED结果
    -> 等待result握手
    -> 等待release_ack
    -> 最后才清除package上下文
```

也就是说，不能在 `package_cancelled` 同一周期清掉：

```text
package_seq_reg
package_check_active
ARF上下文
LSL上下文
checker ownership本地状态
```

必须保留到 `release_ack(seq, epoch)` 到达。

### 3.4 取消结果也必须经过正式协议

ARF 超时、sequence mismatch、checker reset 都必须形成正式结果：

```text
CANCELLED(seq, epoch, reason)
```

不能只清除 `package_check_active`，也不能只给 `R_ICSL` 一个取消脉冲。

## 4. GHM 侧修改

### 4.1 result CDC 改为“接收后锁存”

当前：

```scala
u_result_cdc(i).io.deq.ready := true.B
checker_result_release(i) := u_result_cdc(i).io.deq.fire
```

建议改成：

```text
result AsyncQueue
    -> GHM result_pending[i] 锁存
    -> result_pending_valid[i] 保持
    -> 生成release_req[i]
```

伪代码：

```scala
u_result_cdc(i).io.deq.ready :=
  !result_pending_valid(i)

when (u_result_cdc(i).io.deq.fire) {
  result_pending_valid(i) := true.B
  result_pending_seq(i)   := ...
  result_pending_epoch(i) := ...
  result_pending_status(i):= ...
}
```

只有 `result_pending_valid` 被锁存后，GHM 才认为 result 已经可靠接收。

### 4.2 增加 BOOM release request/ack CDC

原有：

```text
GHM -> BOOM: clear_ic_status_tomain
```

改为两个独立 CDC 通道：

```text
GHM -> BOOM:
  release_req_valid
  release_req_checker
  release_req_seq
  release_req_epoch

BOOM -> GHM:
  release_ack_valid
  release_ack_checker
  release_ack_seq
  release_ack_epoch
```

两个方向都使用 `AsyncQueue` 或等价的稳定握手同步器。

`release_req` 必须保持到 ack：

```scala
release_req_valid(i) :=
  result_pending_valid(i) &&
  !release_ack_seen(i)
```

不能再使用单周期脉冲作为唯一释放机制。

### 4.3 BOOM 清除 ownership 必须带序号检查

BOOM 侧收到 release request 后，必须检查：

```text
request.checker_id == 当前checker
request.owner_id   == 当前BOOM
request.seq        == 当前ownership.seq
request.epoch      == 当前ownership.epoch
```

只有全部匹配才执行：

```text
ic_status(checker) := 0
checker_big_owner(checker) := 0
```

然后产生：

```text
release_ack(checker, seq, epoch)
```

如果请求重复到达：

```text
若当前ownership已经清除，但seq/epoch匹配：
    再次返回相同ack
```

这样协议具备幂等性，允许 CDC 重传，不会因为重复消息死锁。

如果序号不匹配：

```text
拒绝清除
记录协议错误
返回NACK或错误ack
```

禁止“收到任意 clear 就清 bit”。

### 4.4 GHM 收到 ack 后才释放 result

```scala
when (release_ack_fire &&
      ack_seq === result_pending_seq &&
      ack_epoch === result_pending_epoch) {
  result_pending_valid(i) := false.B
  release_ack_seen(i)     := true.B
}
```

然后再向 Rocket checker 发送：

```text
result_release_ack(seq, epoch)
```

Rocket checker 收到该 ack 后，才进入 `IDLE`。

## 5. R_ICSL 修改

[R_ICSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_ICSL.scala:120) 当前 `clear_ic_status` 是本地状态机输出，建议拆成两个信号：

```text
clear_ic_status_request
clear_ic_status_ack
```

`R_ICSL` 不应因为进入 `fsm_reset` 就默认认为外部 ownership 已清除。

建议状态扩展为：

```text
fsm_reset
fsm_nonchecking
fsm_checking
fsm_postchecking
fsm_result_wait
fsm_release_wait
```

关键规则：

```text
fsm_postchecking:
  允许返回 special PC

fsm_result_wait:
  等待 result 被 RocketTile/GHM 接收

fsm_release_wait:
  等待 release_ack

收到 release_ack:
  才允许回到 fsm_reset
```

`clear_ic_status` 可以继续保留一周期输出，用于兼容旧连接，但它只能作为内部提示，不能作为跨域事务完成条件。

## 6. START/FINISH 协议修改

当前 session 协议已经有 START/FINISH 和 epoch，但 FINISH 仍依赖多个 empty 条件。建议将 FINISH 改成显式的生产者提交标记：

```text
START(epoch, seq)
DATA(seq, payload)*
ARF(seq, payload)*
CSR(seq, payload)*
FINISH(epoch, seq)
```

完成条件必须是：

```text
收到匹配的 FINISH
&& data AsyncQueue为空
&& ARF AsyncQueue为空
&& CSR AsyncQueue为空
&& LSL为空
&& packet ingress已经关闭
&& 没有同seq在途数据
```

禁止把单次 `filter_empty` 或一次同步后的 empty 电平当成最终完成条件。

此外：

```text
收到FINISH后，禁止接受更老seq的数据
收到新START前，禁止接受新seq数据
```

如果 FINISH 超时：

```text
进入CANCEL_DRAIN
继续排空所有属于当前seq的数据
生成CANCELLED
进入RESULT_PENDING
```

不能直接回到 `IDLE`。

## 7. watchdog 修改

当前 watchdog 位于：

[core.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/exu/core.scala:2040)

不建议简单把 `little_status1(20)` 改成更大的位数。建议分成三级：

### 第一级：协议等待超时

例如等待 ARF、data、FINISH 超时：

```text
记录 timeout reason
生成 CANCELLED
进入 release 流程
```

### 第二级：release 请求超时

```text
release_req保持有效
定期重发
记录 release_retry_count
```

### 第三级：BOOM ownership watchdog

只有在以下条件同时满足时才触发强制恢复：

```text
ownership持续存在超过阈值
&& 已经发出ABORT请求
&& checker没有新的有效事务
&& release协议超时
```

恢复动作应为：

```text
冻结对应checker
清空对应CDC队列
清除BOOM ownership
增加forced_abort计数
使session_epoch递增
```

强制清除必须同时带 `seq/epoch`，不能使用无条件 bit clear。

同时将原断言拆成：

```text
assert(!pipeline_hang)
assert(!release_protocol_timeout)
assert(!ownership_without_transaction)
```

这样下次可以直接判断是流水线挂死还是 CDC 释放失败。

## 9. 与旧 workload 的兼容方式

为了兼容当前软件和已有 workload：

1. 保留原 `package_result_valid/status/seq` 接口。
2. 新增 `epoch/reason/version` 字段，旧结果默认解释为：
   ```text
   version=0
   epoch=0
   reason=NORMAL_COMPLETE
   ```
3. 旧 workload 不需要修改启动方式。
4. 旧单周期 `clear_ic_status` 保留为兼容输出，但只在内部完成新协议 ack 后产生。
5. 新硬件对旧格式结果采用隐式 `seq` 匹配。
6. 新协议检测到旧格式时，禁止同时存在多个同 checker 未确认事务。

这样软件仍然可以继续运行原来的 benchmark，但硬件内部已经从“脉冲协议”升级为“可重传、可确认、可幂等”的协议。

## 10. 推荐实施顺序

建议按以下顺序修改，避免一次改动过大：

1. 在 `GH_GlobalParams.scala` 增加协议版本、epoch、result reason 定义。
2. 在 `RocketCore.scala` 增加 `RESULT_PENDING/RELEASE_WAIT`，结果锁存保持。
3. 在 `RocketTile.scala` 增加 result ack 的接收和转发。
4. 在 `GHM.scala` 将 result CDC dequeue 改为锁存式接收。
5. 增加 GHM 到 BOOM 的 `release_req` 和 BOOM 到 GHM 的 `release_ack` 两条 CDC。
6. 在 BOOM 中按 `checker_id + seq + epoch` 清 ownership。
7. 将原 `clear_ic_status_tomain` 改为新协议的兼容派生信号。
8. 最后再加入 watchdog 分级恢复和协议断言。

最重要的设计原则是：

```text
本地完成 != 全局完成
result被发送 != result被接收
result被接收 != BOOM ownership已清除
ownership清除 != checker可以立即复用

只有 release_ack(seq, epoch) 到达后，
本次 checker 事务才真正结束。
```

这能直接消除本次 `ic_status(1)` 长期保持为 1 的根因，同时避免为了规避问题而无限延长冻结时间。
