## 最重要的设计难点

用户说“参考 L1→L2 的分类和延迟统计”，但 L2→DRAM 需要判断该 L2 victim 对应的 packet 是否已验证，因此必须有 packet provenance：

1. L1→L2 ReleaseData 发生时，包序号必须传给 L2；
2. packet sequence 需要在 L2 line metadata 中保留；
3. L2 victim 发生时，读取该 line 的 packet sequence；
4. L2 侧需要看到当前安全水位，或者在 BOOM 侧依据 L2 输出的 packet sequence 再分类；
5. 延迟统计需要：
   - 写回时刻；
   - 后续包完成/安全水位推进时刻；
   - L2 与 BOOM 跨时钟域，时间基准必须明确。

不能简单把 L1→L2 的字段直接复制到 L2，因为 TileLink 标准 Bundle 没有自定义 packet seq 字段。可选路径：

### 方案 A：BoringUtils sideband（推荐最小侵入）

- 在 BOOM DCache 对每个 L1→L2 C transaction（或其 source/address）输出 sideband：
  - packet seq
  - tracked
  - possibly dirty
- 在 L2 SinkC 接收/建立 MSHR 时，通过地址/source 关联 sideband；
- 但通过 BoringUtils 按 transaction/source 做动态关联比较复杂，且 source ID 会被内部重写；
- 需要确认 source ID 生命周期和每 bank 多事务并发。

### 方案 B：扩大内部 InclusiveCache Bundle

不改标准 `TLBundleC`，只扩展内部 Bundle：

- 在 `SinkCResponse`、`FullRequest`、`ScheduleRequest`、`DirectoryEntry`、`SourceCRequest` 中加 packet metadata；
- 由 `SinkC` 从一个 sideband/映射获得 metadata；
- 仍需要从 BOOM 将 metadata 送到 L2。

### 方案 C：利用现有全局 BOOM safe watermark 在 L2/BOOM 侧重建

- 不传播每条 line 的 packet seq 无法精确判断 L2 victim 来源包；
- 只能做粗略统计，不符合用户“同样分类”的要求。

### 方案 D：将 packet metadata 编码到现有 TileLink source/address（不推荐）

- 会破坏 source ID/协议语义，不应采用。

**5. 为什么 `l2_wb_dirty=45`，但分类总数只有 44**

这是另一个独立问题。

基础 dirty 计数器没有受到统计窗口使能控制：

[InclusiveCache.scala:218](/data1/gzh/EC/chipyard/generators/sifive-cache/design/craft/inclusivecache/src/InclusiveCache.scala:218)

```scala

  dirtyCount := dirtyCount + 1.U
}
```

而分类计数受到：

```scala

```

控制。

波形显示：

```text

2415559  l2Counting=0
2415627  窗口关闭后又发生一个 dirty writeback，dirtyCount=45
```

所以：

```text

```

并不是分类丢失，而是：

```text
基础 dirtyCount 统计窗口外事件；
分类计数器只统计窗口内事件。
```
