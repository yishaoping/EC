**结构判断与证据边界**

`PackageAddressStats` 的 `packageMem`/`strictMem` 已用 `SyncReadMem`，但五组 `packetWindow × 4 × 64-bit` bucket 仍为 `Reg(Vec(...))`。`packetWindow=256`，合计 **327,680 bit** 的 bucket 状态；源代码还对 bucket 和 64 项 `strictOverflowData` 做并行索引、比较、溢出检查和更新。这与 892,396 LUT 的主归因相符：问题不只是存储容量，而是大规模动态读写、宽 mux、并行比较/归约。Watermark retire 路径本身按 bucket 并行处理，所以直接换成同步 BRAM 可能改变每拍输出；需要保留同一 target-edge 行为的内存模型或结构重写。

Barrier 统计实现对 256 个 bucket 展开 `currentCycle * count(i)`。已有同工具、同器件的 OOC 配对映射从 170,241 降至 83,179 LUT，DSP 从 4,096 降至 16，FF 不变。这是可快速评估的等价组合重写，但证据为 sampled sequential PASS，**不是形式证明，也未证明整机 FIT**。

MSHR 层级有显著异常：`mshrs_0` 为 167,771 LUT，而其他 MSHR 约 3,357–17,544。当前报告定位到了异常，但尚未证明其内部根因。DCache 的 slot epoch、generation、image key、transaction/replay identity 和 SVB payload 属于 EC 功能状态，不应删除；DCache full-module field-read 配对映射显示 1,770,518→1,629,524 LUT，节省 140,994，但报告明确标记为 **not cycle admitted、not whole FIT**。

工作区有 Native 源码副本，但未找到可与 EC 按同一配置、Vivado 阶段和统计口径比较的 Native utilization report 或 DCP。因此不能声称存在准确的逐块 Native→EC LUT 增量。源码确认 Native 没有 `PackageAddressStats`、`SpeculativeVersionBuffer` 和新增 BarrierLatencyStats；这些可标作 EC 新增模块的当前 LUT 占用。MSHRFile 和 DCache 自身则不能从现有报告精确拆出 Native 基线与 EC 增量。

**结构归因**

最大的异常在地址统计逻辑，不是简单的“存储位太多”。[PackageAddressStats](/data1/gzh/EC/firesim/final-opt4-20261106/C4/chipyard/generators/boom/src/main/scala/lsu/PackageAddressStats.scala:230) 用五组 `Reg(Vec(256, Vec(4, UInt(64.W))))` 保存 bucket 计数，共 **327,680 bit**。结构审计还确认有 **3,072 个同周期 64 位 bucket 更新**，以及把 8/80 个来源散射到 256 个目标的归约和错误检查。[结构审计](/data1/gzh/EC/Experiment/firesim-final-opt4-20261106/build-logs/Opt4-fit-structural-roots-r1-20261111/FINDINGS.md:5)

`packageMem` 和 `strictMem` 已经用 `SyncReadMem`，在 MCRams host 层级映射为 200 个 RAMB36 和 24 个 RAMB18。主要开销仍来自 bucket `RegVec` 的动态索引、宽 mux、重复比较、并行溢出归约和清零逻辑，而非这些已映射的关联存储器。[存储与 bucket 定义](/data1/gzh/EC/firesim/final-opt4-20261106/C4/chipyard/generators/boom/src/main/scala/lsu/PackageAddressStats.scala:196)

MSHR hierarchy 也容易误导：`mshrs_0` LUT 特别高，但源码到网表的归因审计发现 `lineGeneration`、`slotEpoch`、`imageKey`、`appliedEffect` 等 DCache metadata 被放进 MSHR0 名下，barrier bucket 逻辑则被放进 prober 名下。这是跨层级搬移，不是 MSHR FSM 本身突然膨胀；不应按模块名去优化错对象。[归因审计](/data1/gzh/EC/Experiment/firesim-final-opt4-20261106/build-logs/Opt4-fit-structural-roots-r1-20261111/FINDINGS.md:3)

DCache 的 epoch、generation、image key、transaction/replay identity 和 SVB payload 是 EC 所需状态，不能靠删字段或缩窄语义来省资源；当前 [DCache metadata 声明](/data1/gzh/EC/firesim/final-opt4-20261106/C4/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:713) 多处使用二维动态索引，适合评估字段分 bank、host 侧复用或 BRAM/URAM 映射。四个 Rocket LSL 各 **3,424 LUT**，合计 **13,696 LUT**，不是 FIT 主因。

**可行优化与最快路径**

- 已有 owner-image MCRams 边界映射把 **405,706 LUT 降到 24,192 LUT**，节省 **381,514 LUT**，但完整 host 仍超容量。它证明存储映射有价值，不代表整机可 FIT。
- 当前地址统计 packed helper 单元从 **5,211 降到 4,879 LUT**，只省 **332 LUT**，不能按 256 倍外推。完整模块已通过 6,144 周期、5,684 输出的逐边沿对照；该候选完整模块面积仍未知。[单 bucket 面积结果](/data1/gzh/EC/Experiment/firesim-final-opt4-20261106/build-logs/Opt4-address-packed-bucket-area-r3-20261112/result.json:1)
- 直接改成 MCRams 并没有解决多端口问题：256×64 接口从 `Reg` 的 **57,148 LUT** 变成 `MemMC` 的 **117,874 LUT**，多用 **60,726 LUT**；barrier storage 候选从 **83,888 LUT** 变成 **158,516 LUT**，多用 **74,628 LUT**。后者虽然有限 parity 通过，但生成接口仍是 256 个零延迟读口、一个写口。[地址存储配对结果](/data1/gzh/EC/Experiment/firesim-final-opt4-20261106/build-logs/Opt4-mcrams-address-bucket-area-r2-20261112/result.json:1) [barrier 配对结果](/data1/gzh/EC/Experiment/firesim-final-opt4-20261106/build-logs/Opt4-barrier-fullmodule-host-pair-r2-20261112/result.json:1)
- 现有局部 DCache field-read 映射报告节省 **140,994 LUT**，但尚未通过完整 target-cycle admission；`appliedEffectResult` 单独映射节省 **33,318 LUT**，仍需完整 DCache 边界证明。它们与其他候选可能重叠，不能相加充作整机节省。

BRAM 容量尚有余量，URAM 未使用；真正的限制是大量异步、多端口访问无法直接推断成紧凑存储器。Golden Gate host 侧时间复用仍可行，但必须保持同一 target edge 的读写、旁路、冲突和错误状态语义；未经完整模块逐周期验证的同步 RAM 改写不能直接采用。
