最重要的技术问题：

1. 当前 sideband 只填充 `SinkC.io.req.bits`，但 `ProbeAckData` 属于 `SinkC.io.resp` 路径，不会进入 `io.req`。而 BOOM writeback unit 对 L2 probe 很可能发送 `ProbeAckData`，因此实际 dirty writeback provenance 可能丢失。
   - 应扩展 `SinkCResponse`，携带 `packetSeq/packetTracked`。
   - 在 `SinkC` 对 `ProbeAckData` 的 response 设置这些字段。
   - 在 `MSHR.when(io.sinkc.valid)` 中更新当前 `meta`。
   - 还需通过 `NestedWriteback` 将 c-MSHR 收到的 provenance 回传给父 MSHR，否则父 MSHR 产生的 L2 victim 仍会丢失元数据。

2. BoringUtils 地址 CAM 当前只有 16 项、没有消费/确认机制，旧项永久 valid：
   - 同地址可能存在多个匹配项，`Mux1H` 不再真正 one-hot。
   - 后续 clean release 可能错误复用旧 dirty metadata。
   - 更稳妥的方案是给 `TLBundleC.user` 增加自定义 `ControlKey`，沿 C 通道传输；相关接口在 `rocket-chip/src/main/scala/tilelink/Bundles.scala:206-221`，参数传播通过 `requestFields/requestKeys`。
   - 若继续使用 CAM，至少要只对 `ReleaseData/ProbeAckData` 匹配，并采用按地址更新或足够大的表及有效期策略。

3. L2 统计当前事件定义为 `scheduler.io.dcacheWriteback = sourceC.io.req.fire()`，这是 SourceC 接受内部请求的时刻，不是实际外部 `out.c.fire()`。需要明确统计口径：
   - 若表示“L2 victim 开始处理”，当前定义可保留；
   - 若表示“真正发往 DRAM 的写回”，应使用 SourceC 外部 C 通道首 beat fire。

4. `GH_L2_STATS_ENABLE_BORE` 已在 BOOM DCache 侧定义并输出，但 L2 当前未看到对应 sink/事件门控，可能导致统计窗口外也累计 L2 事件。应在 L2 sink enable，并让周期与事件只在测量窗口内推进；reset 需优先于同周期事件。
