## Store/load 不匹配的逻辑解释

BOOM 与 checker 的计数本身各自满足内部不变量：

BOOM：

```text
store_total = store_cache + store_uncache
60559 = 60510 + 49

load_total = load_cache + load_uncache
93455 = 93158 + 297
```

`load_forward=1578` 单独统计。当前源码已经把 BOOM `load_total` 定义成 cache + uncache，保持与 checker 的语义范围一致；forward 另列。

Checker：

```text
store=1648 cache + 48 uncache = 1696
load=1627 cache + 286 uncache = 1913
load_forward=0
```

真正的问题是 package 没有完整执行：

- BOOM 统计的是检查窗口内真实完成的全部 BOOM memory 操作；
- Rocket checker 只统计它实际重执行并完成到 WB 的操作；
- BJL 在每个包的 branch 流处失败后，checker package 被取消并 flush；
- 当前包后半段的 store/load 不会再由 checker 完成；
- 因此 checker 只留下部分前缀操作，导致 `60559 vs 1696`、`93455 vs 1913`。

`store_uncache` 恰好接近：

```text
BOOM=49
checker=48
```

这不是说明协议基本正确，而是不可缓存 store 分布较稀疏，出现了接近的偶然结果。

## BOOM 与 Rocket 数据流逻辑链

```text
BOOM R_IC snapshot
  -> packet_seq_counter / checker_segment_id
  -> GH_BUF 生成数据和 branch packet
  -> GHM 依据 live checker_segment_id 添加 sequence
  -> data AsyncQueue / ARF AsyncQueue
  -> RocketTile 解码 packet
  -> RocketCore package lifecycle
  -> R_ICSL / R_LSL / R_RSUSL / CSR 完成
  -> result CDC
  -> GHM BOOM 域 dequeue
  -> R_IC clear_ic_status
  -> DCache package bitmap / dirty writeback statistics
```

当前风险：

1. `R_IC` 在 snapshot 时分配 sequence，不要求 data anchor 已经产生。
2. `GH_BUF` 的 FIFO 项没有保存 package sequence。
3. GHM 使用当前 live `checker_segment_id` 给 GH_BUF 输出打 sequence。
4. ARF/CPS 与 data 是独立 CDC 队列，没有原子包边界握手。
5. package allocation、data anchor、ARF/CPS merge 不是一个不可分割事务。
6. BJL 输入只携带 branch payload 和 sequence，不能证明 branch record 属于当前包的执行前缀。

已有 Debug 文档明确指出这些风险：

- `Debug/guardian_protocol_audit.md`

## store/load 不匹配的原因

BOOM 计数本身闭合：

```text
60559 = 60510 + 49
93455 = 93158 + 297
```

checker 计数也闭合：

```text
store=1648 cache + 48 uncache =1696
load =1627 cache +286 uncache =1913
```

问题不是单个 cache/uncache 计数器简单加错，而是统计集合不同：

- BOOM 统计检查窗口内实际完成的全部 BOOM memory 操作；
- checker 只统计成功到达 WB 的重执行操作；
- BJL 失败后 package 被取消并 flush；
- 取消包后半段的 store/load 不会由 checker 完成；
- checker 只留下取消前的部分前缀。

所以：

```text
BOOM store=60559 vs checker store=1696
BOOM load =93455 vs checker load =1913
```

不可缓存 store：

```text
BOOM=49
checker=48
```

只是由于事件稀疏而接近，不能说明协议正确。

## latency 统计问题

`R_ICSL.scala` 中：

- `debug_perf_num_st_uncache` 对 checker 不可缓存 store completion 全局累加；
- `debug_perf_st_uncache_cycle_sum` 只在 `io.if_check_completed` 时把当前包事件数乘入；
- 取消包会清空当前包计数，但不会把它的周期和加入总周期和。

因此可能出现：

```text
事件数量包含取消包
周期和不包含取消包
```

软件 `report.c` 当前只用：

```c
checker_count == boom_count
```

作为 latency 可计算条件，不足以证明两边是同一组 package。应至少要求：

```text
stats_valid=1
pending=0
result_dropped=0
cancelled=0
BOOM/checker package sequence 集合一致
```

更严谨的方案是按 package sequence 关联 BOOM 和 checker 的不可缓存 store 事件。

## 脏写回 latency 失败链

DCache 使用 256 项 bitmap/bucket：

- allocated bitmap
- completed bitmap
- passed bitmap
- packet sequence
- dirty writeback bucket

安全水位只跨连续 PASS package 推进。第一个 package 就 cancelled，因此：

```text
safePacketWatermark=0
```

后续 PASS 不能跨过 sequence 1 推进安全水位，最终：

```text
resolved=0
pending=638
stats_valid=0
```

因此 dirty writeback latency 失败的根因是 package completion ledger 无法闭合，而不是周期减法本身错误。

当前不建议：

- 只把 `commit_pending_age` 从 15 调大；
- 只把 `statsWindow` 从 256 改成 512。

这些只会延迟或掩盖问题。

## 当前完整逻辑链

```text
BOOM R_IC snapshot
  -> packet_seq_counter / checker_segment_id
  -> GH_BUF 数据包和 branch packet
  -> GHM 根据 live checker_segment_id 添加 sequence
  -> data AsyncQueue / ARF AsyncQueue
  -> RocketTile 解码并路由
  -> RocketCore 包生命周期
  -> R_ICSL / R_LSL / R_RSUSL / CSR 完成
  -> checker result CDC
  -> GHM BOOM 域 dequeue
  -> R_IC clear_ic_status
  -> DCache package bitmap / dirty writeback 统计
  -> 软件 report.c 输出 latency
```

当前协议存在的核心结构性问题：

1. `R_IC` 在 snapshot 时分配 sequence，不要求 data anchor 已产生。
2. `GH_BUF` FIFO entry 不保存 package sequence。
3. GHM 使用当前 live `checker_segment_id` 给输出打 sequence。
4. Data、ARF/CPS、BJL 使用独立 CDC 队列，没有原子包边界。
5. allocation、data anchor、ARF/CPS merge、BJL owner 不是不可分割事务。
6. ARF/CPS 可能在没有 data anchor 时先到达。
7. BJL branch record 可能在包真正启动前生成，却被当前 live sequence 归属。
8. `packet_cdc_ready = RSU ready | LSL ready | BJL ready` 的旧语义会导致目标队列不能接收时，GHM 仍消费整个 beat。
9. R_RSU merge 结束条件如果不检查 `big_hang`，可能在 ARF CDC 满时丢最后一项。
10. 结果队列等待、local cleanup、BOOM release 之前曾存在顺序耦合和结果丢失。
11. sequence 只用普通大小比较，回绕时存在风险。
12. 当前 generated collateral、VCD、Scala 工作树不是完全保证同一 revision，分析时必须明确区分。

## store/load 不匹配根因

BOOM 统计闭合：

```text
60559 = 60510 + 49
93455 = 93158 + 297
```

checker 统计也闭合：

```text
store=1648 cache +48 uncache=1696
load=1627 cache +286 uncache=1913
```

问题不是 cache/uncache 加法错误，而是统计集合不同：

- BOOM 统计检查窗口内实际完成的 BOOM memory operations；
- checker 只统计成功到达 WB 的重执行 operations；
- BJL/ARF/进度错误会取消 package 并 flush；
- 取消发生后，包后半段 store/load 不会在 checker 执行；
- checker 只保留取消前的前缀。

所以：

```text
BOOM store=60559 vs checker store=1696
BOOM load =93455 vs checker load =1913
```

不可缓存 store 恰好接近：

```text
BOOM=49
checker=48
```

只是因为事件稀疏，不能证明协议正确。

当前 `R_ICSL.scala` 已尝试修复一个边界：

```scala
if_completion 使用 ic_counter_shadow
```

而旧逻辑使用 `ic_counter_shadow + 1.U`，可能把 checker drain-tail 指令计入包，造成额外 checker memory traffic。

当前 `RocketCore.scala` 的统计路径：

```scala
checker_mem_complete =
  checker_mode &&
  !if_overtaking_next_cycle &&
  wb_valid &&
  wb_ctrl.mem &&
  lsl_resp_valid &&
  !lsl_resp_replay
```

需要保证 BOOM 与 checker 统计都定义在相同语义上：建议都只统计有效 package、有效 architectural completion，并用 `package_seq` 关联。

## store_uncache latency 根因

`R_ICSL.scala` 当前逻辑：

```text

result_dropped == 0
cancelled == 0

BOOM/checker package sequence 集合一致
```

当前故障的关键是：这些阶段并没有共同使用一个严格的 `valid/fire/sequence/terminal-result` 协议。

**3. P0 根因一：首包启动时 BJL 流与 checker 实际执行流不一致**

但此时 Rocket checker 前端 PC 仍在：


这不是简单的低位对齐错误，而是 BJL 分支流和 checker 实际取指流不属于同一个控制流。

随后出现重定向竞争：


`Frontend.scala` 中的 `pc_match`、BJL replay 和 `RocketCore.scala` 中的 `take_pc_wb`/`replay_wb`/`mem_npc` 多个控制源没有形成唯一的启动优先级：

**4. P0 根因二：包分配、data anchor、ARF/CPS 不是原子事务**

`R_IC.scala` 中的 allocation 本质上由 snapshot 接受触发，见 [R_IC.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_IC.scala:168)。它不要求：

- GH_BUF 已经有 data；
- data CDC 已经 `enq.fire`；
- data anchor 已经进入 checker；
- ARF/CPS 已经具备对应序列。

旧协议允许出现：

```text
sequence N 已分配
ARF/CPS sequence N 已开始发送
但 data sequence N 没有任何有效 anchor
```

sequence 7 的波形正是这种情况：

```text
105583: R_IC 分配 sequence 7
105585: checker segment watermark 变为 7
105595 之后: ARF/CPS sequence 7 开始进入 CDC
整个窗口没有 sequence-7 data enqueue
```

GHM 当时从 live `checker_segment_id` 给输出打序列，而 GH_BUF 的 data FIFO 并没有保存 package sequence。于是：

```text
ARF sequence 7 存在
data sequence 7 不存在
dataConsumedSeq 仍停留在 6
ARF FIFO 无法继续释放
ARF CDC 满
big_hang=1
BOOM ROB 停止提交
BOOM idle watchdog 最终触发
```

这条链解释了 `assert__assert_21` 类型的 BOOM hang。

当前源码已经加入 zero-data anchor、sequence 保留、data/ARF 顺序控制等尝试，但保存的 VCD/生成 RTL 属于旧 revision，因此不能把这些源码修改视为已经通过波形验证。

**5. P0 根因三：数据入口曾经不是按 lane 类型进行原子握手**

旧路径中，RocketCore 的 `packet_cdc_ready` 曾经是：

```text
RSU ready | LSL ready | BJL ready
```

这不能表示一个混合数据 beat 是否真的可以被完整接收。例如：

```text
LSL 已 near-full
BJL 仍 ready
```

OR 结果仍为 1，GHM 会 dequeue 整个 beat，但 LSL 对应 lane 无法接收，导致内部 FIFO 丢数据。

后果是：

```text
GHM 已消费数据
目标 FIFO 没有接收
上游没有回滚
checker 后续永远等待缺失的 memory record
```

当前源码已经向 `RocketTile`、`R_LSL` 和 `GH_FIFO` 增加了按类型的 ready、overflow 和原子 beat 判断，相关位置见：

- [RocketTile.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/tile/RocketTile.scala:194)
- [R_LSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_LSL.scala:95)
- [R_LSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_LSL.scala:309)

但这些修改尚未经过重新生成 RTL 和运行验证。

**6. P1 根因：R_RSU 的合并进度必须绑定真实 CDC fire**

ARF/CPS 合并流很长，而 ARF CDC 深度只有 8。只要 `big_hang=1`，最后的 PC/FCSR/CSR 项就可能无法发送。

如果 `merging` 状态只根据计数器结束，而不根据真实接收确认结束，就会出现：

```text
最后一项没有进入 CDC
merge 状态却结束
ARF/CPS 尾项永久丢失
checker 永远等不到完整 ECP
```

当前 [R_RSU.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_RSU.scala:151) 已加入 `!io.big_hang` 条件，但真正稳健的协议仍应是“该项 `enq.fire` 后计数器才推进”。

**7. store/load 数量不匹配的真实含义**

日志中的统计是：

```text
BOOM:
store = 60559 = 60510 cache + 49 uncache
load  = 93455 = 93158 cache + 297 uncache + 1578 forward

checker:
store = 1696 = 1648 cache + 48 uncache
load  = 1913 = 1627 cache + 286 uncache
```

加法本身是闭合的，问题在于两边统计的集合不是同一个集合。

BOOM 统计的是 BOOM 侧有效完成的 memory operation；checker 统计的是 checker 模式下满足 [RocketCore.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/rocket/RocketCore.scala:920) 条件、真正到达 WB 的重执行操作。它要求：

```text
checker mode
WB valid
LSL response valid
没有 replay
没有 overtaking
```

因此一个包被取消后：

```text
BOOM 前半段 memory operation 可能已经统计
checker 只执行到取消前缀
checker 后半段 store/load 不会出现
```

此外还有两个语义差异：

- BOOM 有 `load forward`，checker 没有对应 forwarding 统计；
- 当前 checker 统计只在有效 architectural completion 时累加，不统计进入 FIFO 但没有成功重放的记录。

所以不能用：

```text
BOOM 总 store/load == 所有 checker 总 store/load
```

作为正确性条件。正确条件应该是：

```text
对每一个 PASS package sequence：
BOOM 的 memory log 集合
==
checker 实际重放并完成的 memory log 集合
```

取消包必须从 latency 样本中排除，或者整个测量窗口判 invalid。

**8. 不可缓存 store latency 的问题**

当前 [R_ICSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_ICSL.scala:497) 同时维护：

```text
全局不可缓存 store 数
当前 package 内不可缓存 store 数
不可缓存 store cycle sum
```

事件发生时，全局计数会增加；但 cycle contribution 只有在包完成时才加入总和。取消包路径只是清空当前 package 的事件计数：

```text
if_check_cancelled -> packet_event_count := 0
```

却不会把该包的周期贡献加入总和。

因此可能出现：

```text
event count 包含取消包
cycle sum 不包含取消包
```

这正是 BOOM `49`、checker `48` 接近但不相等的一个原因。它不是证明协议正确，而是因为不可缓存 store 事件较少，差异暂时只有 1。

软件 [report.c](/data1/gzh/EC/Software/Test/stat/report.c:143) 目前只用：

```c
checker_count == boom_count
```

决定是否计算平均 latency。这个条件必要但不充分；即使数量相等，也不能证明两边是同一批 package sequence。

**9. 脏写回 latency 为什么全部无效**

DCache 统计逻辑在 [dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:903) 中使用 256 项 bitmap/bucket，并且 `safePacketWatermark` 只跨连续 PASS package 推进。

当前结果是：

```text
verify_required = 651
verified        = 0
resolved        = 0
pending         = 638
other           = 13
safe_watermark  = 0
stats_valid     = 0
```

sequence 1 取消后，PASS watermark 无法跨过 sequence 1。即使 sequence 2、3、4 后续 PASS，也不能推进安全水位。后续脏写回只能进入 pending bucket，无法结算。

这不是周期减法错误，而是“包终态账本没有闭合”。此外，bitmap 窗口没有对 BOOM allocation 施加容量反压，所以 256 项被占满后，allocation collision 只被记账，不会阻止新包继续产生。

**10. 后续综合修复应遵守的协议不变量**

建议按以下优先级处理：

1. 每个 package 只分配一个 sequence/epoch，data、ARF/CPS、BJL、result 全部携带该身份。
2. data anchor 必须先于 ARF/CPS/BJL 消费；空数据包必须有明确的 zero-data anchor。
3. 所有 CDC 都必须使用真正的 `valid/ready/fire`，不能用无关目的地 ready 的 OR。
4. 一个混合 data beat 只有在所有有效 lane 都能接收时才允许 dequeue。
5. BJL 第一条 `cpc` 必须和 checker 实际取指 PC 建立稳定匹配；启动 PC、replay、异常、special return 必须有唯一优先级。
6. R_RSU 只有在对应项真实 `fire` 后才推进 merge counter 或结束 merge。
7. 每个 package 必须产生且只产生一个 terminal result：`PASS/FAIL/CANCELLED`。
8. BOOM `clear_ic_status` 只能由带 sequence 的 result 在 BOOM 域 dequeue 驱动。
9. result waiting、local cleanup、BOOM release 三者必须解耦，但都必须可观测、可回压。
10. 所有 `START_WAIT`、`LSL 非空但 checker 不前进`、异常上下文未返回等状态都必须有独立 progress timeout。
11. 延迟统计必须按 sequence 关联，不能只比较总数。
12. DCache 应区分“所有终态包的 ownership watermark”和“只有 PASS 包的 measurement watermark”，并对 bitmap 容量提供反压或明确 overflow 终止。

最终验收条件应至少是：

```text
allocated = completed
每个 allocated sequence 恰好一个 terminal result
每个 terminal result 恰好一次 GHM dequeue/release
result_dropped = 0
allocation_collision = 0
writeback_dropped = 0
pending = 0
stats_valid = 1
```

对于每个 PASS sequence，还要满足：

```text
BOOM store/load 操作集合
==
```

## 一、最直接的确定性错误：DCache 删除了 `load_forward`

当前 [dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:1414) 把：

```scala
load_total = load_cache_count + load_uncache_count
```

替代了原来的：

```scala
load_total = load_cache_count + load_uncache_count + load_forward_count
```

这会直接破坏计数器不变量。

当前日志中：

```text
BOOM load_total = 93455
load_cache       = 93158
load_uncache     = 297
load_forward     = 1578
```

实际应为：

```text
93158 + 297 + 1578 = 95033
```

但当前 `load_total` 只有：

```text
93158 + 297 = 93455
```

所以 DCache 的 load 总数已经和自己的三个分类项不一致。这一修改没有统计学或硬件语义依据，必须作为第一类回归处理。

协议定义本来就是：

```text
BOOM:
store_total = store_cache + store_uncache
load_total  = load_cache + load_uncache + load_forward

Rocket checker:
store_total = store_cache + store_uncache
load_total  = load_cache + load_uncache
load_forward = 0
```

参考 [store_load_traffic_tracking.typ](/data1/gzh/EC/Method/Traffic/store_load_traffic_tracking.typ:216)。

BOOM 的 STQ forwarding 并不意味着该 load 不需要校验。checker 重执行同一条指令时没有 BOOM 的 STQ forwarding 路径，而是通过 LSL 读出，因此正确的跨核对应关系是：

```text
BOOM store_total == checker store_total
BOOM load_total  == checker load_total

BOOM store_uncache == checker store_uncache
BOOM load_uncache  == checker load_uncache
BOOM load_cache + BOOM load_forward == checker load_cache
```

不能要求 `BOOM load_cache == checker load_cache`，因为 BOOM 的 forwarding load 在 checker 侧会表现为普通 LSL cache load。已有正确结果就是：

```text
BOOM    load = 2337 + 96 + 17 = 2450
checker load = 2354 + 96 + 0 = 2450
```

### 2. RocketCore 结果释放条件被放宽，可能造成 checker 重用重叠

```text

```

不能通过删除 BOOM 的 `load_forward` 来“制造相等”。

### 阶段 D：恢复 latency 统计

不可缓存 store latency 应先保持原方案的统计模型：


但必须明确：

- PASS 包才进入 latency 样本；
- FAIL/CANCELLED 包的包内计数和周期贡献必须一起丢弃；
- 不能出现“事件数包含取消包、周期和不包含取消包”。

更稳健的长期方案是按 `package_seq` 保存：

```text

```

在 PASS sequence 集合上配对计算，而不是只比较全局总数。

脏写回 latency 也不应修改成“把取消包当 PASS”。正确做法是：

```text

```

这样既不会卡死 BOOM slot，也不会把取消包混入有效延迟样本。
