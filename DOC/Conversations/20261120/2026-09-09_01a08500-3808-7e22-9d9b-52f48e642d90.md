- `memcpy` 的 `0x800032ae`；

## 一、权威计数点改为 ROB commit

BOOM 已经有准确的架构提交信号：

[`rob.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/exu/rob.scala:458)

```scala
io.commit.valids(w)      := will_commit(w)
io.commit.arch_valids(w) := will_commit(w) && !rob_predicated(com_idx)
```

并且已经导出为：

[`core.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/exu/core.scala:2173)

```scala
io.commit_valids := rob.io.commit.arch_valids
io.commit_uops   := rob.io.commit.uops
```

因此，权威计数应当按照以下条件产生：

```text
commit_mem = commit_arch_valid &&
             (uop.uses_ldq || uop.uses_stq)
```

具体分类：

```text
load_commit  = commit_arch_valid &&
               uop.uses_ldq &&
               uop.mem_cmd == M_XRD

store_commit = commit_arch_valid &&
               uop.uses_stq &&
               uop.mem_cmd == M_XWR
```

LR、SC、AMO 单独统计，不并入普通 load/store total。这样与 Rocket checker 中的：

```scala
checker_store_complete && mem_cmd === M_XWR
checker_load_complete  && mem_cmd === M_XRD
```

保持一致。

这里必须使用 `arch_valids`，不能使用普通的 `valids`，因为 `valids` 可能包含被 predication 屏蔽的指令。

## 三、cacheable/uncacheable 也要在提交点分类

仅把 total 改成 commit 计数还不够。为了保证以下关系始终成立：

```text

```

每个 LDQ/STQ 项都应携带一个稳定的 `commit_cacheable` 元数据。

```text

```

- TLB miss 重试；
- DCache replay；
- MSHR refill；
- store queue 等待；
- load forwarding；
- ROB commit。

```scala
edge.manager.supportsAcquireBFast(addr, lgCacheBlockBytes.U)
```

当前 DCache ingress 已经使用该判定：

[`dcache.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:637)

```scala

  edge.manager.supportsAcquireBFast(...)
```

不要在提交时重新读取当前 DCache 状态，也不要使用当前全局的 `traffic_check_state` 推测 cacheability。

在 LSU 的 commit dequeue 过程中，直接从即将提交的 LDQ/STQ 项读取该字段。对应位置在：

[`lsu.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:1577)

```scala
val commit_store = io.core.commit.valids(w) && ...
val commit_load  = io.core.commit.valids(w) && ...
```

在 queue entry 被清除之前生成与 commit slot 对齐的：

```text
commit_cacheable(w)
commit_cacheable_valid(w)
```

不要直接复用 `gh_buf.io.commit_cacheable`。该信号经过 `RegNext` 和 Guardian buffer 路径，适合校验包生成，不适合作为精确计数点。

## 四、建议的统计向量定义

现有软件 ABI 中的 counter 编号可以保持不变，但重新定义前 7 项的含义：

| Counter | 建议含义 |
|---|---|
| `STORE_TOTAL` | ROB 架构提交的普通 store |
| `STORE_CACHE` | ROB 提交且 cacheable 的普通 store |
| `STORE_UNCACHE` | ROB 提交且 uncacheable 的普通 store |
| `LOAD_TOTAL` | ROB 架构提交的普通 load |
| `LOAD_CACHE` | ROB 提交且 cacheable 的普通 load |
| `LOAD_UNCACHE` | ROB 提交且 uncacheable 的普通 load |
| `LOAD_FORWARD` | forwarding 路径诊断计数，不再参与 `LOAD_TOTAL` |

因此 total 应定义为：

```text
STORE_TOTAL = STORE_CACHE + STORE_UNCACHE
LOAD_TOTAL  = LOAD_CACHE + LOAD_UNCACHE
```

`LOAD_FORWARD` 是执行路径信息。它可能与 cacheable load 的架构提交事件重叠，不能继续采用：

```text
LOAD_TOTAL = cache_load + uncache_load + forward_load
```

这种做法会把实现路径误当成架构指令数。

本次运行期望得到：

```text

store_cache  = 60521
store_uncache= 49

load_total   = 95062
load_cache   = 94765
load_uncache = 297
```

并满足：

```text
60521 + 49   = 60570
94765 + 297  = 95062
```

## 五、forwarding 只保留为独立诊断统计

当前 forwarding 的问题来自：

[`lsu.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:1137)

```scala
mem_forward_traffic_check = RegNext(io.dmem.traffic_check_state)
wb_forward_traffic_check  = RegNext(mem_forward_traffic_check)
```

这实际上是使用全局状态延迟两拍推测某条 load 的归属，无法保证与具体 load 对齐。

如果还需要精确统计 forwarding 路径，应改为每条 load 携带元数据：

```text
LDQEntry.forward_traffic_check
LDQEntry.commit_cacheable
```

并随以下信号一起保存：

```text
mem_forward_valid
mem_forward_ldq_idx
mem_forward_ld_addr
mem_forward_traffic_check
```

到 forwarding writeback 阶段使用对应 LDQ 项的属性：

```text
forward_count =
  wb_forward_valid &&
  ldq(f_idx).forward_traffic_check &&
  !ldq(f_idx).traffic_seen &&
  forward_uop.mem_cmd == M_XRD
```

不能再使用统一的：

```text
RegNext(RegNext(global_traffic_check_state))
```

不过需要强调：即使 forwarding 统计完全正确，也不应将其加入架构 `LOAD_TOTAL`。架构 total 只由 ROB commit 产生。

## 六、现有 DCache 计数保留为微结构诊断

当前 DCache 统计点：

[`dcache.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:1346)

```scala
completed_store_cache =
  dataWriteArb.io.in(0).fire &&
  s3_req.traffic_check &&
  ...
```

load 则来自：

```scala
traffic_load_cache_complete
traffic_load_uncache_complete
traffic_load_forward_complete
```

这些统计可以继续保留，用于：

- DCache 实际请求完成数；
- cache hit/miss；
- replay；
- forwarding；
- uncacheable 延迟；
- data-array 写入；
- MSHR completion；
- 性能和一致性诊断。

但是建议在软件报告中把它们与架构计数区分开，例如概念上分为：

```text
arch_store_total
arch_load_total

exec_store_cache
exec_load_cache
exec_load_forward
exec_store_uncache
```

这样不会再把 DCache response 数误认为退休指令数。

## 七、RESET/START/STOP 必须与提交计数保持同样语义

当前 DCache 对 STOP 边界采用“包含 STOP 当周期事件、下一周期生成快照”的方式：

[`dcache.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:453)

```scala
trafficCounting =
  (trafficEnabled || io.traffic_start) &&
  !io.traffic_reset
```

并在 STOP 后一拍捕获快照。

新增的 commit counters 必须使用完全相同的规则：

- RESET 周期清零；
- START 周期允许计数；
- STOP 周期仍计数；
- STOP 下一周期锁存快照；
- 快照读取过程不再增加计数。

否则即使 commit 计数点正确，也可能因为 START/STOP 边界不同而少一条或多一条。

## 八、推荐的验证条件

后续修改后，不需要重新依赖大量波形人工分析，直接增加以下一致性检查：

```text
arch_store_total == arch_store_cache + arch_store_uncache
arch_load_total  == arch_load_cache + arch_load_uncache
```

并在测试结束时检查：

```text
BOOM arch_store_total == checker_sum store
BOOM arch_load_total  == checker_sum load
```

本次运行应为：

```text
BOOM arch_store_total = 60570
checker_sum store     = 60570

BOOM arch_load_total  = 95062
checker_sum load      = 95062
```

还应增加一条波形/断言性质：

```text
架构 total 计数器只能在 rob.commit.arch_valids &&
M_XRD/M_XWR 时递增
```

这样可以保证以下事件不会影响架构 total：

- speculative load；
- branch-mispredict 后的 load；
- DCache replay；
- nack；
- refill response；
- forwarding response；
- cache line writeback；
- 同一 LDQ 项的重复 response。

## 最终推荐

最稳妥的方案是：

```text
ROB commit
   ├── arch store/load total
   ├── commit cacheability 分类
   └── 与 checker 统计直接比较

DCache/LSU completion
   ├── response
   ├── replay
   ├── forwarding
   └── 延迟与路径诊断
```

不要试图继续通过调整 `traffic_check` 的延迟拍数，让 DCache response 计数器“碰巧”追上 checker。这样只能修复当前波形中的边界误差，无法保证其他程序、其他 cache miss 模式或其他包边界下仍然匹配。

本方案暂不需要修改软件测试、访存执行逻辑、校验协议或硬件行为，只需要在后续实现阶段把统计源从 DCache completion 改为 ROB architectural commit，并将 cacheability 元数据稳定地随 LDQ/STQ 保存到提交点。

## 1. 当前问题的本质

当前大核计数存在三种不同语义：

### DCache 请求作用域

在 DCache ingress 处使用：

```scala
outer.dcache.module.io.traffic_check_state :=
  core.io.debug_maincore_status === 2.U
```

并在请求进入 DCache 时锁存：

```scala
s0_req(w).traffic_check := io.traffic_check_state
```

这个信号代表的是：

```text
请求进入 DCache 的时刻，BOOM 是否处于 check 状态
```

它不代表：

```text
这条指令最终是否提交
```

### DCache/LSU 完成路径

当前统计位置包括：

- cacheable store：`dataWriteArb.io.in(0).fire`
- uncacheable store：TileLink A 通道 `mem_access.fire`
- cacheable load：DCache response
- uncacheable load：MSHR response
- forwarding load：forwarding writeback

这些事件都可能发生在 ROB 提交之前，并且可能对应：

- speculative load；
- replay/nack；
- 内存顺序失败；
- 被分支错误清除的指令；
- 请求进入和响应完成跨越 `fsm_check` 边界的指令。

### forwarding 的全局延迟信号

当前 forwarding 使用：

[`lsu.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:1137)

```scala
mem_forward_traffic_check = RegNext(io.dmem.traffic_check_state)
wb_forward_traffic_check  = RegNext(mem_forward_traffic_check)
```

这实际上是假设每条 forwarding load 都固定在两拍后完成，但 forwarding 的具体来源、阻塞、流水线状态和 LDQ 项并不一定与这个全局延迟信号严格对应。

因此，不能继续用：

```text
全局 traffic_check_state 延迟 N 拍
```

来判断具体某条 load 是否属于统计窗口。

## 2. 使用三种不同的统计标签

建议不要继续只使用一个 `traffic_check` 信号，而是区分三个语义。

### 2.1 `exec_traffic_check`

表示：

```text
访存请求进入 DCache 或发生 forwarding 时，当前是否处于执行统计窗口
```

它可以保留现有 `traffic_check`，主要用于原始微结构路径分析。

例如：

```text
request.traffic_check
response.traffic_check
raw_forward_traffic_check
```

这类信号可以继续观察“请求从哪个状态进入执行路径”。

### 2.2 `arch_traffic_check`

表示：

```text
该访存指令最终在 ROB commit 时，是否属于架构统计窗口
```

建议在 ROB 提交点生成：

```scala
arch_traffic_check(w) =
  rob.io.commit.arch_valids(w) &&
  (debug_maincore_status === 2.U)
```

这里必须使用 `arch_valids`，而不是普通的 `valids`。

`CommitSignals` 已经有：

```scala
val valids      = Vec(retireWidth, Bool())
val arch_valids = Vec(retireWidth, Bool())
val uops        = Vec(retireWidth, new MicroOp())
```

其中：

- `valids` 表示 ROB 释放/提交流水线槽位；
- `arch_valids` 才表示真正的架构指令提交。

这条 `arch_traffic_check` 是严格微结构计数的最终门控信号。

### 2.3 `path_traffic_check`

表示：

```text
某个 LDQ/STQ 项的严格微结构计数资格
```

它不再来自全局延迟信号，而是来自对应的 LDQ/STQ 项：

```text
ldq(idx).arch_traffic_check
stq(idx).arch_traffic_check
```

forwarding、DCache response 和 store completion 都通过具体的 LDQ/STQ 索引读取该字段。

这样，forwarding 判断的是：

```text
这条 forwarding load 对应的 LDQ 项是否属于架构统计窗口
```

而不是：

```text
当前全局状态两拍前是否为 1
```

## 3. 增加 LDQ/STQ 访存记账状态

### LDQ 建议新增字段

```text
arch_traffic_check       // ROB commit 时确定
traffic_cacheable        // 该 load 的统一 cacheability
traffic_path_valid       // 是否已经产生最终执行路径
traffic_path             // CACHE_RESP / UNCACHE_RESP / FORWARD
traffic_path_counted     // 是否已经完成严格记账
traffic_exec_epoch       // replay/order-fail 代次
```

已有的：

```text
traffic_seen
```

继续用于响应去重，但不再作为架构计数是否完成的唯一依据。

### STQ 建议新增字段

```text
arch_traffic_check
traffic_cacheable
traffic_path_valid
traffic_path             // CACHE_STORE / UNCACHE_STORE
traffic_path_counted
```

store 的 `arch_traffic_check` 在 ROB 提交时锁存，随后随 STQ 项一直保存到 DCache 完成。

## 4. Load 的严格记账流程

Load 的正确时序通常是：

```text
load 执行
  -> DCache response 或 forwarding
  -> 可能 replay/order-fail
  -> ROB commit
```

因此不能简单地在 response 或 forwarding 当周期增加最终计数。

建议采用以下流程。

### 4.1 DCache response

DCache response 到达 LSU 时：

```text
记录 path = CACHE_RESP 或 UNCACHE_RESP
记录 cacheability
设置 traffic_path_valid
```

但此时不立即增加严格架构计数。

如果之后发生：

- nack；
- memory ordering failure；
- 分支清除；

则清除：

```text
traffic_path_valid
traffic_path_counted
```

并允许同一个 LDQ 项重新执行。

### 4.2 Forwarding response

forwarding writeback 时：

```text
f_idx = wb_forward_ldq_idx(w)
```

应当读取：

```text
ldq(f_idx).arch_traffic_check
ldq(f_idx).traffic_cacheable
```

而不是使用：

```scala
wb_forward_traffic_check
```

forwarding 只记录：

```text
path = FORWARD
```

并且应当明确：

```text
forwarding load 是 cacheable load 的一个执行子路径
```

因此：

```text
strict_load_cache
    = strict_load_cache_response + strict_load_forward
```

而不是：

```text
strict_load_total
    = cache_response + uncache_response + forwarding
```

否则 forwarding 会被重复计入。

### 4.3 Load commit 时结算

在 LSU 当前的 commit dequeue 位置：

[`lsu.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:1577)

```scala
val commit_store = ...
val commit_load  = ...
```

应在清除 LDQ 项之前，读取该项的：

```text
arch_traffic_check
traffic_path_valid
traffic_path
traffic_cacheable
```

生成一次严格计数事件：

```text
strict_load_commit_event =
    commit.arch_valid &&
    commit.mem_cmd == M_XRD &&
    ldq.path_valid &&
    !ldq.path_counted
```

然后按照最终路径分类：

```text
CACHE_RESP  -> strict_load_cache_response + 1
FORWARD     -> strict_load_forward + 1
UNCACHE_RESP-> strict_load_uncache + 1
```

其中：

```text
strict_load_cache =
    strict_load_cache_response +
    strict_load_forward

strict_load_total =
    strict_load_cache +
    strict_load_uncache
```

这样，即使 load 的 response 发生在 ROB commit 之前，也不会因为 speculative response 过早计数。

## 5. Store 的严格记账流程

Store 的时序与 load 相反：

```text
ROB commit
  -> store 进入 STQ committed 状态
  -> DCache data write 或 uncache A 通道完成
```

因此 store 适合使用“两阶段状态”。

### 5.1 ROB commit 阶段

ROB 提交 store 时：

```text
stq.committed := true
stq.arch_traffic_check := debug_maincore_status == 2
stq.traffic_cacheable := canonical_cacheable
```

这一步只锁存架构资格，不增加路径计数。

### 5.2 Cacheable store 完成

在：

```scala
dataWriteArb.io.in(0).fire
```

发生时，根据对应的 `stq_idx` 生成：

```text
path = CACHE_STORE
path_valid = true
```

严格记账条件为：

```text
stq.committed &&
stq.arch_traffic_check &&
!stq.path_counted &&
cache_store_completion
```

### 5.3 Uncacheable store 完成

在：

```scala
io.mem_access.fire
```

发生时，根据 MSHR 中携带的 `stq_idx` 生成：

```text
path = UNCACHE_STORE
```

严格记账条件与 cacheable store 相同。

### 5.4 Store 需要返回 STQ 索引

当前 DCache 的 cache store 计数直接在 DCache 内部完成：

```scala
val completed_store_cache =
  dataWriteArb.io.in(0).fire &&
  s3_req.traffic_check &&
  ...
```

建议改为输出一个带索引的完成事件：

```text
store_cache_complete_valid
store_cache_complete_stq_idx
store_cache_complete_cacheable
```

uncache MSHR 同样输出：

```text
store_uncache_complete_valid
store_uncache_complete_stq_idx
```

由 LSU 根据 STQ 项中的：

```text
committed
arch_traffic_check
path_counted
```

完成最终结算。

这样可以避免 DCache 直接根据全局 `traffic_check_state` 做最终记账。

## 6. Cacheability 必须统一

大核和小核的 cacheable/uncacheable 分类必须使用同一个定义。

当前 BOOM DCache ingress 使用：

```scala
edge.manager.supportsAcquireBFast(
  io.lsu.req.bits(w).bits.addr,
  lgCacheBlockBytes.U)
```

checker 侧的 cacheability 来自 LSL packet 中的 cacheability 位。

建议把 BOOM 的 cacheability 在访存地址确定时锁存到 LDQ/STQ：

```text
ldq.traffic_cacheable
stq.traffic_cacheable
```

该字段之后不能重新计算。

统一原则：

```text
cacheable = edge.manager.supportsAcquireBFast(addr, blockBytes)
```

对于 forwarding load，即使它没有真正访问 DCache，也必须使用 LDQ 中保存的这个字段。

应增加断言：

```text
DCache response cacheability == LDQ/STQ stored cacheability
```

如果两者不一致，说明 cacheability 判定路径不统一。

## 7. 严格路径计数的定义

建议定义以下计数。

### Store

```text
strict_store_cache
    已提交、统计窗口内、最终通过 cache data-array 完成的 store

strict_store_uncache
    已提交、统计窗口内、最终通过 uncache TileLink A 通道完成的 store

strict_store_total
    strict_store_cache + strict_store_uncache
```

### Load

```text
strict_load_cache_response
    已提交、统计窗口内、通过 cache response 完成的 load

strict_load_forward
    已提交、统计窗口内、通过 store-to-load forwarding 完成的 load

strict_load_uncache
    已提交、统计窗口内、通过 uncache response 完成的 load

strict_load_cache
    strict_load_cache_response + strict_load_forward

strict_load_total
    strict_load_cache + strict_load_uncache
```

这组定义中：

```text
strict_load_forward
```

是 `strict_load_cache` 的子集，不能再和 `strict_load_cache` 相加。

预计本次测试应满足：

```text

strict_store_uncache = 49
strict_store_total    = 60570

strict_load_cache    = 94765
strict_load_uncache  = 297
strict_load_total     = 95062
```

forwarding 的具体数量可以单独报告，但不能再作为 total 的额外加项。

## 8. 保留旧计数，新增严格计数

为了避免破坏已有调试含义，建议不要直接覆盖现有计数器。

当前 `trafficCounterLive` 的定义是：

[`dcache.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:1414)

```scala
load_total =
  load_cache_count +
  load_uncache_count +
```

### 3. LDQ 增加路径状态

`LDQEntry` 当前位于：

[`lsu.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:207)

或者使用互斥枚举/编码。

语义：

- DCache cache response 到达：记录 cache response path；
- uncache response 到达：记录 uncache path；
- forwarding writeback 到达：记录 forwarding path；
- 发生 branch kill、nack、memory ordering failure：清除当前路径状态；
- ROB commit 前只允许一个最终路径；
- commit 后释放 LDQ 项。

forwarding 必须根据：

```text

ldq(f_idx).traffic_path_*
```

```text

```

### 4. STQ 增加提交和路径状态

[`lsu.scala`](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:231)

- ROB commit 时锁存 `traffic_arch_check`；
- 地址确定时锁存统一 cacheability；
- cacheable store 完成时设置 cache path；
- uncache store 完成时设置 uncache path；
- 每个 STQ 项最多只允许一次严格结算。

### 6. Load 严格结算应在 commit 时完成

Load 的路径完成早于 ROB commit：

```text
response/forwarding -> ROB commit
```

因此建议：

- response/forwarding 只记录 path metadata；
- ROB commit 时读取 LDQ path metadata；
- commit 时递增严格微结构计数。

严格 load 事件：

```text
strict_load_commit =
  commit.arch_valid &&
  commit.uop.uses_ldq &&
  commit.uop.mem_cmd == M_XRD &&
  ldq.path_valid
```

分类：

```text
path_cache_response -> STRICT_LOAD_CACHE_RESPONSE
path_forward        -> STRICT_LOAD_FORWARD
path_uncache        -> STRICT_LOAD_UNCACHE
```

聚合：

```text
STRICT_LOAD_CACHE =
  STRICT_LOAD_CACHE_RESPONSE + STRICT_LOAD_FORWARD

STRICT_LOAD_TOTAL =
  STRICT_LOAD_CACHE + STRICT_LOAD_UNCACHE
```

这样 speculative response、replay、nack、branch-killed load 不会进入严格计数。

### 7. Store 严格结算在实际完成路径完成

store 已经先 ROB commit，因此 store path completion 时可以检查：

```text

!stq.traffic_path_counted
```

然后按实际路径增加：


## 关键设计决定

1. 架构计数必须在 BOOM ROB 提交处使用：

```scala

io.core.commit.uops(w)
```

普通访存判定：

```scala

load : arch_valid && uses_ldq && mem_cmd === M_XRD
```

不要使用 `commit.valids` 作为架构口径，也不要用 DCache response 直接代表架构计数。

2. `traffic_check_state` 只用于锁存统计资格，不能在 forwarding 或 delayed response 处简单使用 `RegNext` 延迟两拍。

3. LDQ 项需要锁存唯一完成路径：

```text

2 = uncache response
3 = store-to-load forwarding
```

同一个 LDQ 项只能记录一个路径，提交时再增加严格 load 统计。

4. forwarding 统计必须依据对应的：

```scala
wb_forward_ldq_idx(w)

ldq(f_idx).bits.traffic_path_valid
```

不能继续依赖：

```scala

```

5. cache/uncache response 需要只记录 LDQ 路径元数据；nack、replay、branch kill 不能完成统计。

6. store 严格统计必须以架构已提交的 STQ 项为资格，不能只依据 DCache 请求阶段采样的 `traffic_check`。当前较稳妥的方向是让 DCache 返回带 STQ index 的 store completion，LSU 根据：

```text
stq(idx).traffic_cacheable
!stq(idx).traffic_seen
```
