## 10. 助手 · 2026-09-23T14:13:13.416Z

我说的“扩展协议”，是指在 L1 把安全前驱写进 L2 时，**只更新 L2 的数据副本，但不让 L1 失去当前 cache line 的所有权**。

例如 L1 中是包 P1 的安全值，随后 P2 对同一 line 做推测写：

```text
L1 -- SafeSnapshot(P1, 地址, 数据) --> L2
L2 更新为 P1 的安全值，但目录仍记录 L1 持有更新的版本
L1 再写入 P2 的推测值
```

这样 L2 保存着最新安全前驱，L1 保留较新的推测版本。此后如果其他请求访问该 line，目录仍要知道 L1 持有更新版本，不能把 L2 的快照误当成当前一致性值。

普通 TileLink `ReleaseData` 不是这种操作：它把数据交给 L2 的同时表示 L1 正在释放该 line 的权限。当前 C 通道和 sideband 能携带写回归属信息，但 sideband 本身不会改变 `ReleaseData` 的协议语义。因此，保留 L1 新版本需要端到端新增一种快照写入语义，或单独的数据通路，并让 L2 更新数据但保留相应目录状态。相关 C 通道处理可见 [SourceC.scala](/data1/gzh/EC/chipyard/generators/sifive-cache/design/craft/inclusivecache/src/SourceC.scala) 和 [SinkC.scala](/data1/gzh/EC/chipyard/generators/sifive-cache/design/craft/inclusivecache/src/SinkC.scala)。

另一种做法是不扩展消息语义：用普通 `ReleaseData` 把安全值交给 L2，L1 释放 line，再重新获取权限并写入 P2。协议更常规，但重新获取期间 Store 需要等待；即使不专门为校验水位 stall，也会有实际的协议延迟。

还剩一个必须区分的点：**统计桶满可以只让统计无效；保存待写回数据的缓冲满则不同。**如果此时继续放行并丢弃或绕过待写回数据，安全前驱就可能丢失，不能只靠置“统计无效”保证数据正确。要坚持不兜底 stall，就必须保证功能数据缓冲不溢出；若无法保证，溢出时只能接受该次运行不再保证隔离正确，或者允许反压。统计元数据桶和实际保存 cache line 的数据缓冲应分别设计、分别报告溢出状态。

“扩展协议”可以缩小理解为两件事：

- **L1 replacement**：走现有 L1→L2 写回即可，替换本来就会释放 L1 line；不需要为这个场景新增通用 TileLink 消息。
