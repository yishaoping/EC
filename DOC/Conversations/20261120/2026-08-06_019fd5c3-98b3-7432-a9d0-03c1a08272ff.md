**一、主要原因：Rocket checker 的校验访存绕过了 DCache**

Rocket 在 checker mode 下明确关闭本地 DCache 请求：

[RocketCore.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/rocket/RocketCore.scala:1482)

```scala
io.dmem.req.valid := ... 0.U ...
```

校验访存改走：

```scala
lsl_req_valid
lsl_req_addr
lsl_req_cmd
```

见 [RocketCore.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/rocket/RocketCore.scala:1523)。

因此：

- BOOM DCache 统计的是大核 LSU 发出的真实 DCache 请求；
- Rocket DCache 统计的不是 checker 正在校验的 LOAD/STORE；
- checker 实际消费的是 LSL FIFO 中的 BOOM packet。

Rocket 当前计数条件位于 [NBDcache.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/rocket/NBDcache.scala:997)，而 v1 默认 `nMSHRs=1`，实际使用的正是 `NonBlockingDCache`：[HellaCache.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/rocket/HellaCache.scala:257)。

所以 hart1～4 的 `traffic_counter` 数值主要是：

- checker 初始化和收尾阶段的普通访存；
- self-exception、postchecking 等阶段的本地访存；
- PTW 页表访问；
- 可能的 RoCC/HellaCache 访问。

它们不是 BOOM packet 的校验访存数量。这是当前 1600～1800 数量级差异的根因。

**二、BOOM 端存在的漏计和多计**

BOOM 计数代码在 [dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:498)：

```scala

io.lsu.req.bits(w).bits.uop.mem_cmd === M_XRD
```

漏计：

- `LR`：`M_XLR`
- `SC`：`M_XSC`
- AMO：`M_XA_ADD` 等
- 其他 `isRead/isWrite` 覆盖但不等于 `M_XRD/M_XWR` 的命令

测试程序明确包含：

- `lr.w`
- `sc.w`
- `amoadd.w`

见 [test.c](/data1/gzh/EC/Software/Test/test.c:93) 和 [test.c](/data1/gzh/EC/Software/Test/test.c:130)。

按循环边界，每个循环执行 144 次，三轮测试中大约包含：

- 864 次 LR
- 864 次 SC
- 432 次 AMO

如果计数目标是“所有访存事件”，这些都会被当前 BOOM 计数器漏掉。

多计：

1. **投机 LOAD 可能被错误计入**

BOOM 在请求进入 DCache、`io.lsu.req.fire` 时计数。但后续流水线仍可能因为分支预测错误或异常被杀掉：

[dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:640)

因此当前统计更接近“第一次进入 DCache 的请求尝试”，不是“提交或退休的 LOAD”。

2. **HellaCache 请求混入**

[common/tile.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/common/tile.scala:550)

LSU 中这些请求带有 `is_hella` 标志，但计数条件没有排除它们：

[lsu.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:835)

所以检查窗口内的页表访问、RoCC 访问也可能被计入 BOOM 的 LOAD/STORE 总数，而这些访问没有对应的 GHT 校验 packet。

3. **窗口边界可能漏计**

`traffic_seen` 在 DCache fire 时置位：

[lsu.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:868)

如果某条指令第一次 fire 发生在检查窗口外，之后 retry 进入窗口内时，因为 `traffic_seen=true`，它不会再被计数。

当前 `traffic_seen` 主要用于抑制 nack/retry 重复计数，因此 BOOM 端普通 nack/replay 并不是主要的多计源；它的副作用是统计节点和计数窗口不一致时会漏计。

**三、Rocket 端存在的漏计和多计**

漏计：

1. checker 的正常 LOAD/STORE 不经过 DCache，几乎全部漏掉。
2. Rocket DCache 也只匹配：

所以本地 `LR/SC/AMO` 也不会进入这两个计数器。

3. Rocket 已有的 LSL 计数信号也不完整：

[R_LSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_LSL.scala:149)

```scala

```

而 `req_cmd=11` 表示同时具有读写语义的 SC/AMO，这类 packet 会 dequeue，但 `ld_deq/st_deq` 两者都不增加。因此现有 `debug_perf_num_ld/st` 也会漏掉 SC/AMO。

多计：

1. Rocket 的计数使能为：

[RocketTile.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/tile/RocketTile.scala:299)

```scala

```

但 `icsl_status=0` 不仅表示 checking，还包括：

- reset
- self exception
- postchecking
- checker 尚未真正开始消费 packet
- LSL 或 RSU 尚未排空

所以 Rocket 会把检查外的本地访问多计进去。

因此 Rocket 的非零计数不能直接解释为 checker 指令数。

**四、还有一个需要检查的 packet 漏计风险**

BOOM 的 GH_BUF 和 Rocket 的 R_LSL FIFO 入队都没有标准 ready/valid 反压握手。

例如：

[GH_BUF.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/trans/GH_BUF.scala:172)

```scala
u_buffer(i).io.enq_valid := ...
```

FIFO 满时只是不接受写入，并没有向上游返回 ready。与此同时，BOOM 只用最后一个 FIFO 的水位产生 `core_hang_up`：

[GH_BUF.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/trans/GH_BUF.scala:76)

这存在某个非最后 FIFO 满而 packet 被丢弃的可能。R_LSL 入队也有类似结构：[R_LSL.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/r/R_LSL.scala:91)。

这属于潜在 packet 漏计，需要增加：

- FIFO full/drop 计数器；
- packet enqueue/dequeue 计数器；
- packet sequence number。

**五、正确的比较方案**

建议不要再比较 BOOM DCache 与 Rocket DCache。

应比较同一种架构事件：

1. BOOM：在提交访存指令并成功生成/入队 GHT memory packet 时计数。
2. Rocket：在 LSL packet 真正 dequeue 并被 checker 消费时计数。
3. packet 类型至少区分：

```text
normal load
normal store
LR
SC
AMO
```

4. 为 packet 携带 sequence/epoch，检查：

```text
BOOM commit
 -> GH_BUF enqueue
 -> CDC send
 -> Rocket LSL enqueue
 -> Rocket LSL dequeue
```

5. 如果还要比较 cache/uncache，必须由 BOOM 根据物理地址/PMA 判断后把分类位随 packet 传给 checker。Rocket checker 本身没有对被校验地址发起真实 DCache 访问，无法从自己的 DCache 得到同一分类。

另外，当前计数器只有 `RegInit`，没有测试开始时的 clear/start/stop 机制。重复测试或检查窗口切换时会受到历史计数和边界流水线的影响。

总的判断是：

- 当前巨大差值的主因是 Rocket checker 访存绕过 DCache；
- BOOM 端还会多计投机 LOAD、PTW/RoCC HellaCache 请求；
- 两端都会漏计 LR/SC/AMO；
- Rocket 的检查窗口使能过宽，会混入非 checker 访问；
- packet FIFO 还存在额外的潜在丢包漏计风险；
- `store_cache + store_uncache = store_out`、`load_cache + load_uncache = load_out` 均成立，说明六个计数器内部加法没有问题，问题在事件选择和比较口径。

## 重要设计决策

### BOOM cacheability

BOOM DCache 内部已经使用：

```scala
edge.manager.supportsAcquireBFast(addr, lgCacheBlockBytes.U)
```

可以在 DCache 入口确定请求是否 cacheable。

```scala
val traffic_cacheable = Bool()
```

在 DCache LSU 请求入口锁存：

```scala
s0_req(w).traffic_cacheable :=
  edge.manager.supportsAcquireBFast(s0_req(w).addr, lgCacheBlockBytes.U)
```

并通过 replay/MSHR/response 传递。

### BOOM uncacheable store 完成点

`BoomIOMSHR` 是 uncacheable/MMIO 请求路径：

```scala
class BoomIOMSHR ...
```

其有效写总线发送点是：

```scala
io.mem_access.fire
```

对于：

```scala
req.traffic_check &&
!req.traffic_seen &&
!req.traffic_cacheable &&
req.uop.uses_stq &&
req.uop.mem_cmd === M_XWR
```

可定义 `traffic_store_complete` 输出。

建议：

1. 在 `BoomIOMSHR` IO 增加：
   ```scala
   val traffic_store_complete = Output(Bool())
   ```
2. 在 `io.mem_access.fire` 上生成 pulse。
3. 在 `BoomMSHRFile` 增加同名输出，并 OR 所有 IO MSHR。
4. DCache 使用该 pulse 增加 `store_uncache_count`。

用户明确允许“写入 MSHR 或写上总线”作为 uncache store 统计点，因此 `io.mem_access.fire` 是合适的完成事件。

### Rocket cacheability sideband

Rocket checker 的 LSL 不访问实际 DCache，因此不能直接从 Rocket DCache 请求得到 cacheability。

现有 packet payload 宽度是 136 bit：

- 8 bit instruction index/type
- 128 bit memory data/address
- 实际 BOOM `ldq_header/stq_header` 形式是：
  ```scala
  Cat(data64, zeros24, vaddr40)
  ```
- 因此 payload 的 address bit 63 当前是零填充，且 Rocket 后续 `lsl_resp_addr` 只使用低 40 bit。

可利用 payload address bit 63 携带 cacheability，不改变全局 `GH_WIDITH_PACKETS`，避免大规模拓宽接口。

建议修改：

1. `GH_BUF.scala` 增加：
   ```scala
   val commit_cacheable = Input(Vec(params.core_width, Bool()))
   ```
2. 对 load/store 的 `filter_packet`，将 bit 63 替换为 `commit_cacheable(i)`：
   ```scala
   Cat(io.alu_in(i)(127,64),
       io.commit_cacheable(i),
       io.alu_in(i)(62,0))
   ```
3. `boom/common/tile.scala` 根据 `ldq_header/stq_header` 低 40 位调用：
   ```scala
   outer.dcache.node.edges.out(0).manager.supportsAcquireBFast(...)
   ```
   给 `gh_buf.io.commit_cacheable(w)`。
4. `RocketCore.scala` 从：
   ```scala
   io.packet_lsl(i)(63)
   ```
   传给 R_LSL。
5. R_LSL 当前保存地址低 64 位，增加：
   ```scala
   val resp_cacheable = Output(Bool())
   ```
   输出：
   ```scala
   io.resp_cacheable := Mux(resp_valid_reg, out_packet(63), false.B)
   ```
6. RocketCore 增加 `lsl_resp_cacheable` wire，连接 R_LSL。
7. 在 checker 完成 pulse 上拆分：
   ```scala
   checker_store_cache_complete
   checker_store_uncache_complete
   checker_load_cache_complete
   checker_load_uncache_complete
   ```

注意：不要把 bit 63 传给 ELU 地址比较。当前 `lsl_resp_addr` 是 40 bit，只取低 40 位，因此该 sideband 会被自然截断，不影响地址校验。
