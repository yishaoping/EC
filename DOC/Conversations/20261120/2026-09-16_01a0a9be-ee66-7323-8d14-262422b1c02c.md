基于当前工作树中的源码，我的理解如下。这里先只讨论方案，没有修改代码，也没有运行仿真。

**指标定义**

设粒度 `g` 分别为 byte、word、cache line。跨边界访问会命中多个粒度单元。

| 指标 | 我的理解 |
|---|---|
| 第一种 | 对每个包 `p`，统计该包所有“需要校验的 store”触及的唯一物理地址单元数。同一地址在包内出现多次只算一次，不同包重复出现则分别计数。最终结果是所有包计数之和。 |
| 第二种 | 运行过程中，只累加当前还没有达到安全水位的包的第一种计数，记录这个动态总量的最大值。 |
| 第三种 | 对每个包 `p`，找出包内第一次访问为 load 的物理地址单元；如果之后存在本包或更晚包的 store 修改同一地址单元，则该地址对包 `p` 计一次。最后对所有包求和。 |
| 第四种 | 第三种对应的动态在途量峰值。地址在后续 store 真正使条件成立后开始计入，包达到安全水位后移除。 |

我建议“第一操作”按架构提交顺序定义，而不是 DCache 实际请求顺序。否则乱序执行、replay 和 store-to-load forwarding 会改变结果。同周期多条提交按 ROB lane 顺序处理。

粒度建议定义为：

- byte：访问实际覆盖的每个字节。
- word：访问覆盖的每个对齐 word。
- cache line：访问覆盖的每个对齐 `blockBytes` 缓存行。

其中 word 必须进一步确定是 RISC-V 的 4 字节 word，还是当前 DCache 的 8 字节 machine word。

**最关键的问题**

1. `lastLoadPacketSeq` 单独不能实现第三种指标。

例如：

```text
包1: load A
包2: load A
包3: store A
```

按当前描述，A 应分别计入包1和包2。但一个 `lastLoadPacketSeq` 在 store 到来时只剩包2，包1会丢失。因此它最多能实现“最后一个读者包”的指标，不能实现“每个读过该地址的包”的指标。

2. 当前的 `dirtyPacketSeq` 严格来说不是普通的“最后一次 store 包序号”。

它只在 cacheable store 真正写入 DCache 时更新，并保留该 resident line 见过的最大校验包序号；后续非校验 store 不会清除它，refill 才会清除。这是保守的 dirty writeback 安全归因，而不是通用访问历史，见 [dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:1388)。

因此不建议直接把新统计建立在 `dirtyPacketSeq + lastLoadPacketSeq` 上，否则会把安全归因状态和访问顺序状态混在一起。

3. 缓存行上的元数据无法保证物理地址全局去重。

以下情况都会破坏精确性：

- 包内访问 A，A 被替换，随后同一包再次访问 A，会重复计数。
- 包1 load A 后 A 被替换，包2 store A 时已经找不到包1的 load 记录。
- uncacheable/MMIO 根本不驻留在 DCache。
- byte、word 粒度不能只靠一个 line 级序号表达。

所以 per-line 元数据只适合“当前驻留缓存行”的近似统计。精确统计需要独立的、以物理地址为 key 的表，或者离线分析。

4. load 必须在提交点采集。

当前 load 请求没有携带包序号，普通 load 的 `packet_seq` 仍为默认零；store 则在提交时写入活动包序号，见 [lsu.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:1821)。

如果在 DCache load hit/miss 上更新 `lastLoadPacketSeq`，还会遇到：

- 推测执行后被 squash；
- nack/replay 重复；
- load 提前越过较老操作；
- store-to-load forwarding 不经过 DCache 数据读取。

LSU 在提交时仍持有物理地址、`mem_size` 和访问类型，[lsu.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:1849) 已经用这些字段输出 MEMTRACE，因此提交点是更合适的统计事件源。

5. “需要校验的 store”目前存在两种口径。

GH_BUF 对 `uses_stq && !fence` 形成 type 2 包，其中包含普通 store、SC 和 AMO，见 [GH_BUF.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/trans/GH_BUF.scala:120)。当前严格流量统计则只认 `arch_valids && mem_cmd == M_XWR`，见 [lsu.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/lsu.scala:1782)。

必须先决定：

- 只统计普通架构 store；
- 还是统计所有送往 checker 的 type 2 访存，包括 SC/AMO；
- SC 失败是否算“修改过数据”，通常不应该；
- MMIO/uncacheable 是否属于“数据物理地址”。

6. “未校验”和“未达到安全水位”不是同一件事。

当前 `safePacketWatermark` 只跨过连续 PASS 的包，[dcache.scala](/data1/gzh/EC/chipyard/generators/boom/src/main/scala/lsu/dcache.scala:1040)。所以：

- 后面的包即使已经 PASS，只要前面有洞，仍属于未安全；
- FAIL/CANCELLED 会永久阻塞水位，后续所有包都会一直计入峰值；
- 若只想表示“结果尚未返回”，应看 `completed` 位图，而不是水位。

你明确提到“验证安全水准”，所以我倾向第二、第四种使用“尚未安全”，即 `seq > safePacketWatermark`。

7. 第四种需要明确计入时间。

例如：

```text
包1 load A
包1 已经 PASS 并进入安全水位
包2 store A
```

第三种按字面仍会把 A 计入包1。但包2 store 时包1已经安全，第四种是否曾包含 A？

我建议第四种定义为：后续 store 已经发生，并且原 load 包此时仍未安全。这样它表示真实在途风险，能够在线统计；如果希望从包1 load 开始追溯计入，则需要预知未来，只适合离线计算。

8. byte、word、line 的第三种不能简单互相推导。

例如先 `load byte 0`，再 `store byte 1`：

- byte 粒度没有同一个字节被修改；
- 若二者属于同一个 word，则 word 粒度满足；
- cache line 粒度也满足。

因此第三、第四种必须分别维护“该粒度下首次访问类型”，不能只算 byte 后简单汇总成 word/line。

**建议方案**

第一、第二种相对容易：在架构提交点生成 `{packet_seq, paddr, size, store}` 事件，每个当前包维护以 cache line tag 为 key 的表，表项保存 store byte mask。由 byte mask可以计算第一种的 byte/word/line 唯一数；包结束后只保留三个计数，供安全水位推进时从当前在途量中扣除。

第三、第四种需要反向关系：

```text
物理地址单元 -> 所有尚待后续 store 匹配的 load-first 包集合
```

这不是一个 `lastLoadPacketSeq` 能表达的。精确硬件表在最坏情况下会随着包数和唯一 load 地址数增长。当前单包最多 5000 条指令，[GH_GlobalParams.scala](/data1/gzh/EC/chipyard/generators/rocket-chip/src/main/scala/guardiancouncil/GH_GlobalParams.scala:10)，因此资源和关联查找代价都不小。

我的建议是先建立一个提交级离线黄金模型：给现有 MEMTRACE 增加 `packet_seq`，同时记录包分配和安全水位变化，用软件集合精确算出 12 个结果，也就是四类指标乘三种粒度。确认语义和实际数据规模后，再决定硬件实现采用：

- 精确但有容量上限的 SRAM/hash 表，并提供 overflow/valid 标志；
- 只跟踪未安全包，精确实现第二、第四种安全峰值；
- 第一、第三种总量保留为仿真或离线统计。

在进入实现前，最需要确定的是：word 是 4B 还是 8B、SC/AMO/MMIO 是否计入、第四种从 load 时刻还是从后续 store 时刻开始计入，以及 FAIL/CANCEL 后是否继续统计安全峰值。

口径已经比较清楚了：

- 四种粒度：1B、4B、8B、cache line。
- 只统计架构提交的、cacheable 普通 `M_XRD/M_XWR`。
- 第二、第四类以 `seq > safePacketWatermark` 作为“尚未安全”。
- 第四类在后续 store 发生时才计入，且原 load 包当时必须尚未安全。
- FAIL/CANCELLED 后立即冻结统计并置错误，由软件报告结果无效。

**推荐的宽口径**

定义每个包的 `load-first candidate` 集合：

> 在该包中，某物理地址粒度的第一次架构访问是 load，就加入集合；不再要求未来一定出现 store。

四种粒度分别独立维护：

```text
wide3[g] = Σ 每个包的唯一 load-first candidate 数量

wide4_current[g] =
    当前所有尚未安全包的 load-first candidate 数量之和

wide4_peak[g] = max(wide4_current[g])
```

它是原第三、第四类的严格上界：

```text
exact3[g] <= wide3[g]
exact4_current[g] <= wide4_current[g]
exact4_peak[g] <= wide4_peak[g]
```

这个方案比“统计所有唯一 load 地址”更合适。后者会把“先 store、后 load”的地址也算进去，口径过宽；`load-first candidate` 只需要维护包内首次访问状态，复杂度增加不大，但与目标指标更接近。

**为什么实现简单**

它不需要保存“某地址被哪些历史包 load 过”，因此不需要跨包 reader 列表，也不需要 `lastLoadPacketSeq`。

每个当前包只需维护四套独立状态：

```text
seen[g]       // 本包是否已经访问过
storeSeen[g]  // 本包是否已经由 store 触及
loadFirst[g]  // 第一次访问是 load
```

提交 load 时：

```text
newLoadFirst = touched[g] & ~seen[g]
loadFirst[g] |= newLoadFirst
seen[g]      |= touched[g]
```

提交 store 时：

```text
newStore      = touched[g] & ~storeSeen[g]
storeSeen[g] |= touched[g]
seen[g]      |= touched[g]
```

`newStore` 更新第一、第二类；`newLoadFirst` 更新宽口径第三、第四类。包切换后只需保留该包的四组计数，供安全水位推进时从当前在途量中扣除。

**建议再加一个简单下界**

在已有状态基础上，可以很便宜地增加“同包 load-first 后又 store”的统计：

```text
samePkgQualified[g] =
    第一次访问是 load，并在同一个包中随后被 store 的唯一地址
```

store 时计算：

```text
newSamePkg = touched[g] & loadFirst[g] & ~qualified[g]
```

这样可以得到：

```text
samePackage3[g] <= exact3[g] <= wide3[g]
samePackage4Peak[g] <= exact4Peak[g] <= wide4Peak[g]
```

这个上下界很有价值：

- 上下界接近：跨包修改贡献很小，没有必要立刻实现复杂的历史 reader 表。
- 上下界差距很大：跨包 load-store 关系重要，后续值得实现精确第三、第四类。
- 宽口径明显小于第一类：store 工作集远大于潜在的 load-first 工作集。
- 宽口径接近或超过第一类：读后可能失效的数据规模不可忽略。

**四种粒度**

建议四套首次访问状态分别计算，不能从 byte 结果事后聚合：

```text
byte       : 每个实际覆盖字节
word4      : 每个对齐 4B 单元
word8      : 每个对齐 8B 单元
cache line : 每个对齐 blockBytes 单元
```

例如先 load byte 0、再 store byte 1，byte 级不满足同地址修改，但 word4、word8、line 可能满足。

**异常处理**

FAIL、CANCELLED、地址表溢出或包槽冲突都应进入统一的停止路径：

```text
statsRunning := false
statsValid   := false
statsErrorReason := fail / cancelled / tableOverflow / slotCollision
```

建议冻结错误发生前的计数，但软件只打印错误原因，不把数值作为有效统计结果。这样不会因安全水位停止推进而让峰值继续无意义增长。

第一阶段我建议同时统计“原第一、第二类 + load-first 上界 + 同包下界”。它不解决精确的跨包第三、第四类，但能够用较低复杂度判断精确实现是否值得。

可以，而且这类统计在硬件上比第三、第四类更容易实现。关键是先明确“其他读写操作”作用于哪个范围。

我建议按**同一粒度、同一物理地址单元**理解：

> 对某个 byte、4B word、8B word 或 cache line，如果当前架构提交的 load 之前，对该单元的最近一次架构访存是 store，则记为一次写后读；中间不能出现对该单元的其他 load/store。

例如：

```text
S A, L A              -> 1 次
S A, S A, L A         -> 1 次，第二个 store 与 load 配对
S A, L A, L A         -> 1 次，第二个 load 前有 load
S A, S B, L A         -> 1 次，同地址口径
S A, S B, L A         -> 0 次，若按全局访存相邻口径
```

我建议使用“同地址单元”口径。否则任意其他地址的访存都会打断配对，统计结果更接近全局访存序列相邻性，而不是地址的数据复用关系。

**实现状态**

每种粒度独立维护：

```text
lastOp[g][address] = NONE / STORE / LOAD
lastOpPacketSeq[g][address]
```

在 load 到来时：

```text
lastOp == STORE -> 写后读命中
```

随后把状态改为 `LOAD`。新的 store 会把状态重新改为 `STORE`，因此不要求它是该地址的第一次写。

只记录 `lastStorePacketSeq` 不够，因为无法判断 store 后是否已经出现过其他 load/store。`lastLoadPacketSeq` 对这类判断也不是必需的。

**总量和峰值**

我建议把一次命中归属到 **load 所属的包**：

- 总量：每次命中时，对对应粒度的 `wr_total` 加一。
- 在线量：如果 load 包尚未达到 `safePacketWatermark`，对该包的 bucket 和全局在线量加一。
- 包达到安全水位后，从在线量中扣除该包累计的写后读次数。
- 峰值就是在线量的最大值。

这样即使 store 属于已经安全的旧包，只要后续 load 所属包尚未安全，这次写后读仍会进入在线峰值，定义比较稳定。

如果改为归属 store 包，跨包情况下会出现“store 已安全、load 后来才到达”的延迟归属问题，在线峰值语义会复杂很多。

**宽口径估计**

可以定义一个简单上界：

> 只要该地址在历史上出现过 store，后续每次 load 都计入，忽略中间是否有其他访存。

这只需维护 `everStored` 或持久的 `lastStore`，实现简单，但会明显高估：

```text
S A, L A, L A
```

严格口径是 1 次，宽口径会是 2 次。

因此建议同时保留：

1. `strict write-read`：维护 `lastOp`，检查真正的相邻关系。
2. `wide write-read`：只检查历史上是否写过，作为上界估计。

如果目标只是先判断这类行为规模，宽口径可以先做；但它与严格结果的差距可能很大，尤其是循环反复读取同一地址时。

**需要特别注意**

- 四种粒度必须独立统计，不能由 byte 结果推导 word 或 cache line。
- 同一条 store/load 可能覆盖多个单元，按实际 mask 分别处理。
- 在 byte 粒度下，不同 byte 的访问不互相打断；在 cache-line 粒度下，同一行内任意其他 byte/word 访问都会打断。
- 同周期多条提交必须按架构顺序处理，否则 store/load 的先后关系可能不确定。
- 如果统计表只跟随 DCache resident line，发生替换、refill 或表溢出后不能继续声称结果精确，必须清除状态或标记统计无效。
- 第三、第四类是“唯一地址数量”，而写后读更自然是“配对出现次数”。例如 `S A,L A,S A,L A` 应是 2 次，而不是 1 个地址。两者不能直接比较，除非另外定义去重版本。

所以结论是：可以像第三、第四类一样增加宽口径总量和未安全峰值；但这类关系本身用 `lastOp` 就能做较紧的在线统计，建议把“历史写过即算”的宽口径作为估计上界，同时保留严格相邻版本用于比较。

- 粒度分别为 byte、4B word、8B word、cache line；
- 只统计架构提交的普通 cacheable load/store；
- “同一地址”按当前粒度的物理地址单元理解；
- 第三、四类中的“后续 store”可以来自本包或后续包；

## 六类指标

| 类别 | 含义 | 结果性质 |
|---|---|---|
| 1 | 所有包中需要校验的 store 地址单元总数，包内重复地址只算一次 | 精确总量 |
| 2 | 第 1 类的在线峰值，只统计当前尚未安全的包 | 精确峰值 |

## 第一、二类：精确统计

对每个包、每种粒度维护唯一 store 地址集合：

```text
storeSet[packet][granularity]
```

每次架构提交普通 store 时，根据地址和访问 mask 生成四种粒度的地址单元集合：

```text
byteSet
word4Set
word8Set
lineSet
```

如果某个单元在当前包中第一次出现：

```text
package_store_count[g] += 1
online_store_count[g] += 1   // 当前包尚未安全时
```

包进入安全水位后：

```text
online_store_count[g] -= package_store_count[g]
```

因此：

```text
metric1[g] = 所有包 package_store_count[g] 的累加
metric2[g] = max(online_store_count[g])
```

这里必须使用完整物理地址或完整 tag，不能只使用 cache set/way。cache line 的 `dirtyPacketSeq` 只能用于 dirty 归因，不能直接作为包内唯一地址集合。

## 第三、四类：推荐的上下界方案

第三类的严格条件是：

```text
某地址在包 p 中第一次访问是 load
并且之后出现 store
```

如果多个包都先 load 同一地址，后续一个 store 可能同时满足多个包：

```text
P1: load A
P2: load A
P3: store A
```

严格结果应为 P1、P2 各计一次。因此一个 `lastLoadPacketSeq` 不能得到严格总量。

### 第三类上界

使用“load-first candidate”作为上界：

> 只要某地址在包内第一次访问是 load，就计入候选集合，不要求之后真的出现 store。

```text
upper3[g] =
    所有包中第一次访问为 load 的唯一地址单元数
```

它满足：

```text
exact3[g] <= upper3[g]
```

这个上界相对紧，而且所需状态与第四类的“首次访问判断”基本重合。

例如：

```text
P1: load A
P2: load B
P3: store C
```

上界会统计 A、B，但只有真正后续被 store 的地址才属于严格第三类。

### 第三类下界

建议维护每个地址单元**最近的一个未匹配 load-first 包**：

```text
latestLoadFirstPacket[g][addr]
```

当某包第一次访问该地址是 load 时，记录该包序号；如果已经有旧候选，则用新的包覆盖旧候选。

后续发生 store 时：

```text
如果存在 latestLoadFirstPacket：
    下界 +1
    清除该候选
否则：
    不计数
```

这个方案可能丢失较早的包，但不会误计，因此满足：

```text
lower3[g] <= exact3[g] <= upper3[g]
```

例如：

```text
P1: load A
P2: load A
P3: store A
```

最近候选方案只计 P2，结果为 1；严格结果为 2，因此是有效下界。

相比“只统计同包内 load-first 后 store”，最近候选方案能覆盖一部分跨包情况，准确度更好，而状态仍然只需要一个包序号，不需要完整 reader 列表。因此这是第三类较合适的折中方案。

## 第四类：精确在线峰值

第四类不能使用第三类的最近候选，因为峰值要求当前所有尚未安全包都不能漏掉。

对仍未安全的包，需要维护：

```text
firstLoad[p][g][addr]
qualified[p][g][addr]
```

当地址在包 `p` 中第一次访问是 load：

```text
firstLoad[p][g][addr] := true
```

当后续 store 发生时，对所有当前尚未安全的包：

```text
firstLoad[p][g][addr] && !qualified[p][g][addr]
```

满足条件的包都标记为 `qualified`，并使：

```text
online3[g] += 1
package_bucket4[p][g] += 1
```

包进入安全水位后：

```text
online3[g] -= package_bucket4[p][g]
```

最后：

```text
metric4[g] = max(online3[g])
```

这意味着第四类精确统计需要保存“一个地址对应哪些尚未安全包”，而不是只保存一个最后 load 包序号。可以使用包位图或地址—包关联表实现，但必须设置容量上限；发生溢出时应停止统计并报告错误，否则不能声称峰值精确。

## 第五类：推荐的上下界方案

第五类定义为：

```text
前一个同地址操作是 store
当前操作是 load
中间没有其他同地址读写
```

### 第五类下界

维护每种粒度下每个地址单元的最近操作：

```text
lastOp[g][addr] = UNKNOWN / STORE / LOAD
```

load 到来时：

```text
lastOp[g][addr] == STORE
```

才计入下界，然后把状态改为 `LOAD`。

store 到来时把状态改成 `STORE`。

如果历史状态未知、表项被驱逐或发生容量不足，则当前 load 不计入下界。这样：

```text
lower5[g] <= exact5[g]
```

例如：

```text
S A, L A, L A
```

下界计数为 1。

### 第五类上界

维护一个 sticky 状态：

```text
everStored[g][addr]
```

只要地址历史上出现过 store，之后每次 load 都计入上界，不检查中间是否出现过其他操作：

```text
everStored[g][addr] == true
```

例如：

```text

```

上界计数为 2，而严格结果为 1。

因此：

```text

```

第五类采用 `lastOp + everStored` 比较合适：`lastOp` 本来就是第六类精确峰值所需的状态，再增加一个 sticky 位即可得到上界，成本较低且上下界通常比“下界只统计同包、上界统计所有 load”更紧。

## 第六类：精确在线峰值

第五类每次命中时，把事件归属到当前 load 所属的包。

当：

```text

```

且当前 load 包尚未安全时：

```text
online_wr[g] += 1
package_bucket6[packet][g] += 1
```

包进入安全水位后：

```text
online_wr[g] -= package_bucket6[packet][g]
```

峰值为：

```text
metric6[g] = max(online_wr[g])
```

为了保证第六类精确，`lastOp` 必须跨 cache line refill、替换和缓存行驱逐继续有效。仅把它放在 DCache cache line 元数据中是不够的，否则：

```text
S A
cache line A 被驱逐
L A
```

可能漏掉真实的写后读事件。需要独立的物理地址历史表，或在表项丢失时将统计标记为无效。

## 最终推荐输出

每种粒度输出：

```text
store_total                  // 第1类，精确
store_peak                   // 第2类，精确

load_first_lower_total       // 第3类下界
load_first_upper_total       // 第3类上界
load_first_peak              // 第4类，精确

write_read_lower_total       // 第5类下界
write_read_upper_total       // 第5类上界
write_read_peak              // 第6类，精确
```

推荐的核心实现组合是：

```text
第1类：每包唯一 store 集合
第2类：包计数 bucket + safe watermark

第3类下界：每地址最近一个 load-first 包
第3类上界：每包 load-first 候选集合

第4类：未安全包的完整 load-first/qualified 关联

第5类下界：lastOp == STORE
第5类上界：everStored
第6类：完整 lastOp 历史 + 未安全包 bucket
```

这样第三、第五类能够给出有意义的区间，第四、第六类仍然可以保持精确峰值。需要特别强调的是：第四和第六类的“精确”以关联表不溢出为前提；一旦容量不足，应冻结统计并由软件报告统计无效。

```text
metric3[g] = Σp |Qualified[p][g]|
```

```text
包1: load A, load A, store A
```

```text
包1: store A, load A, store A
```

```text
包1: load A
包2: load A
包3: store A
```

```text
upper3[g] = Σp |Candidate[p][g]|
```

```text

    seen := true
    firstOpLoad := true

首次 store：
    seen := true
    firstOpLoad := false

后续任何 load/store：
    不再改变 firstOp
```

```text
firstOpLoad[p][g][a] &&
laterStoreObserved[p][g][a] &&
packet p 尚未安全
```

## 六类最终口径

No code patch has been applied yet in this turn.

3. Add a resettable global `sessionTag` register initialized to a nonzero magic value. On each `io.resetStats`, increment it.
4. Define entry validity as:



- 真正的“第一次读、后续写”必然满足 `everStore`；
- 真正的“第一次写、后续读”必然满足 `everLoad`。


这种情况会使第三类上界保守偏大，但不会低估。

```text

pendingStoreFirst：
    已发现第一次写，但当时还没有观察到 load 的候选数量
```

处理规则：

- 第一次读到达：
  - 若 `everStore` 已置位，立即计入第三类收紧上界；
  - 否则 `pendingLoadFirst` 加一。
- 任意后续 store 到达：
  - 将该地址的 `pendingLoadFirst` 转入第三类收紧上界；
  - 清零 `pendingLoadFirst`；
  - 置 `everStore`。
- 第一次写到达：
  - 若 `everLoad` 已置位，立即计入第五类收紧上界；

## 177. 助手 · 2026-09-21T02:12:13.279Z

我会按现有地址统计设计，比较 byte、4-byte word、8-byte word 和 cache line 四种粒度对去重、峰值、上下界及回滚范围的影响，并给出适合回滚的推荐粒度。这里不修改代码。

## 178. 助手 · 2026-09-21T02:15:27.724Z

当前四种粒度的核心区别，是“一个地址单元有多大”。包内去重、首次操作判断、写后读判断和峰值统计，都是分别在对应粒度上计算，不能由一种粒度简单换算成另一种。

| 粒度 | 统计单位 | 优点 | 缺点 |
|---|---|---|---|
| byte | 每个字节 | 最精确，能区分同一 cache line 内的不同字节 | 状态位最多，硬件开销最大；统计数量通常最大 |
| word4 | 每个 4B 对齐单元 | 适合 32-bit 数据，精度和开销较均衡 | 64-bit 访问可能占两个单位 |
| word8 | 每个 8B 对齐单元 | 适合 RV64，普通 8B 访问通常对应一个单位；比 cache line 精确 | 两个相邻 4B 数据会被视为同一单位 |
| cache line | 每个 cache line | 与 DCache、写回和一致性硬件最匹配，开销最低 | 过于粗糙，同一行内不同地址会被合并 |

例如 cache line 为 64B：

- 一个 8B store：byte 统计 8 个，word4 统计 2 个，word8 统计 1 个，line 统计 1 个。
- 对地址 `A` store、对同一 cache line 内地址 `B` load：
  - byte、word4、word8 可能认为是两个不同地址；
  - cache line 会认为是同一个地址单位，可能计入写后读。

因此，粒度不仅影响总量，也会影响第三、第五、第七类的首次操作和写后读分类，不能只把结果按比例换算。

我的建议是分两层处理：

1. **实际硬件回滚：选择 cache line。**  
   当前 DCache 的一致性、脏数据、写回和恢复天然以 cache line 为单位。按 cache line 回滚最容易保证完整性，避免只恢复部分 word 导致同一 cache line 内数据不一致。

2. **后续优化和精细分析：重点看 word8。**  
   BOOM 是 RV64，word8 能较好匹配常见 64-bit 访问，同时比 cache line 精确很多，硬件状态和统计规模也明显小于 byte。

如果以后实现真正的子 cache-line 回滚，推荐优先采用 **word8 + byte mask 合并恢复**；在当前实现阶段，建议使用 **cache line 作为安全回滚依据，word8 作为优化参考粒度**。

为什么swr\_peak跟sf\_peak对比，在字节粒度差不多，后面则越差越多了呢


## 180. 助手 · 2026-09-21T02:32:30.005Z

这通常是定义造成的正常现象，不一定是统计错误。

这里：

- `sf_peak`：第六类，store-first 后，只要以后出现过 load 就计入；
- `swr_peak`：第八类，store-first 后，**下一次同粒度地址操作必须直接是 load** 才计入。

所以第七、八类是第五、六类的严格子集，理论上应满足：

```text
swr_peak <= sf_peak
```

差距随粒度变粗而扩大，主要原因是“同一地址单元”变大了。

例如同一 cache line 内：

```text
store A
store B
load A
```

其中 A、B 是不同字节，但属于同一个 4B word、8B word 和 cache line。

在 byte 粒度：

- `store B` 不影响 A 的 strict 候选；
- 后面的 `load A` 仍是 A 的下一次操作；
- 因此第五类和第七类都可能计入，两个 peak 接近。

在 word4、word8 或 cache line 粒度：

- `store B` 被认为访问了和 A 相同的地址单元；
- 它成为 A 的下一次同地址操作，而且是 store；
- 第七类候选被清除；
- 但第五类仍然允许后续出现 store，只要之后有 load，所以第五类仍会计入。

因此粒度越粗，越容易出现：

```text
store A -> store B -> load A
```

这种“第五类计入、第七类不计入”的情况，导致 `sf_peak` 和 `swr_peak` 差距扩大。

另外，cache line 粒度会把整条 cache line 看成一个地址单位，同一行内不同 word 的 store/load 都会相互影响，所以差距通常最大。

byte 粒度下两者也不会完全相等，因为第五类允许中间存在其他操作，而第七类要求严格相邻；只是实际程序中相同字节的后续访问经常比较接近，所以表现得较接近。

建议检查：

```text
swr_peak <= sf_peak
swr_total <= sf_upper
```

如果出现 `swr_peak > sf_peak`，才比较像是桶计数、在线量扣减或粒度掩码实现问题。当前这种从 byte 到 word4、word8、cache line 差距逐渐增大的趋势，本身符合两类指标的定义。

这里的“后面三类峰值”应是：

- 第四类 `load_first_peak`
- 第六类 `store_first_peak`
- 第八类 `strict_write_read_peak`

`store_peak` 的口径最宽：只要一个尚未安全包中的地址单元出现过 store，就计入。它包括：

- 只写不读的地址；
- 写后又多次写、但没有读的地址；
- 第一次是 load、后来被 store 的地址；
- 第一次是 store、后来被 load 的地址；
- 没有形成任何后续访问关系的地址。

而后三类都要求额外的访问关系：

| 峰值 | 统计条件 |
|---|---|
| `load_first_peak` | 第一次访问是 load，之后出现 store |
| `store_first_peak` | 第一次访问是 store，之后出现 load |
| `strict_write_read_peak` | 第一次访问是 store，且下一次同粒度访问必须直接是 load |

因此，大量“写一次就结束”的地址会进入 `store_peak`，但不会进入后三类。

例如：

```text
store A
store B
store C
```

这会使 `store_peak` 增加 3，但后三类都不增加。

再比如：

```text
store A
store A
load A
```

- 第五类可以计入，因为最终出现了 load；
- 第七类不会计入，因为 store 后的下一次同地址操作仍然是 store。

还有一个重要原因是峰值都按“当前尚未安全”统计，但候选属于不同时间状态：

```text
包1：store A
包1很快变为安全
包2：load A
```

第五类总量可能认为这个地址最终满足 store-first 后续 load，但第六类峰值不会计入，因为发生 load 时包1已经安全。`store_peak` 和 `store_first_peak` 的最大值也可能出现在不同时间，不能直接拿两个峰值理解成同一时刻的地址集合。

对于同一粒度，通常应满足：

```text
strict_write_read_peak <= store_first_peak <= store_peak
```

因为第八类是第六类的严格子集，第六类又来自第一次 store 的地址，属于第二类的 store 地址集合。

但第四类 `load_first_peak` 与 `store_peak` 没有严格的大小关系。原因是一个后续 store 可能同时确认多个更早包留下的 load-first 候选，所以 `load_first_peak` 理论上甚至可能高于 `store_peak`。

粒度变粗后，差距还可能进一步扩大：

- word4、word8 和 cache line 会把同一单位内的不同地址合并；
- 中间对同一单位的 store 更容易打断严格的 store→load；
- cache line 粒度下，同一行内任意地址的访问都会影响同一个候选。

所以“`store_peak` 很大，而后三类峰值明显较小”本身符合定义。真正需要警惕的是以下异常关系：

```text
strict_write_read_peak > store_first_peak
store_first_peak > store_peak
```

如果出现这些关系，才更像是桶计数、在线峰值扣减或重复计数实现问题。
